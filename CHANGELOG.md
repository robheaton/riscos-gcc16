# Changelog

## Libraries for the 32-bit tool chain: libffi 3.8.0 and OpenSSL 1.1.1w (pre-release `libs-armeabihf-1`, 28 October 2026)

* **New pre-release `libs-armeabihf-1`**: static libraries, headers, pkg-config files and licences of **libffi 3.8.0** and **OpenSSL 1.1.1w** for `arm-riscos-gnueabihf` (hard float), built with the cross compiler 16.2.0-24 and unpacked over it (`-lffi`, `-lssl -lcrypto` then need no flags). A user porting Python 3.8 asked how to add such libraries: those built for GCCSDK 4.7.4 are for the old soft-float ABI and cannot be linked. The release attaches the two upstream tarballs and `SHA256SUMS`. See [docs/EXTRA-LIBS.md](docs/EXTRA-LIBS.md).
* The recipe is [`recipe/extra-libs/build-extra-libs.sh`](recipe/extra-libs/build-extra-libs.sh). OpenSSL's `BSD-generic32` target passes `-pthread`, which the compiler of this tool chain does not accept (threads are in UnixLib); the recipe defines a target without it, so OpenSSL is built thread safe. Random numbers come from `/dev/urandom` (the CryptRandom module); the compiled-in certificate directory is `/OpenSSL`, which does not exist, so programs pass their CA bundle explicitly.
* Checked on the Raspberry Pi (RISC OS 5.30) with three programs, [`tests/extra-libs`](tests/extra-libs): libffi calls and closures (9 checks), OpenSSL digests, AES, an EC key, a certificate and a TLS 1.3 handshake with data both ways (all passed), and four threads at once with shared `SSL_CTX` objects (five runs, all passed). Python itself was not built against the libraries, and OpenSSL's own tests were not run.

## Unreleased (RISC OS 64, for the next tool chain release)

- **The RISC OS 64 compiler on 32-bit RISC OS** (new pre-release `riscos64-cross32-0.1`, 25 October 2026): `aarch64-riscos-gcc`, `g++`, the GNU tools, `cmunge64`, `mkoslib` and `modreloc64` as programs for 32-bit RISC OS 5, so that programs and modules for RISC OS 64 can be built on a 32-bit machine. The output is the same, byte for byte, as the Linux cross compiler's (tested on a 32-bit machine, and the programs on RISC OS 64); see [docs/CROSS-FROM-32BIT.md](docs/CROSS-FROM-32BIT.md). The module tools are now also C programs (`riscos64/tools/modreloc64.c`, `riscos64/hosted32/src/cmunge64.c`, `mkoslib64.c`).
- `poll` and `select` know about sockets numbered up to 63 (they stopped at 31, and a socket above that was reported ready at once: a non-blocking `connect` followed by `poll` and `send` failed with `ENOTCONN`; curl with several connections to one host hit it). A socket whose non-blocking `connect` has not finished is no longer reported writable.
- `build-sdk.sh` accepts `TC=<installed tool chain>` to compile the POSIX support files with that tool chain's headers (the raw picolibc headers lack `struct passwd` fields that the files use).

## v16.2.0-24: 2026-10-14, UnixLib with the thread ticker of Andrew Youll's riscos-unixlib: a threaded program no longer makes other tasks abort

| Asset | Version |
|---|---|
| native compiler `Gcc16` | 16.2.0-24 |
| runtime `SharedLibs-C-armeabihf` | 16.2.0-15 (new: UnixLib fix level 17) |
| runtime `SharedLibs-C++-armeabihf` | 16.2.0-6 (unchanged) |
| runtime `SharedLibs-Fortran-armeabihf` | 16.2.0-2 (unchanged) |
| self-test `Gcc16SelfTest` | 16.2.0-24 |
| Linux cross compiler | 16.2.0-24 |
| optional `SharedULibFix` (the fixed SharedUnixLibrary) | 1.16-vforkfix3 (unchanged) |

* **The thread ticker is fixed** (UnixLib fix level 17, runtime 16.2.0-15, and the `libunixlib.a` of the Linux tarball). A user reported that a picture viewer built with this tool chain made every other task abort, one after another, as soon as the mouse moved over its window, and then locked the machine; the same program built with Andrew Youll's UnixLib was fine. Cause: a program with more than one thread gets a system-wide timer (`OS_CallEvery`) that switches threads, and its routines ran from the program's own memory; when the timer fired while another task was paged in, it ran whatever that task had at that address. A program **linked statically** with a thread made **before `Wimp_Initialise`** (as SDL programs do) also has no Wimp filters to stop the timer. Reproduced on the Raspberry Pi with the new test [`tests/tickbug`](tests/tickbug): the static program made `MiniTime` abort at once and then an endless `abort on data transfer` on the screen; the same program dynamically linked (the code is in the shared library area) and the control (thread made after `Wimp_Initialise`) were fine. With the fix, the static program ran 120 seconds and the timer fired 6025 times into other tasks without a single abort, with or without the optional module.
* **The fix is Andrew Youll's.** The thread ticker patch (`patches-unixlib/unixlib-thread-ticker.patch`: `pthread/ticker.c`, `internal/ticker.s`, `module/pthticker.s` and the changes to `_context.s`, `pthinit.c` and others) is taken from his [riscos-unixlib](https://github.com/adyoull/riscos-unixlib) (UnixLib 5.0.3.3) with his comments and copyright notices: the routines run from a copy in the RMA block, or from his small `PThreadTicker` module when it is loaded (optional: `build-pthticker.sh` builds it), and the Wimp filters follow the task. Thank you. It is adapted to this tree (the generated `Makefile.in`; `__pthread_prog_fini` keeps the earlier fix for the RMA block that a `vfork` child shares with its parent). `sysconf (0x4700)` answers 17.
* **Programs linked statically with an older `libunixlib.a` have the old ticker:** link them again with this tool chain. Dynamically linked programs get the fix from the runtime package 16.2.0-15.
* A web browser, Iris, that quit without an error when its icon bar icon was clicked, with the runtime 16.2.0-14, works with the runtime 16.2.0-15 (reported by the user who tested it; it is a threaded program, so the thread ticker is the probable cause, but that is not confirmed).
* `tools/check-libunixlib.sh` looks for the ticker in a built library, and `tools/sim-exit-hooks.py` (the model of the exit code on an ARM interpreter, with its mutants) has the new owner and detach logic of `__pthread_prog_fini` (37 scenarios, 82 mutants).
* Not changed: GCC, binutils, the module kit, the C++ and Fortran runtimes and `SharedULibFix`; `Gcc16` 16.2.0-24 needs `SharedLibs-C-armeabihf` 16.2.0-13 or later, as before (install 16.2.0-15 for the fix).
* Checked on the Raspberry Pi with the packages of this release, installed with PackMan: the self-test (12 of 12 checks, 33 seconds, UnixLib fix level 17); the regression run (the same 54 `SUMMARY` lines as in the earlier releases, none failing; the six `vfork` heap stages ran in the same run, as `RunNew29` now asks for fix level 17, and left every parent intact); the thread ticker test [`tests/tickbug`](tests/tickbug) with the libraries of this release: the program linked statically with a thread made before `Wimp_Initialise` (which made `MiniTime` abort with 16.2.0-23), the same linked dynamically, the control (thread made after `Wimp_Initialise`, with the Wimp filters registered) and the static one with the `PThreadTicker` module loaded each ran 120 seconds while the timer fired 6025 times, and no task aborted; and the network module and the test program RomCmp built on the Pi, each byte for byte the cross build (39 network checks; 545 RomCmp checks, 0 failed, 9,820 of 9,820 result lines the same as the ROM's).

New since 16.2.0-22: the module kit (`modkit`) and the documents about modules. The native `Gcc16` and the Linux cross compiler carry the kit; the compiler itself (code generation, binutils) and the runtimes are not changed except for one linker option of `-mmodule`.

* **Modules are smaller: the linker drops the functions that nothing calls** (`-ffunction-sections -fdata-sections` for the library and `--gc-sections` in the link of `-mmodule`). SysLogD went from 61,868 to 38,780 bytes, SOManager from 47,084 to 40,516, ARMEABISupport from 40,816 to 36,100, a `sprintf` and `memcpy` module from 9,520 to 8,372, Sunfish from 298,516 to 224,264 (`-O0`; 189,784 to 144,808 with `-O1`). * **Sockets are file descriptors** (about 590 functions in the kit): `socket` and `accept` return descriptors of the table that `open` uses, and `close`, `read`, `write`, `readv`, `writev`, `ioctl`, `fcntl`, `dup`, `fstat` and `select` work on them, as in UnixLib and in Acorn's TCPIPLibs, so a source written for either builds as it is (`socketclose`, `socketread` ... still work). `__modlib_socket_fd` turns a socket made with the raw `Socket_` SWIs into a descriptor and `__modlib_socket_handle` gives the Internet module's number back (code that compares the socket of an `Event_Internet` event with the result of `socket ()` must use it: GCCSDK's SysLogD needs that one line); `fdopen` of a socket is `ENOTSUP`. The sockets that are still open when a program ends (`exit`, a return from `main`, `__modlib_closeall`) are closed. New headers `<net/if.h>`, `<sys/errno.h>` and `<sys/param.h>`, `fcntl` in `<fcntl.h>`, and `<sys/ioctl.h>` has the request numbers of the RISC OS Internet module (the "get" requests are 95 to 99, not 4.4BSD's: `SIOCGIFADDR` was wrong from 16.2.0-19 to -22).
* **C99 maths and `<fenv.h>`**: `erf`, `erfc`, `lgamma`, `lgamma_r`, `signgam`, `tgamma`, `fma`, `remquo`, `scalbln`, `nexttoward` and `nanf` with their `long double` forms (= `double`), and a software `<fenv.h>` (the flags are kept in software and the rounding is always to nearest). `fma` and `remquo` give the result of glibc bit for bit; `erf`, `erfc` and `lgamma` are Sun's fdlibm; `tgamma` is within a few units in the last place. The two new sections of the library test (`c99`, 142,966 results, and `gamma`, 2,004) are the same as glibc's on the host, on the interpreter and on the Pi. `<cmath>` has the overloads.
* **The last names of GCCSDK 4.7.4's module library**: `sethostname`, `setdomainname`, `settimeofday` and `clock_settime` (each fails with `EPERM`, as in UnixLib: a module does not set the clock or the name of the machine), `strcasecmp_l`, `strncasecmp_l` and `strerror_l` (with `locale_t` and `LC_GLOBAL_LOCALE`; the locale is ignored), and `imaxabs`, `imaxdiv`, `strtoimax` and `strtoumax` as functions and not only inline functions of the header. `tools/compare-4.7.4-names.sh` counts them: of the 439 public names that the default module library of GCCSDK 4.7.4 defines (`scl-module/hard/fpa`), the kit defines 423; the other 16 are 13 names that belong to the Shared C Library itself (`TrapHandler`, `EventHandler`, `disable_stack_extension`, the `x$` run-time entries ...) and three `signbit` functions (a macro here).

* **Sunfish builds and runs.** [Sunfish](https://github.com/ajw498/NFS), Alex Waugh's NFS client filing system (about 40 C compilations of its source and four assembler files, a module of 224 KB), builds from its **unmodified source** with `tests/sunfish/build-sunfish.sh` (no TCPIPLibs, no libiconv), loads on the Pi without a lock-up, mounts an NFS export, lists it and reads 64 KB of a file of 733 MB with the right CRC (compared with an independent NFS client on the host; write, TCP, NFS2/4 are not tested). A build with GCCSDK 4.7.4 had been reported to lock the machine up.
* **The documents about modules were checked against the code, the tests and the results from the Pi, and corrected** (about 60 findings in [MODULES.md](docs/MODULES.md), the OS modules page, the porting guide, the README and the install and build documents). [PORTING-FROM-4.7.4.md](docs/PORTING-FROM-4.7.4.md) now says who should move to this tool chain and who should not (an old CPU, hardware floating point, C++ exceptions and RTTI in a module, the smallest possible size, applications for the Shared C Library), what GCC 16 refuses in old code (and the options that let it through), and what behaves differently (`errno` numbers, `BUFSIZ`, `FOPEN_MAX`).
* Not changed: GCC's code generation, binutils, UnixLib, the C, C++ and Fortran runtimes and `SharedULibFix` (the build instructions were run again from an empty home directory, in 19 minutes, and the four runtime packages came out identical to those of 16.2.0-22: member for member the same); `Gcc16` 16.2.0-23 needs `SharedLibs-C-armeabihf` 16.2.0-13 or later, as before.

* **Changes in behaviour that can affect a CMHG file or a module built with 16.2.0-14**: a CMHG file that says `module-is-runnable:` now gets a real start entry (16.2.0-14 ignored the line with a warning, so the module's start word was 0; a module with no `main` ends with 0 when it is run, `*RMRun` and `*Run` call it); a command without `max-args:` takes no arguments (CMunge's default; it was 255); `min-args:`, `max-args:` and `gstrans-map:` above 255 are refused (they were cut to 255); a SWI chunk must be a non-zero multiple of 64 without bit 17, a `swi-handler-code:` needs a `swi-chunk-base-number:` and the other way round, and a chunk without a `swi-decoding-table:` takes the title as its prefix (CMunge does the same); the handler of a `generic-veneers:` entry returns a `_kernel_oserror *` and does not claim a vector (0: the registers the handler left in the block and the flags come back as they were; else V set, r0 = the error); `finalisation-code:` is optional; the help line, `Module_Help`, `Module_VersionString` and `Module_VersionNumber` are made from the `help-string:` as CMunge makes them, and a help string that CMunge refuses is refused; `time_t` is a 32 bit `long` (as in the Shared C Library); `module.mk` builds the kit's library from the kit's own sources.
* **`libmodkit` fixes found by the new tests**: `malloc` of more than 2 GB wrapped round to a small block (it is `ENOMEM` now); `exit` in a module that had run as a program ended the desktop when a command of that module called it later (it is an error again); an `atexit` function of an aborted program ran in the next run.
* **A figure in the repository's documents after 16.2.0-14 was wrong**: it said that 26 of the 66 C modules of the RISC OS Open sources use nothing that the 30 functions lack. That did not count the RISC OS library calls (`_swix` and the `_kernel_*` functions; 51 of the 66 call `_swix`); the right figure was 4. With the new library it was 51; with the `stdio` files it is 66, and the 58 that `cmunge` accepts pass both the library and the CMHG test (`tools/scan-os-modules.py`).
* **Tests** (`modkit/tests`): `libtest` (the library against glibc), `sim-veneers.py` (generic veneers in SVC, IRQ and USER mode), `sim-runnable.py`, `sim-mk32.py` (international help, `add-syntax`, SWI tables, a module run as a program), `os-cmhg-corpus.py` and `cmhgdiff.py` (the CMHG files of the OS against the real CMunge), and a larger `test-ctools.py` (2956 checks, with the files that the real CMunge also accepts). The interpreter (`tools/a32.py`) ignores a write to the mode bits of the CPSR in USER mode and reports the real mode in `mrs`, as the processor does. **Run on the Pi (2026-10-07)**: the library test (the 8 compared sections equal to glibc's, the heap, `setjmp`, `getenv`, the real SWIs: `TOTAL fail=0`) and `module-is-runnable` (`*RMRun` with arguments, the exit codes). A second run the same day passed international help (with the NULs), `add-syntax:`, the module's own SWIs with a prefix that differs from the title, the generic veneer in SVC mode, USER mode and in interrupt time (`OS_CallEvery`), `exit` in a command, and 15 checks of a self test in SVC and in USER mode. **Not run on hardware**: floating point in modules (C++ in modules does not work yet). New since 16.2.0-13:

* **`-mmodule`**: the option that GCCSDK 4.7.4 used for relocatable modules works: ARMv6, soft float, ARM state, freestanding, no PIC, the headers of modkit instead of UnixLib's, `__TARGET_MODULE__` defined; the linker gets the module linker script and `libmodkit.a`, and no start files. **`gcc -mmodule -o Module,ffa main.o header.o` writes the module**: after the linker the driver runs `modreloc`, which replaces the ELF file by the flat image (an output named `*.elf`, or a partial link with `-r`, stays what it is).

* **Modules can be built on RISC OS**: the three module tools (`cmunge`, `mkoslib`, `modreloc`) are C programs now (no Python; `modkit/src`, the same source for Linux and RISC OS), and the native `Gcc16` has them with `libmodkit.a`, the linker script and the headers: `gcc -mmodule` works on the Pi as on Linux. The C tools make the same files as the Python versions they replace, byte for byte (`modkit/tests/test-ctools.py`: 2812 comparisons).
* **`mkoslib --from-objects`** writes the SWI veneers of the OSLib functions that your objects use: the replacement for `-lOSLib32` (GCCSDK's archive is for the old ABI). `module.mk` has it all as make rules, needs no list of functions and no RISC OS sources (set `RISCOS_SOURCES` to have the one SWI number of the header read from them).

See [docs/MODULES.md](docs/MODULES.md) (with the changes a GCCSDK 4.7.4 module Makefile needs) and [docs/CROSS-COMPILER.md](docs/CROSS-COMPILER.md#risc-os-modules--mmodule-cmunge).
* **`SharedULibFix`** (new, optional): the fixed **SharedUnixLibrary** module 1.16-vforkfix3, which the author's machine has run since 4 Oct 2026, as a PackMan package with an installer. A `vfork` child that ends without `exec` no longer kills its parent, resizes its Wimp slot or (under a parent that was started by `exec`) freezes the machine. **It replaces a system module**, so the package changes nothing until you run its `Install`: that replaces the module only if it is exactly the stock 1.16 (the whole file is compared), refuses a runtime older than fix level 10, backs the stock module up twice, checks every copy and puts the stock module back if a check fails; `Restore` goes back and `Check` tests the result after the reboot. [docs/SHAREDULIB-FIX.md](docs/SHAREDULIB-FIX.md).

New since 16.2.0-12:
