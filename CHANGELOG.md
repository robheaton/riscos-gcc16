New since 16.2.0-18: the module kit (`modkit`, which `gcc -mmodule`, `cmunge` and `mkoslib` use), its tests and the programs in `tools/`. The native `Gcc16` and the Linux cross compiler carry the new kit.

* **`cmunge -zbase` and `-apcs 3/32`** (C and Python versions): `-zbase` makes `Image__RO_Base` (a constant that holds `Image$$RO$$Base`) and declares it in the header, as GCCSDK's CMunge does; the example modules of 4.7.4 use it. `-apcs 3/32` and `-apcs 32` are accepted (they changed nothing here).
* **`-lOSLib32` links unchanged.** `mkoslib` also makes the **non-X functions** of OSLib (`os_cli`, `os_read_var_val` ...: the result is the register that the `Returns:` line of OSLib's comment names, and an error is raised with `OS_GenerateError` through the new `__modlib_raise`), and `mkoslib --library DIR` writes a C file for every function it can make. `modkit/bin/mkoslib-lib.sh`, which `install-modkit.sh` runs when `OSLIB` is set, builds `libOSLib32.a` from them (4,268 veneers; 367 Toolbox calls that are messages and 34 functions that do not compile with OSLib's types are left out), puts the headers in the tool chain (`include/oslib`) and links them for `-mmodule`. The archive carries weak copies of the SWI helpers, so an ordinary program can link it too. **Not shipped:** OSLib is GPL version 1 or later with an exception for linking, so the released tool chains contain neither OSLib's headers nor `libOSLib32.a`; the generator is shipped, and anyone who has OSLib makes the library with `OSLIB=<folder with oslib/> modkit/bin/mkoslib-lib.sh <tool chain>` (or `install-modkit.sh` with `OSLIB` set).
* **BSD sockets for modules** (`<sys/socket.h>`, `<netinet/in.h>`, `<arpa/inet.h>`, `<netdb.h>`, `<sys/select.h>`, `<sys/ioctl.h>`, `<syslog.h>` constants; `lib/sockets.c`, `lib/netdb.c`): the calls on the Internet module's SWIs, the Shared C Library's names (`socketclose`, `socketread` ...), `gethostbyname` through the Resolver. GCCSDK's SysLogD builds unchanged. Tested on the interpreter with a model of the Internet module (`modkit/tests/sim-sockets.py`); run on the Pi (`pack/module45`: 53 checks, 0 failed). A failing non-X OSLib call ends the whole command line (the kernel's error handler), as with any non-X SWI.
* **`__modlib_stack_left ()`** tells a module how much of the kernel's 32 KB SVC stack is left. A private stack was tried and abandoned: the Task window aborts when `r13` is not on the SVC stack (documented in `MODULES.md`).
* `swisnums.h` has the SWI names `DDEUtils_ThrowbackSend` and the 17 SWIs of the SysLog module that the Shared C Library's `swis.h` has and the RISC OS sources do not (969 SWIs).
* The four official examples of 4.7.4 (`Examples/Module/Simple`, `NoSCL`, `ResourceFS`, `FS`) build with their own Makefiles (`modkit/tests/test-gccsdk-examples.py`).
* Tests: `test-ctools.py` compares the non-X functions, `--library` and `-zbase` (1,209 checks in the quick run); new `sim-oslib.py`, `sim-sockets.py` and `test-gccsdk-examples.py`; the model of the kernel has `OS_GenerateError`, more `Socket_*` SWIs and `Resolver_GetHostByName`.
* Not changed: the compiler, binutils, UnixLib, the C, C++ and Fortran runtimes and `SharedULibFix`; `Gcc16` 16.2.0-19 needs `SharedLibs-C-armeabihf` 16.2.0-13 or later, as 16.2.0-14 to -18 did.
* Checked on the Raspberry Pi with the packages of this release, installed with PackMan: the self-test (twelve of twelve checks in 32 seconds; its module check builds, loads and runs a small module with the kit, natively), the regression run of eight suites (the self-test and seven more: 54 summary lines, the same as in the runs of 16.2.0-18, 16.2.0-17, 16.2.0-16 and 16.2.0-13, none failing), the network module built on the Pi by the commands of its GCCSDK 4.7.4 makefile (4 seconds; byte for byte the module that the Linux tarball makes, 23,024 bytes; loaded and run through 39 network checks, a 500 KB transfer and a soak of 300 commands among them), and `RomCmp`, the 1,400 lines of C of the ROM-comparison program, built on the Pi (7 seconds; byte for byte its cross build, 72,328 bytes), loaded, run against the ROM's modules (545 checks, 0 failed) and its 9,820 lines of results compared with those of 8 October: none different. The build instructions ([docs/BUILDING.md](docs/BUILDING.md)) were run again in an empty home directory, and the packages and the tarball are the output of that run.

* **`mkoslib` put only the `R0` constant of an OSLib comment into a veneer.** The comment above an OSLib function says `Calls SWI 0x40240 with R1 |= 0x3` or `with R1 = 0x0, R2 = 0x80000000`; every constant but the one for `R0` was left out. For 617 of the 2,125 functions that can be made the veneer changes: `xwimp_initialise` had no `R1 = 0x4B534154` ("TASK"), `xosfile_load` no `R3 = 1`, the `xservice_*` functions no service number in `R1`, the `xpalettev_*` and `xkeyv_*` functions no vector number in `R9`. **A module of 16.2.0-14 to -17 that calls one of those functions gets a wrong veneer.** The functions that the examples and the hardware tests call (`xos_cli`, `xosfile_delete`, `xosfile_read_no_path`, `xosfind_*`, `xosgbpb_*`, `xos_claim`, `xsocket_*` ...) are not among them. Now every `R<n> = / |= / += value` is put in, and a comment that `mkoslib` does not understand is an error. A test checks 300 of the veneers against their comments.
* **`mkoslib` made a veneer that did not compile** when a parameter of the OSLib function was called `r`, `e` or `flags` (the locals of the veneer are `_r`, `_e`, `_flags` and `_blk` now). A test compiles one in five of the 2,150 veneers that can be made; 18 do not compile whatever the locals are called (an output of an aggregate type, a pointer type that does not fit, a header that declares a function twice) and are listed in the test.
* **`modreloc` relocated words that are not addresses.** The word of a weak reference that is not defined (its value is 0: `if (weak_fn) weak_fn ();`) was moved by the load address, so the test became true and the module called the first bytes of its own header; a word that holds an absolute symbol was moved too. A test builds a module with both. Both tools (`modreloc.py` and the C `modreloc`) agree.
* **CMHG: the options that were still refused** (`cmunge`, C and Python versions): `swi-decoding-code:` (one function, or `NAME/NUMBER`: two), a function of its own for a SWI (`swi-decoding-table: Prefix One/fn Two`), the options of the veneers (`generic-veneers: g/h (private-word: r4, carry-capable:)`, `vector-handlers: v/h (error-capable:)`), in the command table `handler: fn`, `no-handler:` and `-` (a table without a handler of its own), `module-is-not-reentrant:`. `module-is-runnable:` and `module-is-c-plus-plus:` refuse a value now instead of ignoring it. The header defines `VENEER_SETCARRY` and `VECTOR_ERROR`. Where `swi-decoding-code:` has no `swi-decoding-table:` the header has no table, so that the kernel asks the code in both directions (the real CMunge writes one). The real CMunge makes the same module header from the same files (checked on 138 generated files); `tests/sim-cmhg2.py` runs the veneers on the interpreter in SVC and IRQ mode with four flag states. Still refused: `library-enter-code`, `library-initialisation-code`, `help:`, `swi-handler-code: f (flags-capable:)` and four extensions that only CMunge has. Run on the Raspberry Pi on 2026-10-10 (65 checks and the decoding code through the real kernel): [docs/MODULES.md](docs/MODULES.md).
* **38 of the 66 C modules of the RISC OS Open sources build and link** (29 before): DOSFS, PCCardFS, SDFS, SCSISwitch, SCSISoftUSB, EtherGENET, BootCmds, Picker and the Toolbox's Window; 44 compile completely ([docs/OS-MODULES.md](docs/OS-MODULES.md#new-in-1620-18)). `mkoslib` reads OSLib's own register tables (`Hdr/Wimp`, `Wimp.Hdr`) for the parameters whose register the comment of the header does not give, and makes the functions whose parameters are the components of a block of words (25 more functions); the library has `__current_sp`, `_sprintf` and `<uchar.h>` and the linker script defines `_Lib$Reloc$Off$DP`; `tools/build-os-modules.py` makes `FileCoreErr`, the USB device list and `Interface/USBDriver.h`, builds the Toolbox libraries, knows `VPATH` and RISC OS dotted includes, and works around two limits of `asasm` in the copies it makes.

The interpreter (`tools/a32.py`) reads the CPU identification registers (`MRC p15`).
* Not changed: the compiler, binutils, UnixLib, the C, C++ and Fortran runtimes and `SharedULibFix`; `Gcc16` 16.2.0-18 needs `SharedLibs-C-armeabihf` 16.2.0-13 or later, as 16.2.0-14 to -17 did.

| Asset | Version |
|---|---|
| native compiler `Gcc16` | 16.2.0-17 |
| runtime `SharedLibs-C-armeabihf` | 16.2.0-13 (unchanged) |
| runtime `SharedLibs-C++-armeabihf` | 16.2.0-5 (unchanged) |
| runtime `SharedLibs-Fortran-armeabihf` | 16.2.0-2 (unchanged) |
| self-test `Gcc16SelfTest` | 16.2.0-17 |
| Linux cross compiler | 16.2.0-17 |

New since 16.2.0-16: the module kit (`modkit`, which `gcc -mmodule` and `cmunge` use), its tests and the scripts that install it. The native `Gcc16` and the Linux cross compiler carry the new kit; the compiler (GCC 16.2.0), binutils 2.45.1, UnixLib and the three runtime packages are not changed. **Read the first item: 16.2.0-14, -15 and -16 could link code that needs the VFP into a module.**

* **A fault in 16.2.0-14, -15 and -16** (found while preparing the floating point work, reproduced with the released tool chain): `libmodkit.a` named the whole `libgcc.a` of the tool chain, which is built for ARMv7 with the VFP, and the linker linked its members that GCC compiles from C without a word. A module that converted a `double` or `float` to a `long long` or `unsigned long long`, or used `__builtin_popcount`, `__builtin_parity`, `__builtin_ffs`, `__builtin_ctzll` or `__builtin_powi`, contained VFP and `movw` / `movt` / `rbit` instructions: an undefined instruction on an ARMv6 CPU (the Pi 1), and on a Pi 4 the module used the VFP registers of the program that called it, which RISC OS does not save for SVC code. The statement of those releases that no instruction of the VFP is used in a module was wrong for these routines. A module is only affected if it does one of those things (or complex multiplication or division, `_BitInt` wider than 64 bits or half precision) ([KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md) says how to look). **Fixed:** `install-modkit.sh` makes `libgcc-mod.a` (`modkit/bin/mklibgcc.sh`: `libgcc.a` without the members that have a VFP, NEON, `movw`, `movt`, `rbit`, `ubfx` ... instruction, the Thumb helpers and the fixed-point members: 125 of 1,762 members, 89 KB) and `libmodkit.a` names it instead of `libgcc.a`, so a routine that is not there is an undefined reference at the link; `lib/gccrt.c` has what C code reaches (the conversions of `double` and `float` to 64-bit integers, which saturate and give 0 for a NaN as the VFP does, the bit counts, `__powidf2`), in integer code. `cross-smoke.sh` links a module that does all of this and checks that no member comes from `libgcc.a`.
* **Floating point in `printf`, `scanf` and `strtod`**, exact and as glibc's (the digits of the binary value, rounded to the nearest, ties to even), integer code only: `%f %F %e %E %g %G %a %A` with the flags, width, precision and `L`; `strtod`, `strtof`, `strtold`, `atof`; the same conversions in `sscanf`, `fscanf` and `scanf` (glibc's rules for what is collected, for `0x`, for a dangling exponent and for `infin`). Decimal numbers of any length, hexadecimal numbers, `inf`, `nan`. 5.1 KB more for a program with `printf`, 5.4 KB for one with `sscanf`; a module can leave the code out (see [MODULES.md](docs/MODULES.md#floating-point)).
* **`<math.h>`, 98 functions** in `double` and `float`: the exact ones (`sqrt`, `floor`, `ceil`, `trunc`, `round`, `rint`, `fmod`, `remainder`, `frexp`, `ldexp`, `scalbn`, `modf`, `fmin`, `fmax`, `nextafter`, `logb`, `ilogb` ...) give glibc's results and `errno`; `exp`, `log`, `log10`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `hypot`, `cbrt`, `expm1`, `log1p` are Sun's fdlibm 5.3 (GNU Classpath's copy, with Sun's notice) within 1 to 2.2 units in the last place, measured against `long double`; `exp2`, `log2`, `asinh`, `acosh`, `atanh` are derived. Three changes to fdlibm's sources: its square root shifted by 32 in a case that C leaves undefined, `cosh` and `sinh` took the low word of a number through a pointer cast, and the sources are compiled with `-fwrapv`.
* **Tests** (`modkit/tests/libtest`): the sections `fparith`, `fpconv`, `gccrt`, `fpprintf`, `strtod`, `fpscanf`, `fpmathx` and `fpmath` (about 318,000 results); `LT_ONLY` runs chosen sections, `LT_VERBOSE` prints every case on the interpreter, `run-arm.py` takes `BUILD=` to keep a long run apart from the host runs; `modkit/tests/sim-fpsvc.py` runs the module `FpSvc` (`tests/hwpack/fpsvc.*`: about 1,700 known answers worked out by glibc and Python, `math.h`, the largest conversions, arithmetic in a generic veneer called in IRQ mode) on the interpreter. Deliberately broken versions of the rounding, of the 800-digit rule and of the remainder bit are caught. Run on the Raspberry Pi on 2026-10-09 and 2026-10-10 (the packs `module40` and `module41`): `FpSvc` (892 + 791 + 10 checks, and the same bits as the host in 100 interrupt-time calls), `CxxMod` and `CxxStd` (C++ modules; 33 lines, 0 differ) and `LibTest` (every compared section equal to glibc's, `TOTAL fail=0`) all passed.
* **C++ in modules.** The CMHG directive `module-is-c-plus-plus:` (`cmunge`, C and Python versions) makes the initialisation veneer run the static constructors before the module's initialisation code and the finalisation veneer run the destructors after its finalisation code (`lib/cxxrt.c`); `operator new` and `delete` on `malloc` and `free`, one object each so that a program can replace them (`cxxnew.c`, `cxxnewa.c`, `cxxdel.c`, `cxxdela.c`); the headers of the kit have `extern "C"` guards (they had none: C++ could not call any function of the library). `module.mk` compiles `.cc`, `.cpp` and `.cxx` (`-fno-exceptions -fno-rtti -fno-threadsafe-statics`, the headers of libstdc++ in an order that works). The kit links `libstdcxx-mod.a`, the members of the `libstdc++.a` of the tool chain that are plain ARMv6 code and not position independent (the same filter as `libgcc-mod.a`; 35 of 199), which is what `std::map`, `std::set` and `std::list` need, and `std::string` and the other `extern template`s are instantiated in the module's own code (`include-cxx/bits/c++config.h`); `lib/cxxhash.c` and `lib/cxxsp.c` have what `<unordered_map>` and `make_shared` need; `include-cxx` has the kit's own `<cmath>` and `<math.h>` for C++ and a single thread `bits/gthr-default.h`; `wchar.h`, `wctype.h`, the POSIX `errno` names, `tmpfile`, `tmpnam`, `difftime`, `clock_gettime` and `timespec_get` were added to the C library so that libstdc++'s headers compile. `modreloc` names the reason when it refuses a module with a `.got` (position independent code reaches its data through a table at `0x8000` that only a program has). No exceptions, RTTI, streams or threads: [MODULES.md](docs/MODULES.md#c-in-modules). Tests: `tests/sim-cxxmod.py`, `tests/cxx/test-cxx.py` (the text on the interpreter equals the host's), `tests/cxx/headers-survey.py` (51 small programs and what each needs).
* **`mklibgcc.sh`** (libgcc-mod.a and libstdcxx-mod.a) stops with an error if `objdump` fails (it used to make an archive with the VFP members still in it and say nothing), checks the finished archive again, accepts a relative output name, drops the `.ARM.attributes` of the kept members, recognises more instructions that a module must not run, and drops the members that use the shared library model (`__GOTT_INDEX__`, `R_ARM_GOT*`): code that passes every instruction check and still cannot run in a module.
* **Corrections to the maths library** found by an independent review and glibc probing: `pow (1, y)` and `pow (-1, +-inf)` are 1 as C99 says (fdlibm gave NaN), `pow (0, y)` with y < 0 sets `ERANGE`, the `ERANGE` of the float functions was lost when `errno` was not 0, `atan2` sets `ERANGE` when it underflows to 0, `asinh` and `atanh` of a subnormal number set it as glibc's do, `nan ("99999999999999999999")` leaves `errno` alone. A new section `fpmathsp` compares the class of the result and `errno` of every function that is not exact with glibc on special values. Corrections to `printf` for precisions near `INT_MAX` (a wrong count and a loop of billions of spaces; now `EOVERFLOW` as glibc) and to `strtod` (a wrong value when `malloc` fails for a very long number, and 64-bit arithmetic in the size computation), `scanf` (`nan(chars)`, and a field width that is more than an int) and `strtod`'s `nan(chars)` keeps its payload as glibc's does.
* **The interpreter** (`tools/a32.py`) models `ldrex`, `strex` (and the byte, halfword and doubleword forms) and `clrex`; `armrun.py` shows the output and the place of the program when it fails.
* `tools/scan-os-modules.py`: the library calls of all 66 C modules of the RISC OS Open sources are covered now (MakePSFont needed `math.h`); the survey of `tools/build-os-modules.py` is unchanged (29 build and link, 40 compile completely).
* Not changed: the compiler, binutils, UnixLib, the C, C++ and Fortran runtimes and `SharedULibFix`; `Gcc16` 16.2.0-17 needs `SharedLibs-C-armeabihf` 16.2.0-13 or later, as 16.2.0-14 to -16 did. C++ modules are built with the cross compiler: the C++ headers of the kit are not in the native package (its `libmodkit.a` names `libstdcxx-mod.a`, which is).
* Checked on the Raspberry Pi with the packages of this release, installed with PackMan: the self-test (twelve of twelve checks in 32 seconds; its module check builds, loads and runs a small module with the kit, natively), the regression run of eight suites (the self-test and seven more: 54 summary lines, the same as in the runs of 16.2.0-16 and 16.2.0-13, none failing), the network module built on the Pi by the commands of its GCCSDK 4.7.4 makefile (5 seconds; byte for byte the module that the Linux tarball makes, 23,012 bytes; loaded and run through 39 network checks, a 500 KB transfer and a soak of 300 commands among them), and `RomCmp`, the 1,400 lines of C of the ROM-comparison program, built on the Pi (8 seconds; byte for byte its cross build), loaded, run against the ROM's modules (545 checks, 0 failed) and its 9,820 lines of results compared with those of 8 October: none different. Floating point, `math.h` and C++ in modules, built with the kit of this release, were run on the Pi on 9 and 10 October (see the first items). ## v16.2.0-16: 2026-10-09, modkit: fixes to the SWI and command veneers, and the kit tried on the C modules of the RISC OS Open sources

| Asset | Version |
|---|---|
| native compiler `Gcc16` | 16.2.0-16 |
| runtime `SharedLibs-C-armeabihf` | 16.2.0-13 (unchanged) |
| runtime `SharedLibs-C++-armeabihf` | 16.2.0-5 (unchanged) |
| runtime `SharedLibs-Fortran-armeabihf` | 16.2.0-2 (unchanged) |
| self-test `Gcc16SelfTest` | 16.2.0-16 |

| optional `SharedULibFix` (the fixed SharedUnixLibrary) | 1.16-vforkfix3 (unchanged) |

New since 16.2.0-15: the module kit (`modkit`, which `gcc -mmodule` and `cmunge` use), its tests, the programs in `tools/` and a licence text. The native `Gcc16` and the Linux cross compiler carry the new kit; the compiler (GCC 16.2.0), binutils 2.45.1, UnixLib and the three runtime packages are not changed. The C modules of the RISC OS Open sources were built with the kit as the OS build builds them ([docs/OS-MODULES.md](docs/OS-MODULES.md)): **29 of the 66 build and link into a module image without a change to their sources, and 40 compile completely**. Three of them (Squash, MimeMap, DrawFile) were run on a Raspberry Pi in place of the ROM's modules and gave the same results as the ROM's: the same program, 545 checks on each side, 9,820 lines of results compared and none different (the size of MimeMap's messages file is reported but not compared: the ROM's file is tokenised), and the same pixel count, bounding box and checksum from DrawFile ([Compared with the ROM](docs/OS-MODULES.md#compared-with-the-rom)). What that found, and what changed:

* **`cmunge`**: numbers after the C preprocessor are constant expressions (the OS's headers write `Service_X` as `(0x60)`); the generated header has what CMunge's has and OS sources use (`<prefix>_00`, the `X` SWI names, `error_BAD_SWI`, `arg_CONFIGURE_SYNTAX`, `arg_STATUS`, `configure_*`); **`event-handler:`** (ENTRY[/HANDLER] [numbers]); a handler name followed by something (`(flags-capable:)`) is an error, not a bad symbol; `library-enter-code` and `library-initialisation-code` are refused with the reason. By the scan of `tools/scan-os-modules.py`, 62 of the 66 modules have nothing in their CMHG file that `cmunge` lacks (58 with 16.2.0-15); `cmunge` itself accepts 56 of the 61 components that have a CMHG file and refuses 5 ([docs/OS-MODULES.md](docs/OS-MODULES.md#what-was-checked)).
* **`cmunge`: a SWI handler that returns `error_BAD_SWI` now gives the error of the system**, `SWI value out of range for module <title>` (number &1E6), the way CMunge's veneer does. In 16.2.0-14 and -15 the veneer set V with R0 = -1 (`error_BAD_SWI` is `(_kernel_oserror *) -1`), so a program that read the error block after a SWI that the module does not have crashed with a data abort at &FFFFFFFF. A module is affected only if its SWI handler returns `(_kernel_oserror *) -1`, which is what `error_BAD_SWI` is (the header that 16.2.0-14 and -15 write does not define that name, so such a module had to write the -1 itself; the OS's own C modules, which return `error_BAD_SWI` from the `default:` of their handler - Squash, MimeMap, PortMan, RTC ... - could not be compiled with those kits); one that returns its own error block was always right. Likewise a command handler that returns `configure_BAD_OPTION` (-1) was taken for success; it gives V set with R0 = 0 now (what `*Configure` takes for a bad option), as CMunge's veneer does. Found by `modkit/tests/sim-romcmp.py`, which runs the program of the ROM comparison pack against the GCC build of Squash and asks it for a SWI that it does not have; `sim-veneers.py` has the checks now, and on the Raspberry Pi the ROM's Squash and MimeMap and the GCC builds give the same error for a SWI that they do not have. **Rebuild such a module with 16.2.0-16** (with an older kit, return your own error block).

* The binutils programs of the native package have the **8 MB stack** that the documentation always said (the 16.2.0-11 build was made before the request was added: they had 1 MB).
* The compilers' internal-error message points at this repository's issue tracker (it still named the GCCSDK site).
* The self-test (`Gcc16SelfTest`) has ten checks: a coverage run with `gcov` and a profile-guided build were added.
* `Gcc16` 16.2.0-12 needs `SharedLibs-C-armeabihf` 16.2.0-12 or later (install the runtime first, then reboot).
* Not changed: `gprof` (`-pg`) still writes no `gmon.out` ([KNOWN-ISSUES.md](docs/KNOWN-ISSUES.md)); throwback from the assembler and the linker; the C++ and Fortran runtimes.
* Checked on the Raspberry Pi: the full regression run (50 summary lines identical to 16.2.0-11, none failing; four new ones pass), the new library tests (destructors, `RLIMIT_STACK`, semaphores, the `.gcda` files) and the self-test (ten of ten checks).
