# How the port was made

The whole port, from the first compile to this release, was done in ten days, 1 to 10 October 2026, by Rob Heaton with an AI assistant (Claude). The assistant read the sources, wrote the patches, tools and test programs, built the packages and analysed the results;
**every run on real hardware was done by Rob**, on a Raspberry Pi Compute Module 4 running RISC OS 5.30.

## The method

A loop that repeated about a hundred times: build on Linux; put a *test pack* (an Obey file and the programs) on a network share; run it in a Task window on the Pi; read the results file back; explain every deviation; fix; repeat.
Nothing was called "working" until it had passed on the machine, and the packages were promoted to the release folder only after a full regression run.

## Timeline

| Day | What happened |
|---|---|
| **1 Oct** | The GCCSDK 10.2.0 EABI recipe was forward-ported to GCC 16.2.0 (the RISC OS target files, libgcc, the arm backend changes), and the first program ran on the Pi. UnixLib was rebuilt with GCC 16. A 34,541-check C regression suite, then C++ with libstdc++ and thread-local storage, ran on hardware. binutils 2.45.1 was ported (four patches, about 1,500 lines, for BFD, gas and ld: RISC OS's PLT, GOT and module relocations and the ELF file type) and ran on hardware. LTO, Cortex-A72 tuning and a benchmark were built. The first thread tests found that `std::async` deadlocks in UnixLib. |
| **2 Oct** | The thread bugs (`pthread_once`, timed waits, `sleep`) were fixed. Fortran (gfortran 16.2) was built from the recipe and passed on hardware. `std::random_device` got real entropy. The GCC 16-built UnixLib was loaded on the machine. A strange symptom appeared: bytes of a `read()` into a fresh stack buffer came back wrong. |
| **3 Oct** | The cause was traced to RISC OS losing a store when the OS itself first touches a lazily mapped stack page, and a 64-byte `vstm` crash on such pages. The fix is to touch each stack page with an ordinary store, so **`-fstack-clash-protection` became the default** for this target. Programs got stacks bigger than 1 MB. The **native compiler** was built and ran on the Pi: `gcc`, `g++`, binutils, GNU `make` and `gfortran` compiled, linked and ran the test suites, and rebuilt `make` itself. A new class of bug appeared: a `vfork` child that ends without `exec` froze the machine, and the freeze hunt began. |
| **4 Oct** | The freeze was traced to its root in SharedUnixLibrary (a flag left set in a `vfork` child) and fixed. A heap bug of `vfork` + `exec` children was reproduced and fixed. **Throwback** was implemented; making it work on hardware exposed that with the DDEUtils module loaded every native compile failed silently, because GCC 16 compiled UnixLib's inline SWI wrappers differently from GCC 10; fixed. Twenty reports for the GCCSDK maintainers were drafted and checked. The first freestanding **modules** built with GCC 16 ran on the machine. |
| **5 Oct** | **Native LTO**: every link failed silently (a redirected output file swallowed the messages), and once the messages were visible the cause was UnixLib's `scanf`, which could not read a 64-bit hexadecimal number. The library was fixed (fix level 13) and the bug written up as the 21st report for the GCCSDK maintainers; the package was rebuilt, and the **full regression run passed**: 50 summary lines identical to the previous release. The Linux cross compiler was packaged and checked, and this repository was assembled. |
| **6 Oct** | The first public release went out and the open items of the progress table were taken one by one. **gcov and profile-guided optimisation**: a program built with `--coverage` ran but never wrote its `.gcda` file. Two causes: libgcov had been built without the C library (`inhibit_libc`), and UnixLib never ran the `.fini_array` of a program (a FIXME in `__main`), so no C destructor and no exit hook ever ran. Both were fixed (fix level 14), together with two more UnixLib problems that the tests turned up (`getrlimit (RLIMIT_STACK)` answered 512 MB for a 1 MB stack; POSIX semaphores polled, leaked and had no `sem_timedwait`), and written up as reports 22 to 24. The tuning of GCC's garbage collector on the Pi was measured and left alone (no setting made a difference). Release 16.2.0-12. **gprof**: the compiler's `-pg` call assumed an APCS frame, UnixLib's profiler was compiled out for EABI programs (and needs a free hardware timer), and `setitimer` is refused in a Task window; the solution was the AAPCS call (`__gnu_mcount_nc`) and a sampler thread that reads the saved program counter of the thread the pthread ticker interrupted: a first run on the Pi gave exact call counts. **Throwback from the assembler and the linker** worked at the first try on the linker and, after a bug in the test (a name starting with `<`, which the code took for `<stdin>`), on the assembler; the same bug was in the compilers. Release 16.2.0-13. **Modules, the way GCCSDK 4.7.4 did them**: `gcc -mmodule` (the driver links the module linker script and `libmodkit.a`, then runs `modreloc` to make the flat image), `cmunge` (CMunge's command line over a CMHG header generator) and `mkoslib --from-objects` (the OSLib SWI veneers that the objects use). The three tools were rewritten in C, with 2,800 comparisons against the Python versions, so that they build for RISC OS too. The real source of an 800-line network module was built by the commands of its old GCCSDK 4.7.4 makefile **on the Pi itself in three seconds**: byte for byte the module that the Linux cross compiler makes, and it passed 39 network checks. The fixed SharedUnixLibrary of 4 Oct became an optional package with an installer that checks everything, and the installer was run on the machine (install, check, restore, install again). Release 16.2.0-14. |
| **7 Oct** | **A C library for modules.** The module kit had 30 C functions; it got about 150 (the string, `ctype`, `stdlib`, `time`, `setjmp` and `stdio` functions, `_swi` / `_swix` and the `_kernel_*` calls), with `stdio` files on `OS_Find`, `OS_GBPB` and `OS_Args`, so that all 66 C modules of the RISC OS Open sources use only functions that the kit has. The library was tested against glibc (about 114,000 compared results) on the host and on an ARM interpreter; a review of the first version of the `stdio` files had 46 findings, all taken. `cmunge` got international help, `add-syntax:`, `configure:`, `status:`, `fs-command:` and a real `module-is-runnable:` start entry (`*RMRun` calls `main`), and it accepts the CMHG files of 58 of those 66 modules (27 before). Run on the Pi: the library test (glibc's results, the `stdio` files on the real file system among them), `module-is-runnable`, international help, `add-syntax:`, a SWI prefix that differs from the title, and the generic veneer in SVC mode, in USER mode and at interrupt time; the run found that the help text of an international Messages file needs a NUL before the line end. The packages of the release passed the self-test and the native build of a network module (byte for byte the cross build) on the Pi. Floating point and C++ in modules were not run on hardware. Release 16.2.0-15. |
| **8 Oct** | **The module kit against code it was not written for.** The 66 C modules of the RISC OS Open sources were built the way the OS build builds them, with the kit in place of the Norcroft tools: 29 build and link without a change to their sources, 40 compile completely, and the table of what stops the other 37 says that for 30 of them it is not the kit. Building them, and running the OS's modules on an interpreter, found what small test modules had not: the kit lacked `event-handler:`, constant expressions in CMHG files, the numbers of the SWIs, a few headers and `mkoslib` cases; `modreloc` left a section out of a module without a word; and `cmunge`'s SWI and command veneers returned `error_BAD_SWI` and `configure_BAD_OPTION` wrongly (a program that read the error block crashed). Running the OS's Squash on an interpreter also found a bug in Squash itself (an empty input to the fast compressor runs away), which was reported to RISC OS Open. Then three of the modules (Squash, MimeMap, DrawFile) were loaded on the Pi in the places of the ROM's and run by one test program: the first run showed 7 differing lines, which were a fault of the script that made the module images (it left the help texts out of DrawFile's resource file); the second showed one, the size of a messages file that the OS build compresses for the ROM; the third: 545 checks on each side, 9,820 lines of results compared, none different, the ROM's modules back afterwards, and DrawFile painting the same pixels. |
| **9 Oct** | **A test that had not run.** Preparing 16.2.0-16, the regression run stopped after its first suite: one of its suites insisted on exactly Gcc16 16.2.0-13. The same had happened in the runs of 16.2.0-14 and 16.2.0-15, and the comparison of the result files had not looked at their dates, so their notes said that a regression run was identical when only the self-test had run. The suite was changed, the old result files were moved away so that a suite that does not run leaves nothing to compare, the comparison now refuses files from another day, and the regression ran: 54 summary lines, the same as with 16.2.0-13. The module kit's native builds on the Pi (the network module and the ROM-comparison program) were byte for byte the cross builds. Release 16.2.0-16. |
| **10 Oct** | **Floating point, `math.h` and C++ in modules.** From 9 October on, first a fault of the released kits: `libmodkit.a` linked the whole `libgcc.a`, whose C-compiled members need the VFP or ARMv7 and were linked into modules without a word; a filtered `libgcc-mod.a` replaced it. Then `printf`, `scanf` and `strtod` for floating point (exact, with big integers of 32-bit limbs and no floating point instruction, compared with glibc on more than 300,000 results on the host, on the interpreter and as modules), `math.h` (98 functions: Sun's fdlibm with its error measured, and glibc's `errno`), and C++ in modules (static constructors and destructors through a CMHG directive, `new` and `delete`, the headers of libstdc++ and a few of its members, `std::string`, `std::map` ...). The toolchain's own `libstdc++` members turned out to reach their data through the shared-library model of UnixLib, which a module does not have; the interpreter showed it by faulting at address `0x8038`, and the filter that picks library members learned to drop them. Two independent reviews found real defects (`pow` special values, corners near `INT_MAX`). On the Pi on 9 and 10 October everything passed except one line that was the run script's mistake. |

## Things that were harder than they looked

* **Finding out what the OS does.** Most of the interesting bugs were not in the compiler but in the interaction between the compiler's code, UnixLib, the shared-library machinery and RISC OS modules; each needed a hypothesis, a small test on the hardware, and often a trace.
* **Silent failures.** The worst ones printed nothing: a compile that did nothing when a text editor was running, an LTO link that swallowed its own error message. The fixes were as much about making failures visible as about the failure itself.
* **Honest measurement.** Several early diagnoses were wrong and were corrected by the next experiment (a "stdio bug" that was really the OS, a redirect theory that explained the silence but not the failure). The reports say what was measured and what was only read.
