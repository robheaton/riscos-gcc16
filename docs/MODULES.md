# modkit: building RISC OS modules with this tool chain (experimental)

> **Experimental, but it builds real modules.** `modkit` builds RISC OS relocatable modules with GCC 16 **without UnixLib or the Shared C Library**, with the commands of GCCSDK 4.7.4: **`gcc -mmodule`** and **`cmunge`**. **This page describes the kit of 16.2.0-23.** Its C library has 589 functions with a public name, [named header by header below](#the-c-library-of-modkit): strings, `ctype`, `stdlib`, `time`, `stdio` (`printf`, `scanf` and files), the POSIX descriptor functions, BSD sockets as file descriptors ([below](#sockets)), `iconv`, wide characters, `_swi` / `_swix` and `_kernel_*`, and floating point ([below](#floating-point)): exact `printf`, `scanf` and `strtod`, 164 `<math.h>` functions including the C99 ones of the Shared C Library, `<complex.h>` and a software `<fenv.h>`. It has the CMHG support and the `module-is-runnable` start code, and **C++** (static constructors and destructors, `new` and `delete`, and `std::string`, `std::vector`, `std::map` and the like: [below](#c-in-modules)). Since 16.2.0-23 the link drops every function that the module does not call ([below](#size-of-a-module-and-garbage-collection-of-sections)); what else is new in 16.2.0-23 is [listed here](#what-1620-23-added).
>
> **If you have a module that GCCSDK 4.7.4 builds, move it to this kit; [PORTING-FROM-4.7.4.md](PORTING-FROM-4.7.4.md) is the checklist.** What was checked: GCCSDK's own modules (the Shared Object Manager, ARMEABISupport and SysLogD) and its four example modules build from their own sources and Makefiles; 38 of the 66 C modules of the RISC OS Open sources build and link unchanged ([OS-MODULES.md](OS-MODULES.md)); an 800-line network module built on the Pi is byte for byte the module that the Linux cross compiler makes, and passes 39 network checks there; Alex Waugh's Sunfish NFS filing system builds from its unmodified source, mounts an NFS export on the Pi and reads a file. What you get is a current compiler (GCC 16.2: C up to C23 and C++ up to C++23, where 4.7.4 is GCC 4.7.4 of 2012), more of the C library than 4.7.4's module library has (`stat`, `dup`, `fcntl`, sockets as descriptors, wide characters, the C99 maths and `<fenv.h>`), and one EABI tool chain for programs, modules and libraries. **The reasons to stay with 4.7.4 are these five** ([the detail](PORTING-FROM-4.7.4.md#why-move-and-who-should-not)): (1) a CPU older than ARMv6 (an ARM3, StrongARM, ARM710 or ARMv5 machine): a module here is ARMv6 code, and `-mmodule` replaces any `-march=` or `-mcpu=` of your Makefile without a warning; (2) hardware floating point in a module: here a module is always soft float, where 4.7.4's `-mmodule` also has VFP and NEON variants; (3) C++ exceptions, RTTI or iostreams inside a module, which 4.7.4 links and this kit does not support; (4) the smallest possible module: the C library is inside each module here, and the modules are bigger (GCCSDK's SysLogD is 38,780 bytes here and 11,108 with 4.7.4, ARMEABISupport 36,100 and 32,096, the Shared Object Manager 40,516 and 29,748); (5) applications for the Shared C Library (`-mlibscl`, AIF files with `elf2aif`): there is no Shared C Library support here, and `-mlibscl` does nothing. 26-bit code is not a reason: 4.7.4 rejects `-mapcs-26` too. The kit has been run on one machine, a Raspberry Pi Compute Module 4 with RISC OS 5.30, and never on an ARMv6 CPU: save your work before you load a module that is new.
>
> The C library, `cmunge`, `module-is-runnable`, international help, the generic veneers and the `stdio` files and streams were run on the test machine (Raspberry Pi Compute Module 4, RISC OS 5.30) on 2026-10-07 with the kit of 16.2.0-15, and the native build of a module with its packages; three modules of the RISC OS Open sources that were built with the kit were compared there with the ROM's on 2026-10-08, with the same results in everything the program compares ([OS-MODULES.md](OS-MODULES.md#compared-with-the-rom)). Floating point was run there on 2026-10-09 ([below](#floating-point)); C++ was run there on 2026-10-10 ([below](#c-in-modules)); sockets as file descriptors, the library test with the C99 sections and the network module with the kit of 16.2.0-23 were run there on 2026-10-13. [What was proven on hardware](#what-was-proven-on-hardware) says which pack ran with which release. Read the limits first.

## The commands (the same as with GCCSDK 4.7.4)

| GCCSDK 4.7.4 | This tool chain (16.2.0-14 and later) |
|---|---|
| `cmunge -tgcc -32bit -p -d header.h -o header.o file.cmhg` | the same command: `cmunge` is in the tool chain's `bin/` (it is modkit's module header generator behind CMunge's command line. Options with nothing to switch here are accepted and do nothing: `-tgcc`, `-32bit`, `-znoscl`, `-throwback`, `-cmhg`, `-px` (is `-p`), `-apcs 3/<flags>` that only choose a calling convention, and `-depend` (a warning, no file is written). Options that would change the module are refused with a message: `-tnorcroft`, `-tlcc`, `-26bit`, `-blank`, `-apcs 26`, `-apcs reent` and `-apcs pic`, and any other `-t`, `-x` or `-z`. `-zbase`, `-zoslib`, `-zerrors`, `-xh` and `-xhdr` work) |
| `gcc -mmodule -O2 -c file.c` | the same: `-mmodule` means ARMv6, soft float, ARM state, freestanding, no PIC, no stack protector, no unwind tables, `-fno-builtin`, no unaligned access, `__STDC_HOSTED__` 0 (4.7.4's `-mmodule` has 1), the link drops what no code calls ([below](#size-of-a-module-and-garbage-collection-of-sections)), and the headers of modkit instead of UnixLib's; `__TARGET_MODULE__` and `__TARGET_SCL__` are defined, `__TARGET_UNIXLIB__` is not |
| `gcc -mmodule -o Module,ffa file.o header.o` (the linker writes the module) | **the same command**: the driver links with the module linker script and `libmodkit.a` (the tool chain has both) and then runs `modreloc`, so the output is the flat module image. An output named `*.elf` stays an ELF file (for a debugger or a simulation) |
| the Shared C Library through its stubs | **no C library of the usual kind**: `libmodkit.a` is a small library of its own (589 functions, [listed below](#the-c-library-of-modkit)): the string, `ctype`, `stdlib`, `time`, `setjmp`, `stdio` (`printf`, `sscanf` and files), `_swi` / `_swix` and `_kernel_*` functions that modules use, floating point (`%f` in `printf` and `scanf`, `strtod`, `<math.h>`, `<complex.h>`, `<fenv.h>`), sockets as descriptors and `iconv` |
| `-lOSLib32` (OSLib's SWI veneers) | **the same: `-LOSLib: -lOSLib32` links unchanged** (new in 16.2.0-19; **since 16.2.0-21 the best way is OSLib's own library, built by `install-oslib.py` from your checkout: [OSLIB.md](OSLIB.md)**; **not shipped**: `libOSLib32.a` is made from OSLib's own headers, which you must have yourself: OSLib is GPL with a linking exception and is not part of this project. Run `OSLIB=<folder with oslib/> modkit/bin/mkoslib-lib.sh <tool chain>`, or `install-modkit.sh` with `OSLIB` set; the comment above each OSLib function says which SWI and which registers). It has 4,267 veneers (4,268 members with the support routines): the X functions (`xos_cli`: the result is the error block) **and the non-X ones** (`os_cli`: the result of the register that OSLib's comment names, and an error goes to `OS_GenerateError`). It does not have the Toolbox calls that are messages, not SWIs (367), and 34 functions that do not compile with OSLib's own types. Without the library, **`arm-riscos-gnueabihf-mkoslib -I <OSLib>/oslib -o oslibv.c --from-objects main.o`** still writes the veneers of exactly the functions that your objects use (X and non-X, since 16.2.0-19; `--from-objects` also takes static libraries). GCCSDK's own `libOSLib32.a` is built for the old ABI and cannot be linked. `-lOSLibH32` and `-lOSLibSupport32` come with `install-oslib.py` (`libOSLibH32.a` is `libOSLib32.a` under the other name); `mkoslib-lib.sh` and `mkoslib` make only `-lOSLib32` and the veneers |

```bash
export PATH=<tool chain>/bin:$PATH
cmunge -tgcc -32bit -p -d header.h -o header.o module.cmhg
arm-riscos-gnueabihf-gcc -mmodule -O2 -Wall -c main.c -o main.o
arm-riscos-gnueabihf-gcc -mmodule -o MyModule,ffa main.o header.o     # the module: the driver runs modreloc after the linker
```

A makefile that has `.cmhg.o` and `.cmhg.h` rules with `cmunge -tgcc -32bit -p` and `LDFLAGS = -mmodule` works as it is, apart from the library (below). `module.mk` (below) has it all as make rules.
How the module is made: the linker writes an ELF file, and `arm-riscos-gnueabihf-modreloc` (a small C program; the driver runs it, `gcc -mmodule` only) replaces it by the flat image with the table of addresses that the module relocates itself with (the reason is under Limits). A partial link (`-r`) is not turned into a module.

## What can be built today, and what cannot

**It works for** C modules of any size that the C library below covers, and for C++ modules within [the subset below](#c-in-modules): SWI handlers and decoding tables, `*commands` with international help, service calls, vector, IRQ, callback and generic handlers, OSLib and `_swix` calls, `malloc` from the RMA, `printf` and `sscanf`, files (`fopen` and the rest of `stdio`, [with its rules](#stdio-files-and-streams)), sockets, filing systems, modules that can also be run as programs. Modules of that kind ran on the Pi (a service-call and SWI module, a `TickerV` and callback module, a network module of 800 lines, Alex Waugh's Sunfish NFS filing system of about 40 C compilations and four assembler files, and the module that the self-test builds, loads and runs).

**How much of the OS that is.** The RISC OS Open sources (the BCM2835 subset) have 86 components that build assembler modules, which no C compiler helps with, and 66 that build C modules. [`tools/scan-os-modules.py`](../tools/scan-os-modules.py) reads the C sources of those 66 (the calls of C library functions, comments and strings left out) and their CMHG files and holds them against what the kit has: **all 66 use only C library functions that the kit has** (51 before the `stdio` file functions: the 15 others used `fopen`, `fclose` and the like; with the 30 functions of 16.2.0-14 the figure was 7, and 4 of the 63 modules that call a library function at all), **62 of the 66 have nothing in their CMHG file that `cmunge` lacks** (the count of the scan: 27 with 16.2.0-14, 58 with 16.2.0-15, 62 with 16.2.0-16 and -17 and 16.2.0-18; the others use `library-enter-code`, `library-initialisation-code` and `help:`; the 4 more of 16.2.0-16 are the ones with `event-handler`; the scan does not see the handler option `(flags-capable:)` of TerritoryManager, so `cmunge` itself accepts 56 of the 61 components that have a CMHG file: [OS-MODULES.md](OS-MODULES.md#what-was-checked)), and **the same 62 pass both**. One of the 66 uses floating point and none uses C++. `modkit/tests/os-cmhg-corpus.py` runs the CMHG files of the 61 components that have one through `cmunge` and through the real CMunge and compares what the module headers say: where both accept a file the headers are the same, but for the build date that CMunge adds to the help line of a file with no `date-string:` (`cmunge` leaves it out; one file of the 61, NetGHdr, has none). A real module also has to compile with its own headers (most of that source is written for the Norcroft C compiler), so these figures say what the library and the header generator would allow, not what builds untouched; and 51 of the 66 call `_swix`, which behaves here as the Shared C Library's does only as far as `libtest` checks it. **What does build untouched was then tried** (for 16.2.0-16, [OS-MODULES.md](OS-MODULES.md)): the 66 were built the way the OS build builds them, with the kit in place of the Norcroft tools: **29 build and link into a module image, 40 compile completely** (with 16.2.0-18: **38 and 44**), and the page says what stops each of the others. Three of the 29 (Squash, MimeMap, DrawFile) were then run on the Raspberry Pi in place of the ROM's modules, with the same results.

**What is not done**, without promises: the 28 OS modules that do not link yet (the reason for each is in [OS-MODULES.md](OS-MODULES.md#what-stops-the-others)); C++ modules with the native `Gcc16` (its package has no C++ headers of the kit); the names of GCCSDK's module library that are still missing ([PORTING-FROM-4.7.4.md](PORTING-FROM-4.7.4.md#what-is-still-missing)); if you have a module of 4.7.4 that you would build with this kit, [PORTING-FROM-4.7.4.md](PORTING-FROM-4.7.4.md) says what to change, and when to stay with 4.7.4.

## What 16.2.0-23 added

The release is kit only: the runtimes (SharedLibs-C 16.2.0-14, C++ 16.2.0-6, Fortran 16.2.0-2, SharedULibFix 1.16-vforkfix3) are as they were. What changed for modules, with the place where it is described:

* **The link drops what no code calls** (`--gc-sections`, on by default with `gcc -mmodule`; `-Wl,--no-gc-sections` opts out, and a program without the module header needs `-Wl,-u,main`): [Size of a module](#size-of-a-module-and-garbage-collection-of-sections). GCCSDK's SysLogD went from 61,868 to 38,780 bytes.
* **Seven names**: `sethostname`, `setdomainname` and `settimeofday` (stubs: `-1` with `EPERM`), `clock_settime` (the same, and `EINVAL` for a clock that does not exist), and `strcasecmp_l`, `strncasecmp_l` and `strerror_l` (`locale_t` is `struct __locale_struct *`, the value to give is `LC_GLOBAL_LOCALE`, and the locale is ignored: the "C" locale is the only one). With them the kit defines **423 of the 439 names without an underscore** that GCCSDK 4.7.4's default module library (`-mmodule`, `hard/fpa`: `libunixlib.a` and `libm.a`) defines. ## The C library of modkit

One object per group of functions, and since 16.2.0-23 one section per function, so a module pays for what it calls: a module with `sprintf` (`%s` and `%d`) and `memcpy` is 8.4 KB, of which 0.5 KB are its header and entries (measured with `cmunge` and `gcc -mmodule`; 9.5 KB with `-Wl,--no-gc-sections`), and 3.4 KB if the module defines `__modlib_fmtdouble` and `__modlib_strtofp` itself, because `printf` otherwise brings the conversion of `double`s ([Floating point](#floating-point)). It is freestanding. Its state is what C itself has (`errno`, the `rand` seed, the `strtok` position, the static buffers of `asctime`, `gmtime`, `strerror`, `getenv` (256 bytes), `localeconv`, `strsignal` and `getprogname`), the table of signal handlers, the lists of exit functions (32 for `atexit` and 32 for `at_quick_exit`, then the answer is -1), the state of `tmpnam` and `tmpfile`, the table of 64 descriptors, the last OS error (256 bytes) and the Internet module's last error, the `netdb` buffers, the open files and the three standard streams. Where C leaves a choice, the answer is glibc's, with these exceptions: `rand` is a plain linear congruential generator (`srand (1)` does not give glibc's sequence), `qsort` is an in-place heap sort and not stable, `strerror (0)` is "No error" (glibc: "Success"), and `%lc` and `%ls` of `printf` are not wide. The tests compare with glibc (below). **Every function is named in the table below**, except the `float` and `long double` forms of the functions of `<math.h>` and `<complex.h>` (`sinf`, `sinl`, `csinf`: the `double` name with an `f` or `l`; the exceptions are said in the rows) and the classification functions of `<ctype.h>` and `<wctype.h>` that the rows name as groups.

### stdio: files and streams

Built on `OS_Find`, `OS_GBPB`, `OS_Args`, `OS_File` and `OS_FSControl` 25 (`rename`), and on `OS_ReadLine` for the keyboard. A `FILE` and its 512 byte buffer are one `malloc` block (and, since 16.2.0-21, `fopen` keeps a copy of the name in another one, freed when the file is closed). How it differs from a C library on Unix, and from the Shared C Library:

* **Names** go to FileSwitch as they are, and it translates them. Seen on the Pi: `<Var>` is expanded (a variable that is not set is empty: `EINVAL`), a name ends at a space, a wild card opens the first match, and the empty name is the current directory (`EISDIR`); from the sources of FileSwitch: `"` and `/` are refused (`EINVAL`) and `Prefix:` uses `Prefix$Path`. `b` and `t` in a mode mean the same; `x` with `w` fails with `EEXIST` when the file is there. A file that `fopen` makes has the type Data (&FFD), where the Shared C Library makes Text (&FFF) unless the mode has `b`; there is no way to set a type.
* **Size**: a file of 2 GB or more is not opened (`EOVERFLOW`) and a write that would pass 2 GB - 1 fails (`EFBIG`): the C types are 32 bit, although FileSwitch has up to 4 GB.
* **Files that are open**: FileCore opens a file that is open for writing for nobody, and neither deletes nor renames it (`EBUSY`): one stream for a file that is written. A file that is read only or locked is not opened for writing (`EACCES`), and a locked one is neither deleted nor renamed (`EACCES`). `rename` does not replace a file that is there (`EEXIST`) and does not cross file systems (`EXDEV`): `remove` the old name first.
* **Errors**: `errno` is set from the OS error (`ENOENT`, `EISDIR`, `EACCES`, `EBADF`, `EBUSY`, `EEXIST`, `ENOTEMPTY`, `EMFILE`, `EROFS`, `ENOSPC`, `EINVAL`, `EFBIG`, `EOVERFLOW`, `EXDEV`; anything else is `EIO`) and the OS error itself stays in `_kernel_last_oserror ()`. FileSwitch writes late: a disc error shows at `fflush` or `fclose` (`EOF`, `ferror`).
* **stdin** reads a line at a time with `OS_ReadLine`: at most 258 characters, and the OS call drops control characters (TAB too); Escape is the end of the input, and the end-of-file flag stays until `clearerr`. **stdout and stderr** are the screen, unbuffered: one `OS_WriteC` per character and `OS_NewLine` (LF CR) for a line feed. `freopen (name, mode, stdout)` sends `printf`, `puts` and `putchar` to the file. `setvbuf` does nothing for the three. `tmpnam` gives a name in the scrap directory (`<Wimp$ScrapDir>.tmpXXXXXXX`, for which there is no object) and `tmpfile` opens one "w+b" and removes it when the stream is closed (16 at once; a module that is killed without closing them leaves the files, like any other); new in 16.2.0-17. Not there: `freopen (NULL, ...)` (it gives `EINVAL`) and the wide input and output functions. `gets` (for C90 and C99 sources; C11 dropped it), `fseeko` and `ftello` are there since 16.2.0-20 and -21.
* **The end**: `exit ()` and a return from `main` of a runnable module flush and close every file, and close every open socket (the OS does not close files at `OS_Exit`, and the Internet module does not close sockets when a program ends); `_Exit` and `abort` close them without writing the buffers. **A module that is killed does not**: call `__modlib_closeall ()` (declared in `<stdio.h>`; it closes the open sockets too, and returns how many files and sockets there were) in its finalisation. A `FILE` that a runnable program does not close is flushed, closed and freed when the program ends with `exit ()` or a return from `main` (`_Exit` and `abort` close it without the flush); only the `malloc` blocks that the program itself does not free stay in the RMA.
* **Details**: `ungetc` takes one character, a seek throws it away, and `ftell` is one less after it; `fscanf` uses up `0x` even when no hex digit follows (glibc does); `printf` has `%n`, and a width or precision above `INT_MAX` is -1 with `EOVERFLOW`; `scanf` has no `%lc`, `%ls` or `%l[` (the scan stops); in `%[`, `a-c` is a range when `a <= c` and `c` is not `]`, ranges do not chain, and a first `]` is itself.

**How it was tested.** Against glibc: random sequences of operations on files (about 21,000 results in each run of the host test: every mode, `fwrite`, `fputc`, `fread`, `fgets`, `ungetc`, `fseek`, `ftell`, `fgetpos`, `fflush`, `fprintf`, `fscanf`, the buffer modes) must give the same hashes on the host build (with the sanitizers), and as ARM code on the interpreter. The file system there is a model of FileSwitch and FileCore on the host's files (`modkit/tests/libtest/hosthooks.c` and `fsmodel.py`: a file that is open for writing is open for nobody, read only and locked files, unsigned lengths, `OS_Args 1` beyond the end, disc errors that can be switched on); the checks of the section `stdio2` give the answers of the rules above, and `sim-mk32.py` leaves a file open at the end of a program, run after run. **A model is not FileSwitch**, so a hardware pack (a folder of files for the Pi: not published) runs the same sequences and the same rules on the machine. **Run on the Pi on 2026-10-07 (NVMe, ADFS/FileCore): the section `stdio` (21,068 results) gives the same hash as glibc**, and so do the eight other compared sections; the checks of `stdio2` about read only and locked files, a file that is open twice, a folder, the end of a program that leaves a file open (run after run), the keyboard and the screen streams passed. Two checks failed, and both were wrong in the test, not in the library: a rename onto a file that is there is "Bad rename" (`EEXIST`) whatever the state of the source, because FileSwitch looks at the destination before FileCore looks at the source (the model had the order the other way round). A second run with those checks corrected gave `TOTAL fail=0`, and its section `probe` printed what FileCore and FileSwitch answer in about 90 cases (rename, remove and open of read only, locked and open files, two streams on one file, the pointer beyond the end, attributes, names): those lines are `modkit/tests/libtest/pi-probe.txt`, and `check-probe.py` (run by `run-host.sh` and `run-arm.py`) holds the model against them. They differ only in the names (the model has the host's), and in the length that the catalogue shows for a file that was just opened for output. On the NVMe the error numbers are FileCore's with the file system number in front (&1C8C3 is "Locked", &C3): `errno` is mapped from the low byte.

`libmodkit.a` that the driver links is a linker script that names `libmodkit-core.a`, `libgcc-mod.a` and `libstdcxx-mod.a` (new in 16.2.0-17; the earlier kits named `libgcc.a`: see [Floating point](#floating-point) for why that was wrong), so the helpers of the compiler (64 bit division, soft floating point) are found without `-lgcc`; the kit's own integer division comes first.

**A module that is also a program** (`module-is-runnable:` in the CMHG file): `cmunge` makes a start entry, so that `*RMRun Module a "b c" d` (or `*Run` of the file) calls `int main (int argc, char **argv)` in user mode with the words of the command line (up to 39 words after the program name, and the command tail is cut at 255 characters; `"` groups); `exit ()` and a return from `main` end the program with `OS_Exit` and the return code; `atexit` functions run. In SVC mode (a command, a SWI or a service call of the same module) `exit ()` is an error ("exit (3) was called in a module"), never the end of the desktop. A module that says `module-is-runnable:` and has no `main` ends with 0 when it is run.

**International help** (`international-help-file:` and the command option `international:`): the `help-text:` and `invalid-syntax:` of such a command are message tokens, looked up by the kernel in the Messages file that the header names (any path, also through a path variable: `"MyMod:Messages"`). **The value of a help or syntax token must end with a NUL byte (`CHR$ 0`) before the line end**, as the OS's own `CmdHelp` files have it (`HDEV:*GPIODevices lists ...<NUL><LF>`): `*Help` prints the value in place with `OS_PrettyPrint`, which stops only at a NUL, and the text of a syntax error is copied up to the NUL. A value with only the line end prints the rest of the file and then whatever follows it in memory (seen on the Pi). The header that `cmunge` makes is the same as CMunge's; the NUL is in the Messages file.

### Floating point

*New in 16.2.0-17.* `float` and `double` are soft float: for every operation the compiler calls a routine of integer code, so a module has no VFP instruction, does not touch the VFP registers of the program that was running when it was called (RISC OS does not save the VFP state for code in SVC mode), and runs on an ARMv6 CPU.

* **`libgcc-mod.a`, and a fault of 16.2.0-14 to -16.** The `libgcc.a` of the tool chain is built for ARMv7 with the VFP, and the members that GCC compiles from C use both: a `double` or `float` converted to a `long long` or `unsigned long long` (`__fixdfdi` and its three relatives), `__builtin_popcount`, `__builtin_parity`, `__builtin_ffs`, `__builtin_ctzll`, `__builtin_powi`, complex multiplication and division, `_BitInt`. Only the members written in assembler (the soft float arithmetic, the integer division) are plain ARM code. 16.2.0-14, -15 and -16 linked the whole `libgcc.a` after the kit's library and the linker said nothing, so a module that did one of those things contained `vmov`, `vcmpe`, `movw`, `movt` or `rbit` (an undefined instruction on an ARMv6 CPU such as the Pi 1; on a Pi 4 the module would have used the VFP registers of the program that called it). The statement of those releases that no instruction of the VFP is used in a module was wrong for these routines. [`bin/mklibgcc.sh`](../modkit/bin/mklibgcc.sh) now makes `libgcc-mod.a` when the kit is installed: a copy of `libgcc.a` without every member whose disassembly has a VFP or NEON instruction, `movw movt rbit ubfx sbfx bfi bfc mls udiv sdiv dmb dsb isb`, or that is a Thumb helper or a Linux system call, and without the fixed-point members (125 of 1,762 members stay, 89 KB). `libmodkit.a` names it instead of `libgcc.a`, so a routine that is not there is an undefined reference at the link. What C code reaches of the dropped members is in [`lib/gccrt.c`](../modkit/lib/gccrt.c), integer code only: the conversions of `double` and `float` to 64-bit integers (they saturate and give 0 for a NaN, as the VFP does), the bit counts, `__powidf2`. `cross-smoke.sh` links such a module and checks that no member comes from `libgcc.a`. What is **not** there is an undefined reference at the link, not a crash: the division and remainder of `_BitInt` wider than 64 bits (`__divmodbitint4`) and its conversions to floating point, and the atomic operations on 8 bytes and the 1- and 2-byte `__sync` and `__atomic` operations (the members that call the Linux kernel). The complex multiplication and division (`__muldc3`, `__divdc3` and the `float` ones) are in [`lib/complexrt.c`](../modkit/lib/complexrt.c) since 16.2.0-22. The members that are kept are stripped of their debug information and of the `.ARM.attributes` section (they say ARMv7 and VFP, which the code that is left in them is not); the script disassembles the finished archive once more and stops with an error if an instruction is left that a module must not run, or if `objdump` fails.
* **`printf`, `snprintf`, `fprintf`: `%f %F %e %E %g %G %a %A`** with the flags `- + space # 0`, a width and a precision (digits or `*`) and the length `L` (a `double`). The digits are those of the binary value, which a decimal number can hold exactly (the expansion of a `double` ends), rounded to the precision with ties to the even digit, so the output is glibc's for every value, `inf`, `nan` and `-nan` included. It is made with big integers of 32-bit limbs and integer code only (no floating point instruction and nothing of `libgcc`; the kit's own integer division for the exponent): about 1,000 bytes of stack for a call of `snprintf` with a conversion of a `double` (210 for a call without one) whatever the precision (`%.1000f` of 1e300, `%.1100e` of 5e-324 and a precision of 100,000 work on the host; the interpreter tests stop at 1,100), a few thousand to ten thousand instructions for an ordinary number.
* **`strtod`, `strtof`, `strtold`, `atof`, and `%f %F %e %E %g %G %a %A` in `sscanf`, `fscanf`, `scanf`.** The result is the nearest number to the exact value of the text, ties to the even one, for a decimal number of any length (the first 800 digits count, and one more for any non-zero digit after them: the halfway point between two `double`s has 768 digits at most), a hexadecimal one (`0x1.8p3`), `inf`, `infinity`, `nan` and `nan(chars)` (the characters in the parentheses are read as an integer, as `strtoull` with base 0 reads one, and become the payload of the NaN, as in glibc: `nan(12)` is `0x7ff800000000000c`). `strtof` and `%f` round once, to a `float`, not twice through a `double`. `ERANGE` is set for infinity and for a result that is zero or subnormal and not exact (glibc's rule: tiny after rounding to the precision of the type). `strtod` takes about 640 bytes of stack, and for a number of more than about 395 digits (or a large exponent) memory from `malloc` as well (the big-number path needs no more: about 600 bytes measured for 780 digits); if `malloc` fails the first 40 digits are used. `sscanf` with a floating point conversion takes about 1,070 bytes of stack (500 with integers and strings only), and memory from `malloc` for a number of more than 62 characters. `scanf` collects the characters the way glibc's does and converts them with the same routine, so as in glibc the text collected must be a number all through (`1e` and `0x1p+` are no number: nothing is stored), `0x` is used up, `infin` is no number but `inf` and `infinity` are, `nan(abc` is none either, and `%1f` or `%5lf` limit the width.
* **`<math.h>`: 164 functions**, in `double`, `float` and `long double` forms (the `float` ones work in `double` and round once; the 48 `long double` ones, since 16.2.0-20, call the `double` ones, because `long double` is `double`), with `finite`. *Exact*, the result and `errno` as glibc gives them: `sqrt`, `floor`, `ceil`, `trunc`, `round`, `rint`, `nearbyint`, `lround`, `llround`, `lrint`, `llrint`, `fmod`, `remainder`, `frexp`, `ldexp`, `scalbn`, `modf`, `copysign`, `fabs`, `fmin`, `fmax`, `fdim`, `nextafter`, `logb`, `ilogb`, `nan`. *Sun's fdlibm 5.3* (GNU Classpath's copy, `lib/fd_*.c`, with Sun's notice, which allows its use if the notice stays; the [CHANGELOG](../CHANGELOG.md) of 16.2.0-17 lists the three changes): `exp`, `log`, `log10`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `hypot`, `cbrt`, `expm1`, `log1p`; `exp2`, `log2`, `asinh`, `acosh` and `atanh` are worked out from those. Measured against the `long double` functions of glibc over 12,000 values of each, the error is within 1 unit in the last place for `exp`, `log`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `hypot`, `cbrt`, `expm1` and `log1p`, within 1.6 for `log10`, `log2`, `atan2`, `cosh`, `asinh`, `acosh` and `atanh`, and within 2.2 for `sinh` and `tanh`; the last bit is therefore not always the one glibc gives. `errno` follows glibc 2.43 (probed): `EDOM` for a domain error (`sqrt (-1)`, `log (-1)`, `acos (2)`, `sin (inf)`, `fmod (1, 0)`, `ilogb (0)`), `ERANGE` for `log (0)`, `atanh (1)`, `log1p (-1)`, an overflow and an underflow to 0; `pow (0, -1)` is a pole (`ERANGE`); a subnormal result sets nothing (except `nextafter`, `atan2` when it underflows to 0, and `asinh` and `atanh` of a subnormal number, as in glibc; glibc sets `ERANGE` for some subnormal results of `expf`, `exp2f` and `powf` by a rule of its own that is not copied). `pow (1, y)` and `pow (-1, +-inf)` are 1 for every `y`, a NaN included, as C99 says. Every function that is not exact is compared with glibc on special values (zeros, infinities, NaN, subnormals, the edges of each domain) for the class of the result and `errno` (the section `fpmathsp`). `fmin` and `fmax` return the second argument for equal zeros, and a NaN for a signaling NaN, as glibc's do. The macros (`isnan`, `isinf`, `isfinite`, `isnormal`, `signbit`, `fpclassify`, `isgreater` ...) are the compiler's.
* **The C99 functions of the Shared C Library (new in 16.2.0-23):** `erf`, `erfc`, `lgamma`, `lgamma_r` (the sign of the gamma function is in `signgam`, or in the argument of `lgamma_r`), `tgamma`, `fma`, `remquo`, `scalbln`, `nexttoward` and `nanf`, and the `long double` forms of the same (`erfl`, `erfcl`, `lgammal`, `tgammal`, `fmal`, `remquol`, `scalblnl`, `nexttowardl`). `fma` and `remquo` are exact (the bits glibc gives); `erf`, `erfc` and `lgamma` are Sun's fdlibm; `tgamma` is the kit's own (a few ulp, more for large arguments: it multiplies up to 170 factors). Against glibc on the points of the test the worst relative errors were 2.2e-16 (`erf`), 3.2e-16 (`erfc`), 4.3e-14 (`lgamma`) and 1.2e-15 (`tgamma`). **Not there:** the `float` forms of these (`erff`, `fmaf`, `lgammaf` ...), `lgammal_r`, the Bessel functions and `gamma` (use `lgamma`). In a C++ module `<cmath>` has the `float` and `long double` overloads of these, which call the `double` function.
* **`<fenv.h>` (new in 16.2.0-23) is software only.** `feclearexcept`, `fegetexceptflag`, `feraiseexcept`, `fesetexceptflag`, `fetestexcept`, `fegetround`, `fesetround`, `fegetenv`, `feholdexcept`, `fesetenv` and `feupdateenv`, with glibc's values for ARM (`FE_INVALID` 1, `FE_DIVBYZERO` 2, `FE_OVERFLOW` 4, `FE_UNDERFLOW` 8, `FE_INEXACT` 16, `FE_TONEAREST` 0 ...). **What it does:** the exception flags are a word in memory; `feraiseexcept` and `fesetexceptflag` set them and `fetestexcept`, `fegetexceptflag` and `fegetenv` read them, and `feholdexcept`, `fesetenv` and `feupdateenv` save and restore them (`feholdexcept` clears the flags and returns 0: the "non-stop" mode is the only mode). **What it does not do:** the soft float routines and `<math.h>` never set a flag (`1.0 / 0.0` leaves `FE_DIVBYZERO` clear, `sqrt (-1)` leaves `FE_INVALID` clear), nothing traps, and the rounding mode is always `FE_TONEAREST`: `fesetround` of another mode returns non-zero and changes nothing, and the arithmetic rounds to nearest whatever the program asked.
* **Stack.** `snprintf` with a floating point conversion uses about 1,000 bytes of stack, `sscanf` with one about 1,070 (500 without), `strtod` 640; of `math.h` every function stays under about 210 bytes (`sinhf` 208, `powf` and `exp2f` 200), except `sin`, `cos` and `tan` of an argument above about 1.6e6 radians, which need about 850 (the argument reduction). The SVC stack of RISC OS is 32 KB, the IRQ stack 8 KB.
* **Size.** A program that uses `printf` takes 5.1 KB more than before for the conversions of `double` (`fpfmt.o` 4.0 KB, `fpbig.o` 1.0 KB); `sscanf` takes about 5.3 KB more (`strtod.o` 4.0 KB, `fpbig.o` 1.0 KB if `printf` has not brought it, and the float part of `scanf.o`; `strtod` also links `libgcc-mod.a`'s 64-bit unsigned division for the payload of `nan(chars)`); a module that makes one call and has a `double` in it is 3.5 KB with `sqrt`, 4.4 KB with `exp`, 4.3 KB with `log`, 8.5 KB with `pow` and 10.2 KB with `sin` (a module with a `double` addition and nothing else is 1.4 KB: the soft float routines come with any `double` arithmetic; without garbage collection of sections the figures are 4.6, 5.9, 9.9, 12.9 and 13.5 KB; the argument reduction is most of what `sin` costs). A module that wants none of it defines `__modlib_fmtdouble` and `__modlib_strtofp` itself (two functions that return 0): the linker then does not take the library's.
* **Not there:** a rounding mode other than to nearest, exception flags that the arithmetic sets, and traps ([`<fenv.h>`](#floating-point) is software state: nothing raises `SIGFPE`, `1.0 / 0.0` is infinity), the Bessel functions, `gamma`, the `float` forms of `erf`, `erfc`, `lgamma`, `tgamma`, `fma`, `remquo`, `scalbln` and `nexttoward`, and `_Float16`. `long double` is `double`. A NaN made by arithmetic is positive (libgcc's), where the PC's is negative.
* **How it was tested.** The sections `fparith`, `fpconv` and `gccrt` of `libtest` run the soft float of `libgcc` and the routines of `gccrt.c` against the hardware `double`s of the host (62,500, 40,000 and 32,500 results: the same), `fpprintf` (9,000 formatted numbers), `strtod` (9,800 texts, each as `double` and `float`; exact halfway points among them, written out in 760 digits) and `fpscanf` (10,500) against glibc, `fpmathx` (135,000 results: the exact functions of `<math.h>` with their `errno`) against glibc, and `fpmath` (the other functions: the host build of the library and the ARM code agree bit for bit, and the error against `long double` is measured); every section equal on the host (with AddressSanitizer and UBSanitizer) at 40 times the size and as ARM code on the interpreter. The sections `c99` (142,966 results: `fma`, `remquo`, `scalbln`, `nexttoward`, `nanf` and their `long double` forms) and `gamma` (2,004 results: `erf`, `erfc`, `lgamma` and `tgamma`) are new in 16.2.0-23 and equal to glibc's; the checks of `<fenv.h>` are the library test's own. Deliberately broken versions (a tie rounded up, the digits after the 800th ignored) are caught. `modkit/tests/sim-fpsvc.py` runs the module `FpSvc` of the hardware pack on the interpreter and the kernel model: about 1,700 answers worked out by glibc and Python (printf, strtod, sscanf, the arithmetic, `math.h`), the largest conversions, and arithmetic in a generic veneer called in IRQ mode. **On the Raspberry Pi** (Compute Module 4, RISC OS 5.30, 2026-10-09, the pack `module40` with the kit of that day): `FpSvc` passed 892 checks (printf, strtod, sscanf, the arithmetic, the conversions), 791 for `math.h` and the 10 largest conversions in SVC mode; 100 calls of floating point arithmetic in a generic veneer that `OS_CallEvery` calls gave the bits that the host gives; and `LibTest` as a module gave the hashes of glibc's run in all the sections that are compared with it (`fparith`, `fpconv`, `gccrt`, `fpprintf`, `strtod`, `fpscanf`, `fpmathx`: 318,084 results with `fpmath`, which is compared with the host build of the library). The one line that failed (`getenv` of a variable that the run script had not set) was the script's fault. The corrections made since were run as `module41` (below).

### C++ in modules

*New in 16.2.0-17. Run on the interpreter and in the kernel model, and on the Raspberry Pi (below).*

* **Where.** C++ modules are built with the cross compiler on Linux; the native `Gcc16` on RISC OS builds C modules (its `libmodkit.a` names `libstdcxx-mod.a`, but the C++ headers of the kit are not in the package).
* **How.** Put `module-is-c-plus-plus:` in the CMHG file. `cmunge` then makes the initialisation veneer call `__modlib_cxx_init` (the static constructors, in the order of their priority, from `.init_array`) before the module's own initialisation code, and the finalisation veneer call the module's finalisation code first and `__modlib_cxx_fini` after it (the destructors that `__aeabi_atexit` registered, last in first out, then `.fini_array`); a module with no finalisation code gets a finalisation veneer anyway. A module without the directive is as it was (the constructors do not run: the test checks that). `module.mk` compiles `.cc`, `.cpp` and `.cxx` sources with `g++ -mmodule -std=gnu++17 -fno-exceptions -fno-rtti -fno-threadsafe-statics` (a module has one thread of control, and the guard of a local static is an ARMv6 barrier instruction), with the folder `include-cxx` first, then the headers of libstdc++, then the kit's, and links with the C driver (`gcc -mmodule`; `g++` would add the hard-float libstdc++ and libm). Without `module.mk`, use its `MODCXXFLAGS` (`tests/cxx/headers-survey.py` asks `make` for them): `g++ -mmodule` alone does not put the headers in this order. [`examples/cxxmod`](../modkit/examples/cxxmod) is a module of about 90 lines of C++: a static object, classes with virtual functions, `new` and `delete`, a template, a lambda, a local static (13.7 KB).
* **`new` and `delete`** are `malloc` and `free` (the RMA); a failed `new` is `abort ()` (a RISC OS error), `new (std::nothrow)` gives a null pointer. A program may replace the global `operator new (size_t)` and `operator delete (void *)`: `new[]` and the sized and nothrow forms of `delete` go through whatever is linked, as in C++; the nothrow forms of `new` take memory from `malloc` directly, so a program that replaces `new` and uses them replaces those too.
* **The C++ library.** There is no libstdc++ in a module, but most of it is headers, and the kit links the few members of the toolchain's `libstdc++.a` that those headers need: [`bin/mklibgcc.sh`](../modkit/bin/mklibgcc.sh) keeps the members whose code is plain ARMv6 (the same filter as for `libgcc-mod.a`: 35 of 199 left, see below) in `libstdcxx-mod.a`, which `libmodkit.a` names, without the exception runtime. They are libstdc++'s own code, under the GPL version 3 with the GCC Runtime Library Exception, like the library in every program that GCC links. The filter also drops the members that were compiled position independent: this tool chain's `-fPIC` code (the shared libraries of UnixLib) reaches its data through a table at address `0x8000` of the *program*, which a module does not have (the first version of the filter let `string-inst.o` through, and the module read the memory at `0x8038`), so 58 of the 199 members pass, and 23 more that duplicate the kit's own runtime or are the exception runtime are removed (35 are left: the red-black tree behind `map` and `set`, the list nodes, and the like). `std::string` and the other templates that libstdc++ says it has instantiated (`extern template`) are instantiated by the module's own code instead: `include-cxx/bits/c++config.h` switches `_GLIBCXX_EXTERN_TEMPLATE` off. `modreloc` refuses code with a `.got` and says why. What the code of those members names of the exception runtime (`__cxa_begin_catch`, `__gxx_personality_v0`, `_Unwind_Resume` ...) is in `lib/cxxeh.c`, as functions that end the call: nothing in a module throws, so they are never reached.
* **Works** (`tests/cxx/headers-survey.py` compiles and links 51 small programs; `tests/cxx/test-cxx.py` runs two larger ones on the interpreter and compares their text with the host's): static objects with constructors and destructors in several translation units, virtual functions, multiple inheritance, abstract classes, templates, lambdas, structured bindings, `if constexpr`, local statics, `new[]` of objects with destructors, replacing `operator new`; `<new>`, `<array>`, `<algorithm>`, `<numeric>`, `<vector>`, `<deque>`, `<list>`, `<map>`, `<set>` (and `multimap`), `<unordered_map>`, `<unordered_set>` (their rehash policy and `std::_Hash_bytes` are the kit's own, `lib/cxxhash.c`: the bucket counts are other primes than the host's, so the order of the elements differs), `<string>` (`std::string`, `std::to_string`, `std::stoi`), `<string_view>`, `<memory>` (`unique_ptr`, `shared_ptr`, `make_shared`), `<functional>` (`std::function`, `std::bind`), `<tuple>`, `<optional>`, `<variant>`, `<utility>`, `<iterator>`, `<bitset>`, `<span>` (C++20), `<atomic>` (for 4-byte types and pointers), `<chrono>` (the types and arithmetic; `steady_clock::now()` and the other clocks do not link), `<initializer_list>`, `<type_traits>`, `<limits>`, `<complex>` (`*` and `/` of `complex<double>` link since 16.2.0-22), `<random>` (new in 16.2.0-23, now that `std::lgamma` is there: it compiles and links; it was not run), `<cmath>`, and the C headers `<cstdio>`, `<cstdlib>`, `<cstring>`, `<cstdint>`, `<ctime>`, `<cassert>` ... A module that uses `std::string`, `std::vector`, `std::map`, `std::set`, `std::list`, `std::unordered_map` and `std::function` (the test module `CxxStd`) is 78 KB.
* **Does not work.** Exceptions (`throw`, `try` and `catch` do not compile: `-fno-exceptions`), RTTI (`dynamic_cast` and `typeid` do not compile: `-fno-rtti`), `thread_local` (it does not link), the streams (`<iostream>`, `<sstream>`, `<fstream>`: they need locales and the library's `cout`), `<mutex>` and `<thread>` (there are no threads: `bits/gthr-default.h` of the kit is the single thread version of GCC, so `shared_ptr` counts without atomics and `<mutex>` does not compile), `std::exception`, `std::bad_alloc` and the exception classes of `<stdexcept>` (their members are not linked, so a module cannot derive from them), atomics of 1, 2 and 8 bytes beyond `load` and `store` (`exchange` and `compare_exchange` of `atomic<bool>`, `atomic_flag`, `atomic<long long>`: the Linux members of `libgcc` are not there), the wide character functions in `std::` (`<cwchar>` and `<cwctype>` declare nothing in `std::`; the C functions `::wcslen`, `::wcstol`, `::iswalpha` ... are there since 16.2.0-20, and `std::wstring` itself compiles and links) and the aligned `new` of C++17.
* **`<cmath>` and `<math.h>`** are the kit's own for C++ (`include-cxx`): libstdc++'s asks the C library for functions that the kit lacks (the `float` forms of `erf`, `lgamma`, `tgamma` and `fma`, and the special functions of C++17). The kit's has what `math.h` declares, with the overloads that C++ adds for `float`, `long double` (the `double` function is called) and integers, including `erf`, `erfc`, `lgamma`, `tgamma`, `fma`, `remquo`, `scalbln` and `nexttoward` (new in 16.2.0-23), `std::abs`, and the classification macros as functions. Not there: the special functions of C++17, `std::lerp`, three-argument `std::hypot`.
* **On the hardware.** On the Raspberry Pi (Compute Module 4, RISC OS 5.30, 2026-10-10, the pack `module41`): `CxxMod` printed the constructor line before its initialisation line, answered `*CxxMod_Run 5` and `*CxxMod_Run 3` with the right areas and call counts, and printed its finalisation line before the destructor line when it was killed; `CxxStd` (`std::string`, `vector`, `map`, `set`, `list`, `deque`, `unordered_map`, `unique_ptr`, `shared_ptr`, `make_shared`, `std::function`, `optional`, `variant`, `<cmath>`, `<chrono>`, `<atomic>`) printed `33 lines, 0 differ: ok` twice in SVC mode; and `LibTest` as a module gave `TOTAL fail=0` with every compared section equal to glibc's, including the new `fpmathsp` (special values and `errno` of the maths functions), and the `tmpfile` section (which checks its own answers) passing.
* **How it is tested.** `tests/sim-cxxmod.py` builds `CxxMod` and `CxxStd` with `module.mk`, loads them at two addresses in the model of the kernel, and checks the order of the constructors, the module's code and the destructors, the answers, that every block claimed from the RMA is freed when the module is killed, that a module built without the directive does not run its constructor, and that the linked image has no VFP, NEON or ARMv7-only instruction. `tests/cxx/test-cxx.py` runs `cxxtest.cc` (the language) and `cxxstd.cc` (the library: strings, containers, smart pointers ...) on the host and on the interpreter, and the text must be the same. The interpreter learned `ldrex` and `strex` for `std::atomic`.

## Sockets

New in 16.2.0-19; **sockets became file descriptors in 16.2.0-23**. The calls of BSD sockets on the Internet module's `Socket_*` SWIs, the way the `socklib` of the RISC OS sources makes them (the arguments go into `R0`-`R5`, the result is `R0`; [`lib/sockets.c`](../modkit/lib/sockets.c)). **A socket is a file descriptor** (since 16.2.0-23; in 16.2.0-19 to -22 it was the Internet module's own small number, which only the socket calls took, as in a module of GCCSDK 4.7.4 with the Shared C Library): `socket` and `accept` return a number of the table that `open` uses ([the descriptor functions](#the-c-library-of-modkit)), and `close`, `read`, `write`, `readv`, `writev`, `ioctl`, `fcntl`, `dup`, `fstat` and `select` work on it as in UnixLib, so a source written for UnixLib, or for Acorn's TCPIPLibs (where `ioctl`, `close`, `read` and `write` on a socket are the socket calls), builds unchanged. The Shared C Library's names `socketclose`, `socketread`, `socketwrite` and `socketioctl` are the same calls. **A change for code that mixed the two ways:** until 16.2.0-22 the number that `socket` returned could be given as it was to the `Socket_*` SWIs or to OSLib's `socket_...` functions; now give them `__modlib_socket_handle (fd)`. **The same holds for the socket number in the Internet module's events**: `Event_Internet` (the event that `FIOASYNC` asks for) carries the Internet module's socket number in R2, not the descriptor, so a handler compares R2 with `__modlib_socket_handle (fd)`. GCCSDK's SysLogD (`gcc4/riscos/syslogd/main.c`) compares R2 with the value that `socket` returned: it builds unchanged, but with descriptors the comparison never matches (on the Pi, descriptors 3 and 4 were the Internet module's sockets 14 and 15), the event is passed on and SysLogD receives nothing until that line is changed. It has been built, never run. **Another:** `SIOCGIFADDR` and the other interface "get" requests of `<sys/ioctl.h>` had 4.4BSD's numbers in 16.2.0-19 to -22, which are wrong for the Internet module: rebuild a module that used them. **The details.** The descriptor holds the Internet module's handle (`__modlib_socket_handle (fd)` gives it, declared in `<sys/socket.h>`); code that calls the `Socket_*` SWIs itself and gets a handle from one turns it into a descriptor with `__modlib_socket_fd (handle)` (`close` then closes the Internet socket). `dup` makes a second number for the same socket and the Internet module's socket is closed with the last. `select` takes descriptors, and a descriptor that is not a socket (a file, the screen, the keyboard) is always ready. `ioctl (fd, FIONBIO, &on)` and `fcntl (fd, F_SETFL, O_NONBLOCK)` are the same thing (`F_GETFL` says which; a new socket is `O_RDWR`); `FIONREAD` and the interface requests (`SIOCGIFCONF`, `SIOCGIFADDR` ... of [`<sys/ioctl.h>`](../modkit/include/sys/ioctl.h) and [`<net/if.h>`](../modkit/include/net/if.h), with the numbers of the RISC OS Internet module: `SIOCGIFCONF`, `SIOCGIFADDR`, `SIOCGIFDSTADDR`, `SIOCGIFBRDADDR` and `SIOCGIFNETMASK` are not 4.4BSD's numbers; `SIOCGIFFLAGS`, `SIOCGIFMETRIC` and `SIOCGIFMTU` are) go to the Internet module. `fstat` says `S_IFSOCK`; `lseek` is `ESPIPE`; `isatty` is 0 with `ENOTTY`; **`fdopen` of a socket is `ENOTSUP`** (there is no `FILE` stream on a socket: use `read` and `write`, or `recv` and `send`). The table has 64 entries (0 to 2 are the standard streams), so at most 61 files and sockets are open at once, then `EMFILE`. **A socket is closed** when a runnable program ends (`exit ()`, `_Exit ()`, `abort ()`) and by `__modlib_closeall ()`, as the files are; a module that is killed without its finalisation running leaves its sockets open in the Internet module. An error is the result -1 with `errno` set from the Internet module's error number (`&20E00` plus the UNIX number; a number above 81, BSD's `ENEEDAUTH`, becomes `ESRCH`; an error outside `&20E00` to `&20E7F` sets `errno` to the raw error number), and the message in `_inet_err ()`; a number that is no open descriptor is `EBADF` from the table (the Internet module is not asked), and a descriptor of a file or the screen where a socket is needed is `ENOTSOCK`.

* Headers (BSD values and layout, with the length byte at the start of `struct sockaddr`): `<sys/types.h>` (`u_char` ..., `fd_set` of 256 bits: the descriptor table has 64 entries), `<sys/socket.h>`, `<sys/select.h>`, `<sys/time.h>`, `<sys/uio.h>`, `<sys/ioctl.h>` (`FIONBIO`, `FIOASYNC`, `FIONREAD` and, since 16.2.0-23, the interface and socket requests `SIOC...`), `<net/if.h>` (new in 16.2.0-23: `struct ifreq`, `struct ifconf`, the `IFF_` flags), `<sys/errno.h>` and `<sys/param.h>` (`MAXPATHLEN`, `MAXHOSTNAMELEN`, `howmany`, `roundup` ...: the BSD names that UnixLib's headers have and sources written for it include; both new in 16.2.0-23), `<fcntl.h>` (`fcntl` too, since 16.2.0-23), `<netinet/in.h>` (`htons` and the others are compiler built-ins), `<netinet/tcp.h>`, `<arpa/inet.h>`, `<netdb.h>`, `<syslog.h>` (the constants only).
* `gethostbyname` takes a dotted address as it is and asks the **Resolver** module (`Resolver_GetHostByName`, which blocks, like the single-tasking call it is) for any other name; the answer is in a static buffer. `getservbyname` and `getservbyport` read `InetDBase:Services` and use a list of 26 common services when that file is not there; `getprotobyname` and `getprotobynumber` have `ip`, `icmp`, `igmp`, `tcp` and `udp`. Also: `sendmsg` and `recvmsg` (`struct msghdr` with the vector of `<sys/uio.h>`), `inet_aton`, `inet_pton` (`AF_INET` only) and `inet_ntop`, `inet_network`, `inet_makeaddr`, `inet_lnaof` and `inet_netof`, `hstrerror` and `herror` (the texts of `h_errno`), and the Internet module's own calls under the Shared C Library's names: `socketstat` (`Socket_Stat`), `getstablesize` (`Socket_Stablesize`: the size of the Internet module's table), `socketreadv` and `socketwritev`. **Not there:** `gethostbyaddr` (it returns `NULL` with `h_errno` `NO_RECOVERY`), IPv6, `getaddrinfo`, `getifaddrs`, `socketpair`, `poll`, `syslog ()` itself.

## What it is

A module is a flat image with a header, loaded into the RMA, called in SVC mode, with no UnixLib or Shared C Library (the C library is the kit's own). `modkit` supplies what is missing around the compiler:

| Part | What it does |
|---|---|
| `src/cmunge.c` | CMunge's command line (`-tgcc -32bit -p -px -D -U -I -d -o -s -zbase -zoslib -zerrors -xh -xhdr -apcs`, and `-depend` with a warning) over the module header generator: reads a **CMHG** file (title, help and date strings, initialisation and finalisation code, `*` commands with international help, SWI chunks, vector, IRQ/callback and generic handlers, `module-is-runnable`) and writes the assembler header with the entry veneers, plus a C header (`bin/cmunge` and `bin/mkmodhdr.py` are the Python version) |
| `lib/`, `include/` | the C library of the kit (one source per group of functions, [above](#the-c-library-of-modkit)), integer division (`divmod.c`), the SWI veneer (`modswi.S`), the linker script `module.ld` |
| `src/mkoslib.c` | writes OSLib-style veneers for the OSLib functions your objects use (or the OSLib functions you name), from OSLib's headers |
| `src/modreloc.c` | the relocation step: the module is linked as position-dependent code and **relocates itself** when it starts, from a table of address words, so it can be loaded anywhere |
| `bin/` | besides the Python versions of the three tools: `mklibgcc.sh` (makes `libgcc-mod.a` and `libstdcxx-mod.a` when the kit is installed), `mkoslib-lib.sh` (makes `libOSLib32.a` from your OSLib headers), `asasm-fix.sh` ([what it does](#what-1620-23-added)), `mkswis.py` and `swis-extra.txt` |
| `lib/riscos_consts.py` | reads SWI and service call numbers from the RISC OS sources instead of typing them from memory |
| `module.mk` | the make rules: `include` it from the Makefile of a module; it builds the kit's library from the kit's own sources into the module's build folder, so a change of the kit counts at once |
| `tests/` | host simulations: a model of the RISC OS kernel (`riscosmodel.py`, on top of `modpoc/kernelmodel.py`) and an ARM interpreter (`tools/a32.py`) run the module's machine code offline (`sim-tickmod.py`, `sim-veneers.py`, `sim-runnable.py`, `sim-mk32.py`, `sim-cmhg2.py`); `libtest/`: the library against glibc; `test-ctools.py`, `os-cmhg-corpus.py`: the tools; `hwpack/`: the module of a hardware test |
| `modpoc/` (next to `modkit/`) | the two earlier proofs of concept, `HelloMod` and `HelloMod2` (hand-written header and veneers), with their kernel model and a mutation test |

`-mmodule` compiles with `-march=armv6 -mfloat-abi=soft -marm -ffreestanding -fno-stack-clash-protection` (so addresses live in literal pools and no `movw`/`movt` is used), `-fvisibility=hidden`, `-fno-builtin` (so that `memcpy`, `strlen` and `printf` are not replaced by the compiler), `-mno-unaligned-access`, `-nostdinc` and `-nodefaultlibs`, and no unwind tables or exceptions; whatever `-march`, `-mcpu`, `-mfpu` or `-mfloat-abi` you give is replaced (a module image has no relocation for `movw`/`movt`), except `-march=armv6*` (`armv6t2` passes the driver, but `modreloc` then refuses a module with `movw` / `movt` addresses). The link uses `--gc-sections` ([below](#size-of-a-module-and-garbage-collection-of-sections)).

## Size of a module, and garbage collection of sections

*New in 16.2.0-23.* The C library is built with a section for every function and every data item (`-ffunction-sections -fdata-sections`), and `gcc -mmodule` links with `--gc-sections`: the linker keeps what the module's header refers to (`module.ld` has `ENTRY (_start)` and keeps `.text.header` and the tables of constructors and destructors) and what that reaches, and drops the rest. Before 16.2.0-23 a module contained every function of each library object that it used, with the other functions of the same object.

* **What it saved**, with the same sources and flags (bytes, before and after): GCCSDK's SysLogD 61,868 and 38,780, ARMEABISupport 40,816 and 36,100, the Shared Object Manager 47,084 and 40,516, `examples/tickmod` 14,368 and 14,196, `examples/cxxmod` 14,164 and 11,616. GCCSDK 4.7.4 builds the same three modules of GCCSDK at 11,108, 32,096 and 29,748 bytes: the modules here are still bigger, because the C library is inside each of them and the Shared C Library is not.
* **Your own sources** are collected one function at a time if they are compiled with `-ffunction-sections -fdata-sections`; `module.mk` does so (`MODCFLAGS` and `MODCXXFLAGS`). Without the flags the linker can still drop a whole object file, but a function stays if another function of its file is called.
* **A program without the module header** (the test programs of `modkit/tests` have none) has nothing that refers to its start: name it with `-Wl,-u,main`, or the link drops everything.
* **To switch it off**: `-Wl,--no-gc-sections`. A module with `sprintf` and `memcpy` is 8,372 bytes with the collection and 9,520 without it.
* **The cost of one call** (a module of the header, one `double` and one call, in KB with and without the collection): `sqrt` 3.5 and 4.6, `exp` 4.4 and 5.9, `log` 4.3 and 9.9, `pow` 8.5 and 12.9, `sin` 10.2 and 13.5 (see [Floating point](#floating-point) for what the soft float routines cost).
* **Assembler sections** that are not named `.text*`, `.data*`, `.rodata*` or `.bss*` are still refused by `modreloc` (see [Limits](#limits)); `arm-riscos-gnueabihf-asasm-fix` renames them.

## Building the example

`modkit/examples/tickmod` is a module that claims the **`TickerV`** vector (called every centisecond in interrupt context), asks for **transient callbacks**, and records the processor mode, IRQ mask and registers in both handlers.

```bash
export OSLIB=<a directory that contains oslib/*.h>               # OSLib's headers (from GCCSDK or the OSLib distribution), for the SWI veneers
export RISCOS_SOURCES=<a checkout of the RISC OS Open sources>   # optional: https://gitlab.riscosopen.org/RiscOS/Sources: makes the one SWI number of the header be READ from the sources (only the Python `bin/cmunge` does; the C `cmunge` has the number built in)
cd modkit/examples/tickmod
make BIN=<cross toolchain>/bin                                   # -> TickMod,ffa (the module) and TickWait,ff8 (a tiny helper that waits in user mode)
```

A module Makefile sets `MODULE`, `CMHG` and `SRCS` (and `OSLIB_FUNCS`, for OSLib veneers) and includes `module.mk` (see `examples/tickmod/Makefile`): it runs the commands of the table above. `.cc`, `.cpp` and `.cxx` sources are compiled as C++. The other variables are `BIN` (the tool chain's `bin/`: from a checkout of the kit it must be given, the default is `$(HOME)/gccsdk-next/env-f/bin`), `OSLIB`, `BUILD`, `EXTRA_CFLAGS` and `EXTRA_CXXFLAGS` (for instance `-D_DEFAULT_SOURCE`), `CXXSTD`, `CMUNGE`, `MKOSLIB` and `MODRELOC`; `make clean` removes the build folder. It needs GNU make 4.3 or later. The tool chain installs a copy of `module.mk`, the sources of the library and the headers (C and C++) in `share/riscos-modkit/`. `cmunge` calls a C compiler for `-p` and `-o`: `CMUNGE_CC`, else `arm-riscos-gnueabihf-gcc` next to `cmunge` or on the `PATH`.

## Porting the Makefile of a GCCSDK 4.7.4 module

[PORTING-FROM-4.7.4.md](PORTING-FROM-4.7.4.md) is the whole checklist: what behaves differently, what to change and what is still missing. This section is the Makefile. A 4.7.4 module Makefile (compile with `-mmodule`, `cmunge`, link with `-lOSLibH32`) needs four changes. This is the Makefile of a real module (a network command server, 808 lines of C that use sockets, files and OS calls through OSLib) before and after; the module built from its **unmodified source**, passes the 102 checks of the host simulation (`sim-cmdserv2.py`), and passed its 39 network checks on the Pi (a transfer of 500,000 bytes and a soak of 300 commands among them) with the kit of 16.2.0-23; built on the Pi with 16.2.0-22 it was byte for byte the cross build:

```make
# before (GCCSDK 4.7.4)
CC    = arm-unknown-riscos-gcc -c -Wall -mpoke-function-name -O2 -mlibscl -mthrowback -mmodule -mhard-float -march=armv7-a -std=gnu99 -I$(ENV)/include -Ih -I.
LINK  = arm-unknown-riscos-gcc -mpoke-function-name -O2 -mlibscl -mthrowback -mmodule -mhard-float -march=armv7-a -L$(ENV)/lib
OBJS  = mod.o header.o
mod,ffa: $(OBJS)
	$(LINK) -o $@ $(OBJS) -lOSLibH32

# after (this tool chain)
TC    = <tool chain>/bin/arm-riscos-gnueabihf
CC    = $(TC)-gcc -c -Wall -mpoke-function-name -O2 -mthrowback -mmodule -std=gnu99 -I$(ENV)/include -Ih -I.
LINK  = $(TC)-gcc -mthrowback -mmodule
OBJS  = mod.o header.o oslibv.o
mod,ffa: $(OBJS)
	$(LINK) -o $@ $(OBJS)
oslibv.c: mod.o
	$(TC)-mkoslib -I $(ENV)/include/oslib -o $@ --from-objects mod.o
oslibv.o: oslibv.c
	$(CC) -x c -o $@ oslibv.c
```

1. The compiler is `arm-riscos-gnueabihf-gcc`. `-mlibscl`, `-mhard-float` and `-march=armv7-a` can stay (they are accepted; `-mmodule` replaces the architecture and the float ABI; `-mlibscl` after `-mmodule` needs a compiler of 16.2.0-20 or later), but there is no reason to keep them.
2. `cmunge` is the same command (`cmunge -32bit -tgcc -o header.o -d header.h file.cmhg`); the `cmunge` of the tool chain is the one in its `bin/`.
3. `-lOSLib32` links as it is (since 16.2.0-19), and so does `-lOSLibH32` after `install-oslib.py` (since 16.2.0-21); without OSLib built on the machine, `mkoslib` writes the veneers of the functions that your objects use.
4. The source must not need the C library beyond the list in [The C library of modkit](#the-c-library-of-modkit). A call that is not there is an error (the compiler stops at a function that no header declares, except with `-std=c90`, where an implicit declaration is silent; with `-fpermissive` it is an undefined symbol at the link): that is the whole list of what to port.
5. **Assembler files** written for `asasm` do not link as they are: run `arm-riscos-gnueabihf-asasm-fix` on the objects ([what it does](#what-1620-23-added)). Files written for the GNU assembler need nothing.
6. **The language level.** GCC 16 defaults to `gnu23`, 4.7.4 to `gnu89`. `-std=gnu89` compiles old code. With `-std=gnu99` or later, GCC 16 makes errors of an implicit function declaration, an implicit `int`, an integer converted to a pointer, incompatible pointer types and a `return` that does not match the function (K&R definitions and `int f();` are fine; `gnu23` also rejects the call `f (1)` after `int f();` and `typedef int bool`). `-Wno-error=implicit-function-declaration -Wno-error=implicit-int -Wno-error=int-conversion -Wno-error=incompatible-pointer-types -Wno-error=return-mismatch` relax them. Strict `-std=c99` hides the POSIX names (`strdup`, `strcasecmp`): use `-std=gnu99` or `-D_DEFAULT_SOURCE`.

OSLib's headers are needed (for the register layout in their comments); the headers of GCCSDK's `env/include/oslib` are the ones used here. Since 16.2.0-19, when `OSLIB` is set, `install-modkit.sh` (or `modkit/bin/mkoslib-lib.sh`) makes `libOSLib32.a` from your copy and copies the headers into your tool chain (`arm-riscos-gnueabihf/include/oslib`), so that `#include <oslib/os.h>` and `-lOSLib32` work without a flag in that tool chain (the released tool chains do not have them); **the official examples of GCCSDK 4.7.4** (`Examples/Module/Simple`, `NoSCL`, `ResourceFS` and `FS`) build with their own Makefiles unchanged (`modkit/tests/test-gccsdk-examples.py`; `Simple` and `NoSCL` also run on the interpreter).

## Trying it on RISC OS

Copy `TickMod,ffa` (type &FFA, module) and `TickWait,ff8` to RISC OS. **Save your work first**: the module is called from interrupts, and a mistake in a vector veneer shows up as a crash within a second of `*TickMod_Start`.

```
RMLoad TickMod
Help TickMod
TickMod_Start                 claims TickerV
TickWait 200                  wait two seconds in user mode: ticks and callbacks are counted
TickMod_Status
TickMod_Delay 200             two seconds inside a command (SVC mode): one callback waits until it returns
TickMod_Stop
RMKill TickMod
```

On the author's machine TickMod 0.01 (of 2026-10-04, built with the first version of the kit; the example is 0.02 now, which has been run on the interpreter only) ran with: ticks at exactly 100 Hz, the tick handler always in SVC mode with IRQs off, the callback in SVC mode with IRQs on, `r12` right, a callback that waits for the end of a command, `OS_RemoveCallBack`,
`RMKill` with the vector claimed, and thirty quick load / start / kill rounds, without a crash.

## Limits

* No `UnixLib` or `SharedCLibrary`, no exceptions, files only with [the rules above](#stdio-files-and-streams) (nothing is closed when a module is killed), floating point only as [described above](#floating-point) and C++ only as [described above](#c-in-modules): modules run on a small stack, in SVC mode, so keep stack use low (`qsort` is an in-place heap sort, with no recursion and no memory) and do not call blocking functions.
* **The stack.** The C code of a module runs on the kernel's **SVC stack: 32 KB that the whole OS shares**, and there is no automatic stack checking (an overflow is an abort). GCCSDK 4.7.4's modules had the same stack: its documentation says that module code in SVC and IRQ mode is compiled **without** stack checking (`-mmodule` implies `-mno-apcs-stack-check`) because those stacks are not chunked. A private stack (the veneers switching to a block of the RMA) was tried and **does not work**: the Task window saves the SVC stack between its top and `r13` whenever a task writes a character or sleeps, so an `r13` outside the SVC stack aborts it (seen on the Pi, 2026-10-10). Instead, `long __modlib_stack_left (void)` (`<kernel.h>`, since 16.2.0-19) says how many bytes are left (the top of the stack comes from `OS_ReadSysInfo 6`, the size is the kernel's 32 KB; -1 when it cannot know): ask before a deep recursion, and put anything bigger than a few KB in a `malloc` block. On the Pi it read 32,172 bytes at the top of a command and fell with the depth of the recursion. The program of a `module-is-runnable:` module runs in USER mode, on the stack at the top of the application memory, with no check either. `malloc`, `free`, `calloc` and `realloc` take their memory from the RMA (`OS_Module` 6 and 7).
* The header generator implements the subset of CMHG listed above; it reports anything else as an error rather than dropping it silently. **Where it differs from CMunge** (checked against the real CMunge 0.76 on the RISC OS Open sources and on generated files): a command without `max-args:` takes no arguments (CMunge's default; `cmunge` of 16.2.0-14 accepted 255); `min-args:`, `max-args:` and `gstrans-map:` above 255 are refused (they were cut to 255); a SWI chunk must be a non-zero multiple of 64 and must not have bit 17 set; a `swi-decoding-table:` without a prefix of its own takes the module title; `swi-decoding-code:` without `swi-decoding-table:` leaves the table word of the header 0 (the real CMunge points it at the module title); `\n` in a string is a carriage return (13) as in CMHG, and the C escapes `\t \x41 \a` are accepted (CMunge keeps the letter); quoted names are accepted (CMunge keeps the quotes); `help:` is refused (CMunge refuses it too); the `help-string:` is read the way CMunge reads it (name, version, date) and refused when CMunge refuses it; `finalisation-code:` is optional; the handler of `generic-veneers:` returns a `_kernel_oserror *` (0: return to the caller with the registers the handler left in the block and the flags as they were, else V set and r0 = the error), where 16.2.0-14 treated it like a vector handler; `module-is-runnable:` was ignored with a warning in 16.2.0-14 and is a real start entry in 16.2.0-15; a file with no `date-string:` gets no build date in the help line (CMunge adds the day of the build); `international:` and `add-syntax:` cannot be given for one command (both tools refuse); and CMunge 0.76's own output for `vector-handlers: e/h (error-capable:)` and for `module-is-runnable: simple-app:` does not assemble with GCCSDK's assembler (armasm syntax in GNU `as`), so for those two the real CMunge makes no module with `-tgcc` either.
* **Every section of the module must be one that the linker script places in the image**: `.text*`, `.rodata*`, `.data*`, `.bss*` and COMMON. `modreloc` refuses (since 16.2.0-16; it used to leave the section out) a link that has a loaded section of another name, for instance an assembler `AREA` of the OS sources, or `__attribute__ ((section ("x")))`; rename it (`objcopy --rename-section NAME=.text.NAME`, or a name that starts with `.data.`; for the objects of `asasm`, `arm-riscos-gnueabihf-asasm-fix` does it). `.init_array*`, `.ctors*`, `.fini_array*` and `.dtors*` (the constructors and destructors of C++) are placed too. When `modreloc` refuses, the driver exits with status 1 and leaves the ELF file under the name of the module: it is not a module. **Relocations:** `modreloc` accepts the absolute 32-bit words (`R_ARM_ABS32`, `R_ARM_TARGET1`) and PC-relative branches, and refuses the rest (`movw` / `movt`, 16-bit relocations, a GOT, thread-local storage) with "relocations the loader cannot apply". The script also defines `Image$$RO$$Base`, `Image$$RO$$Limit`, `Image$$RW$$Base`, `Image$$RW$$Limit`, `Image$$ZI$$Base` and `Image$$ZI$$Limit` (addresses inside the image, as the Norcroft linker's are) and the library has `__errno`, the BSD name of `errno`.
* The relocation is the modkit's own (a self-relocating image made by `modreloc`), not `ld`'s module support (`--ro-module-reloc` of GCCSDK's linker is not in binutils 2.45.1): that is why the driver runs a program (`modreloc`) after the linker, and why the code is ARMv6.
* `cmunge` has the options of CMunge that a freestanding module can use (`-tgcc -32bit -p -px -D -U -I -d -o -s`, `-zbase` since 16.2.0-19: `Image__RO_Base`, `-apcs 3/32`, and since 16.2.0-20 `-zoslib`, `-zerrors`, `-xh`, `-xhdr` and `-depend` (a warning, no file)), accepts without effect what has nothing to switch, and refuses what would change the module ([the commands](#the-commands-the-same-as-with-gccsdk-474); `cmunge -h` says the same). **The tools are C programs** (`modkit/src`: `cmunge`, `modreloc`, `mkoslib`), the same source for Linux (in the cross tool chain) and for RISC OS (in the native package), so modules can be built **on RISC OS** too: the native `Gcc16` has them, `libmodkit.a`, the linker script and the headers, and its `gcc -mmodule` is the same command as the cross one (16.2.0-14 was the first release with the tools, with the smaller kit). The `*.py` files in `modkit/bin` are the first versions of the three tools; `modkit/tests/test-ctools.py` checks the C ones against them (7,012 checks: the same output byte for byte on every CMHG file and ELF file of the test, and on every one of the 2334 OSLib functions).
* One person has tested it, on one machine (a Raspberry Pi Compute Module 4, RISC OS 5.30); it has not been run on an ARMv6 CPU. Save your work before you load a module that is new.
