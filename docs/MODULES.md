# modkit: building RISC OS modules with this tool chain (experimental)

> **Experimental.** Relocatable modules are the one thing the EABI tool chain could not build: GCCSDK's 4.7.4 compiler (APCS, SharedCLibrary) is still the only supported way for modules that matter. `modkit` shows that GCC 16 can build working modules **without UnixLib or the Shared C Library**,
> and since 16.2.0-14 it is used the way GCCSDK 4.7.4 was: **`gcc -mmodule`** and **`cmunge`**. It has been run on real hardware for small modules (below). **This page describes the kit of 16.2.0-16 and the work after it, which is in the repository and in no release yet:** floating point (`printf`, `scanf`, `strtod`, `<math.h>`, [below](#floating-point)), **C++** (static constructors and destructors, `new` and `delete`, and `std::string`, `std::vector`, `std::map` and the like: [below](#c-in-modules)) and a correction of how a module is linked with the compiler's own routines (16.2.0-14 to 16.2.0-16 could link code that needs the VFP). The C library has about 285 functions (16.2.0-14 had 30), with `stdio` files, the CMHG support and the `module-is-runnable` start code.
> The C library, `cmunge`, `module-is-runnable`, international help, the generic veneers and the `stdio` files and streams were run on the test machine (Raspberry Pi Compute Module 4, RISC OS 5.30) on 2026-10-07 with the kit of 16.2.0-15, and the native build of a module with its packages; three modules of the RISC OS Open sources that were built with the kit were compared there with the ROM's on 2026-10-08, with the same results in everything the program compares ([OS-MODULES.md](OS-MODULES.md#compared-with-the-rom)). What was run with the packages of 16.2.0-16 is in [what was proven on hardware](#what-was-proven-on-hardware). Floating point was run there on 2026-10-09 ([below](#floating-point)); C++ was run there on 2026-10-10 ([below](#c-in-modules)). Read the limits first.

## The commands (the same as with GCCSDK 4.7.4)

| GCCSDK 4.7.4 | This tool chain (16.2.0-14 and later) |
|---|---|
| `cmunge -tgcc -32bit -p -d header.h -o header.o file.cmhg` | the same command: `cmunge` is in the tool chain's `bin/` (it is modkit's module header generator behind CMunge's command line; the options that make no sense here are refused, not ignored) |
| `gcc -mmodule -O2 -c file.c` | the same: `-mmodule` means ARMv6, soft float, ARM state, freestanding, no PIC, no stack protector, no unwind tables, and the headers of modkit instead of UnixLib's; `__TARGET_MODULE__` and `__TARGET_SCL__` are defined, `__TARGET_UNIXLIB__` is not |
| `gcc -mmodule -o Module,ffa file.o header.o` (the linker writes the module) | **the same command**: the driver links with the module linker script and `libmodkit.a` (the tool chain has both) and then runs `modreloc`, so the output is the flat module image. An output named `*.elf` stays an ELF file (for a debugger or a simulation) |
| the Shared C Library through its stubs | **no C library of the usual kind**: `libmodkit.a` is a small library of its own (about 285 functions, [listed below](#the-c-library-of-modkit)): the string, `ctype`, `stdlib`, `time`, `setjmp`, `stdio` (`printf`, `sscanf` and files), `_swi` / `_swix` and `_kernel_*` functions that modules use, and floating point (`%f` in `printf` and `scanf`, `strtod`, `<math.h>`) |
| `-lOSLib32` / `-lOSLibH32` (OSLib's SWI veneers) | **`arm-riscos-gnueabihf-mkoslib -I <OSLib>/oslib -o oslibv.c --from-objects main.o`** writes the veneers of exactly the OSLib functions that your objects use (from OSLib's own headers: the comment above each function says which SWI and which registers); compile `oslibv.c` and link it. GCCSDK's prebuilt OSLib archives are for the old ABI and cannot be linked. New in 16.2.0-16: an output of the comment that is "the processor status register" (the flags) is made (34 more OSLib functions), `--from-objects` also takes static libraries (`libfoo.a`: what their members use is made as far as it can be, with a warning for a function that cannot), and a function that one of your own objects defines is not made again |

```bash
export PATH=<tool chain>/bin:$PATH
cmunge -tgcc -32bit -p -d header.h -o header.o module.cmhg
arm-riscos-gnueabihf-gcc -mmodule -O2 -Wall -c main.c -o main.o
arm-riscos-gnueabihf-gcc -mmodule -o MyModule,ffa main.o header.o     # the module: the driver runs modreloc after the linker
```

A makefile that has `.cmhg.o` and `.cmhg.h` rules with `cmunge -tgcc -32bit -p` and `LDFLAGS = -mmodule` works as it is, apart from the library (below). `module.mk` (below) has it all as make rules.
How the module is made: the linker writes an ELF file, and `arm-riscos-gnueabihf-modreloc` (a small C program; the driver runs it, `gcc -mmodule` only) replaces it by the flat image with the table of addresses that the module relocates itself with (the reason is under Limits). A partial link (`-r`) is not turned into a module.

## What can be built today, and what cannot

**It works for** small and medium C modules that need little from a C library: SWI handlers and decoding tables, `*commands` with international help, service calls, vector, IRQ, callback and generic handlers, OSLib and `_swix` calls, `malloc` from the RMA, `printf` and `sscanf`, files (`fopen` and the rest of `stdio`, [with its rules](#stdio-files-and-streams)), modules that can also be run as programs. Modules of that kind ran on the Pi (a service-call and SWI module, a `TickerV` and callback module, a network module of 800 lines, and the module that the self-test builds, loads and runs).

**What a module may need, and where it stands:**

| A module needs | State today |
|---|---|
| **C library** | [About 285 functions](#the-c-library-of-modkit): `string.h`, `ctype.h`, `stdlib.h` (`malloc` from the RMA, `strtol`, `strtod`, `qsort`, `rand`, `getenv`, `atexit` ...), `math.h`, `time.h`, `setjmp.h`, `locale.h`, `limits.h`, `stdint.h`, `assert.h`, `errno.h`, `inttypes.h`, `signal.h` (`signal`, `raise`), `stdio.h` (`printf`, `sscanf`, files: `fopen`, `fgets`, `fprintf`, `fscanf` ... and the streams `stdin`, `stdout`, `stderr`; [the rules](#stdio-files-and-streams)), `swis.h` (`_swi`, `_swix`) and `kernel.h` (`_kernel_*`). **Not there:** `gets`, `system`, `fenv.h`, `erf` and `gamma`, `fma`, the complex functions and the long double functions (`long double` is `double`). A call that is not there is an error: the compiler stops at a function that no header declares (with `-fpermissive` it is an undefined symbol at the link). |
| **CMHG** | The directives and options listed in the header of `bin/mkmodhdr.py`: title, help and date strings, initialisation and finalisation, service calls, SWI chunk, decoding table and handler, `*commands` (minimum and maximum arguments, GSTrans map, help and syntax text, `international:`, `add-syntax:`, `configure:`, `status:`, `fs-command:`), `international-help-file`, `module-is-runnable`, vectors, IRQ handlers, generic veneers and (new in 16.2.0-16) `event-handler:`. The numbers may be what the C preprocessor leaves of a name from the OS's headers, such as `(0x60)`, or a small constant expression (in the number lists of `service-call-handler:` and `event-handler:` without blanks: `(0x60+1)`, not `(0x60 + 1)`). The header that `cmunge -d` writes defines, besides the module's own names, most of what CMunge's does and OS sources use (not `CMUNGE_VERSION` and `CMHG_VERSION`): `<prefix>_00`, the SWI names with their `X` forms, `error_BAD_SWI`, `arg_CONFIGURE_SYNTAX`, `arg_STATUS`, `configure_BAD_OPTION` ... **Not there** (`cmunge` stops with an error that names the directive): `library-enter-code` and `library-initialisation-code` (they redirect the start-up of the Shared C Library, which a module here does not have: the message says so), `help:`, `swi-handler-code: f (flags-capable:)` (an extension of the newer Norcroft CMHG), the handler options of the `*-handlers:` directives, and `module-is-not-reentrant:`, `module-is-c-plus-plus:` and `vector-traps:` (CMunge accepts these three; none of the 66 modules uses them). |
| **Floating point** | **Works** (new since 16.2.0-16; [below](#floating-point)): `float` and `double` are soft float, with no VFP instruction anywhere in the module; `printf`, `sprintf`, `fprintf` and `scanf` convert them exactly (`%f %F %e %E %g %G %a %A`), as do `strtod`, `strtof`, `strtold` and `atof`; `<math.h>` has 98 functions (`sqrt`, `floor`, `fmod`, `sin`, `exp`, `pow` ...). Compared with glibc on the host and as ARM code on the interpreter; run on the Raspberry Pi on 2026-10-09 (below). 16.2.0-14, -15 and -16 could link code from `libgcc.a` that needs the VFP (a `double` converted to a `long long`, `__builtin_popcount`, `__builtin_powi`): fixed. |
| **C++** | **Works** (new since 16.2.0-16; [below](#c-in-modules)): the CMHG directive `module-is-c-plus-plus:` makes the module run the static constructors before its initialisation code and the destructors after its finalisation code; `new` and `delete` use `malloc` and `free` (the RMA); virtual functions, templates, lambdas; and the parts of the C++ library that need no operating system, as far as the tests go: `<string>`, `<vector>`, `<map>`, `<set>`, `<list>`, `<deque>`, `<array>`, `<algorithm>`, `<memory>` (`unique_ptr`, `shared_ptr`), `<functional>`, `<optional>`, `<variant>`, `<cmath>` ... **No** exceptions, no RTTI, no streams, no threads. Compared with the host on the interpreter, and run on the Raspberry Pi on 2026-10-10. |

**How much of the OS that is.** The RISC OS Open sources (the BCM2835 subset) have 86 components that build assembler modules, which no C compiler helps with, and 66 that build C modules. [`tools/scan-os-modules.py`](../tools/scan-os-modules.py) reads the C sources of those 66 (the calls of C library functions, comments and strings left out) and their CMHG files and holds them against what the kit has: **all 66 use only C library functions that the kit has** (51 before the `stdio` file functions: the 15 others used `fopen`, `fclose` and the like; with the 30 functions of 16.2.0-14 the figure was 7, and 4 of the 63 modules that call a library function at all), **62 of the 66 have nothing in their CMHG file that `cmunge` lacks** (the count of the scan: 27 with 16.2.0-14, 58 with 16.2.0-15, 62 with 16.2.0-16; the others use `library-enter-code`, `library-initialisation-code` and `help:`; the 4 more of 16.2.0-16 are the ones with `event-handler`; the scan does not see the handler option `(flags-capable:)` of TerritoryManager, so `cmunge` itself accepts 56 of the 61 components that have a CMHG file: [OS-MODULES.md](OS-MODULES.md#what-was-checked)), and **the same 62 pass both**. One of the 66 uses floating point and none uses C++. `modkit/tests/os-cmhg-corpus.py` runs the CMHG files of the 61 components that have one through `cmunge` and through the real CMunge and compares what the module headers say: where both accept a file the headers are the same. A real module also has to compile with its own headers (most of that source is written for the Norcroft C compiler), so these figures say what the library and the header generator would allow, not what builds untouched; and 51 of the 66 call `_swix`, which behaves here as the Shared C Library's does only as far as `libtest` checks it. **What does build untouched was then tried** (for 16.2.0-16, [OS-MODULES.md](OS-MODULES.md)): the 66 were built the way the OS build builds them, with the kit in place of the Norcroft tools: **29 build and link into a module image, 40 compile completely**, and the page says what stops each of the others. Three of the 29 (Squash, MimeMap, DrawFile) were then run on the Raspberry Pi in place of the ROM's modules, with the same results.

**The plan**, in this order and without promises: the CMHG directives that are still refused; more of the OS's modules (floating point and C++ are done, in the repository). Bigger or older modules should keep using GCCSDK 4.7.4.

## The C library of modkit

One object per group of functions, so a module pays for what it uses (a module with `sprintf` and `memcpy` takes about 3 KB of library). It is freestanding; its only state is what C itself has (`errno`, the `rand` seed, the `strtok` position, the static buffers of `asctime`, `gmtime` and `strerror`), the list of exit functions, the open files and the three standard streams. Where C leaves a choice, the answer is glibc's, and the tests compare with glibc (below).

### stdio: files and streams

Built on `OS_Find`, `OS_GBPB`, `OS_Args`, `OS_File` and `OS_FSControl` 25 (`rename`), and on `OS_ReadLine` for the keyboard. A `FILE` and its 512 byte buffer are one `malloc` block. How it differs from a C library on Unix, and from the Shared C Library:

* **Names** go to FileSwitch as they are, and it translates them. Seen on the Pi: `<Var>` is expanded (a variable that is not set is empty: `EINVAL`), a name ends at a space, a wild card opens the first match, and the empty name is the current directory (`EISDIR`); from the sources of FileSwitch: `"` and `/` are refused (`EINVAL`) and `Prefix:` uses `Prefix$Path`. `b` and `t` in a mode mean the same; `x` with `w` fails with `EEXIST` when the file is there. A file that `fopen` makes has the type Data (&FFD), where the Shared C Library makes Text (&FFF) unless the mode has `b`; there is no way to set a type.
* **Size**: a file of 2 GB or more is not opened (`EOVERFLOW`) and a write that would pass 2 GB - 1 fails (`EFBIG`): the C types are 32 bit, although FileSwitch has up to 4 GB.
* **Files that are open**: FileCore opens a file that is open for writing for nobody, and neither deletes nor renames it (`EBUSY`): one stream for a file that is written. A file that is read only or locked is not opened for writing (`EACCES`), and a locked one is neither deleted nor renamed (`EACCES`). `rename` does not replace a file that is there (`EEXIST`) and does not cross file systems (`EXDEV`): `remove` the old name first.
* **Errors**: `errno` is set from the OS error (`ENOENT`, `EISDIR`, `EACCES`, `EBADF`, `EBUSY`, `EEXIST`, `ENOTEMPTY`, `EMFILE`, `EROFS`, `ENOSPC`, `EINVAL`, `EFBIG`, `EOVERFLOW`, `EXDEV`; anything else is `EIO`) and the OS error itself stays in `_kernel_last_oserror ()`. FileSwitch writes late: a disc error shows at `fflush` or `fclose` (`EOF`, `ferror`).
* **stdin** reads a line at a time with `OS_ReadLine`: at most 258 characters, and the OS call drops control characters (TAB too); Escape is the end of the input, and the end-of-file flag stays until `clearerr`. **stdout and stderr** are the screen, unbuffered: one `OS_WriteC` per character and `OS_NewLine` (LF CR) for a line feed. `freopen (name, mode, stdout)` sends `printf`, `puts` and `putchar` to the file. `setvbuf` does nothing for the three. `tmpnam` gives a name in the scrap directory (`<Wimp$ScrapDir>.tmpXXXXXXX`, for which there is no object) and `tmpfile` opens one "w+b" and removes it when the stream is closed (16 at once; a module that is killed without closing them leaves the files, like any other); new since 16.2.0-16. Not there: `freopen (NULL, ...)`, `gets`, `fseeko`, `ftello`.
* **The end**: `exit ()` and a return from `main` of a runnable module flush and close every file (the OS does not close files at `OS_Exit`); `_Exit` and `abort` close them without writing the buffers. **A module that is killed does not**: call `__modlib_closeall ()` (declared in `<stdio.h>`) in its finalisation. A `FILE` that a runnable program does not close is an RMA block that stays after the program, like every `malloc` block that it does not free.
* **Details**: `ungetc` takes one character, a seek throws it away, and `ftell` is one less after it; `fscanf` uses up `0x` even when no hex digit follows (glibc does); `printf` has `%n`, and a width or precision above `INT_MAX` is -1 with `EOVERFLOW`; `scanf` has no `%lc`, `%ls` or `%l[` (the scan stops); in `%[`, `a-c` is a range when `a <= c` and `c` is not `]`, ranges do not chain, and a first `]` is itself.

**How it was tested.** Against glibc: random sequences of operations on files (about 21,000 results in each run of the host test: every mode, `fwrite`, `fputc`, `fread`, `fgets`, `ungetc`, `fseek`, `ftell`, `fgetpos`, `fflush`, `fprintf`, `fscanf`, the buffer modes) must give the same hashes on the host build (with the sanitizers), and as ARM code on the interpreter. The file system there is a model of FileSwitch and FileCore on the host's files (`modkit/tests/libtest/hosthooks.c` and `fsmodel.py`: a file that is open for writing is open for nobody, read only and locked files, unsigned lengths, `OS_Args 1` beyond the end, disc errors that can be switched on); the checks of the section `stdio2` give the answers of the rules above, and `sim-mk32.py` leaves a file open at the end of a program, run after run. **A model is not FileSwitch**, so a hardware pack (a folder of files for the Pi: not published) runs the same sequences and the same rules on the machine. **Run on the Pi on 2026-10-07 (NVMe, ADFS/FileCore): the section `stdio` (21,068 results) gives the same hash as glibc**, and so do the eight other compared sections; the checks of `stdio2` about read only and locked files, a file that is open twice, a folder, the end of a program that leaves a file open (run after run), the keyboard and the screen streams passed. Two checks failed, and both were wrong in the test, not in the library: a rename onto a file that is there is "Bad rename" (`EEXIST`) whatever the state of the source, because FileSwitch looks at the destination before FileCore looks at the source (the model had the order the other way round). A second run with those checks corrected gave `TOTAL fail=0`, and its section `probe` printed what FileCore and FileSwitch answer in about 90 cases (rename, remove and open of read only, locked and open files, two streams on one file, the pointer beyond the end, attributes, names): those lines are `modkit/tests/libtest/pi-probe.txt`, and `check-probe.py` (run by `run-host.sh` and `run-arm.py`) holds the model against them. They differ only in the names (the model has the host's), and in the length that the catalogue shows for a file that was just opened for output. On the NVMe the error numbers are FileCore's with the file system number in front (&1C8C3 is "Locked", &C3): `errno` is mapped from the low byte.

`libmodkit.a` that the driver links is a linker script that names `libmodkit-core.a` and then `libgcc-mod.a` (new since 16.2.0-16; the earlier kits named `libgcc.a`: see [Floating point](#floating-point) for why that was wrong), so the helpers of the compiler (64 bit division, soft floating point) are found without `-lgcc`; the kit's own integer division comes first.

**A module that is also a program** (`module-is-runnable:` in the CMHG file): `cmunge` makes a start entry, so that `*RMRun Module a "b c" d` (or `*Run` of the file) calls `int main (int argc, char **argv)` in user mode with the words of the command line (up to 40; `"` groups); `exit ()` and a return from `main` end the program with `OS_Exit` and the return code; `atexit` functions run. In SVC mode (a command, a SWI or a service call of the same module) `exit ()` is an error ("exit (3) was called in a module"), never the end of the desktop. A module that says `module-is-runnable:` and has no `main` ends with 0 when it is run.

**International help** (`international-help-file:` and the command option `international:`): the `help-text:` and `invalid-syntax:` of such a command are message tokens, looked up by the kernel in the Messages file that the header names (any path, also through a path variable: `"MyMod:Messages"`). **The value of a help or syntax token must end with a NUL byte (`CHR$ 0`) before the line end**, as the OS's own `CmdHelp` files have it (`HDEV:*GPIODevices lists ...<NUL><LF>`): `*Help` prints the value in place with `OS_PrettyPrint`, which stops only at a NUL, and the text of a syntax error is copied up to the NUL. A value with only the line end prints the rest of the file and then whatever follows it in memory (seen on the Pi). The header that `cmunge` makes is the same as CMunge's; the NUL is in the Messages file.

### Floating point

*New since 16.2.0-16: in the repository, in no release yet.* `float` and `double` are soft float: for every operation the compiler calls a routine of integer code, so a module has no VFP instruction, does not touch the VFP registers of the program that was running when it was called (RISC OS does not save the VFP state for code in SVC mode), and runs on an ARMv6 CPU.

* **`libgcc-mod.a`, and a fault of 16.2.0-14 to -16.** The `libgcc.a` of the tool chain is built for ARMv7 with the VFP, and the members that GCC compiles from C use both: a `double` or `float` converted to a `long long` or `unsigned long long` (`__fixdfdi` and its three relatives), `__builtin_popcount`, `__builtin_parity`, `__builtin_ffs`, `__builtin_ctzll`, `__builtin_powi`, complex multiplication and division, `_BitInt`. Only the members written in assembler (the soft float arithmetic, the integer division) are plain ARM code. 16.2.0-14, -15 and -16 linked the whole `libgcc.a` after the kit's library and the linker said nothing, so a module that did one of those things contained `vmov`, `vcmpe`, `movw`, `movt` or `rbit` (an undefined instruction on an ARMv6 CPU such as the Pi 1; on a Pi 4 the module would have used the VFP registers of the program that called it). The statement of those releases that no instruction of the VFP is used in a module was wrong for these routines. [`bin/mklibgcc.sh`](../modkit/bin/mklibgcc.sh) now makes `libgcc-mod.a` when the kit is installed: a copy of `libgcc.a` without every member whose disassembly has a VFP or NEON instruction, `movw movt rbit ubfx sbfx bfi bfc mls udiv sdiv dmb dsb isb`, or that is a Thumb helper or a Linux system call, and without the fixed-point members (125 of 1,762 members stay, 100 KB). `libmodkit.a` names it instead of `libgcc.a`, so a routine that is not there is an undefined reference at the link. What C code reaches of the dropped members is in [`lib/gccrt.c`](../modkit/lib/gccrt.c), integer code only: the conversions of `double` and `float` to 64-bit integers (they saturate and give 0 for a NaN, as the VFP does), the bit counts, `__powidf2`. `cross-smoke.sh` links such a module and checks that no member comes from `libgcc.a`. What is **not** there is an undefined reference at the link, not a crash: the complex multiplication and division of `double` and `float` (`__muldc3`, `__divdc3` and the `float` ones: they use the VFP), the multiplication and division of `_BitInt` wider than 64 bits, and the atomic operations on 8 bytes and the 1- and 2-byte `__sync` compare-and-swap (the members that call the Linux kernel). The members that are kept are stripped of their debug information and of the `.ARM.attributes` section (they say ARMv7 and VFP, which the code that is left in them is not); the script disassembles the finished archive once more and stops with an error if an instruction is left that a module must not run, or if `objdump` fails.
* **`printf`, `snprintf`, `fprintf`: `%f %F %e %E %g %G %a %A`** with the flags `- + space # 0`, a width and a precision (digits or `*`) and the length `L` (a `double`). The digits are those of the binary value, which a decimal number can hold exactly (the expansion of a `double` ends), rounded to the precision with ties to the even digit, so the output is glibc's for every value, `inf`, `nan` and `-nan` included. It is made with big integers of 32-bit limbs and integer code only (nothing of `libgcc`, no division): about 1,000 bytes of stack for a call of `snprintf` with a conversion of a `double` (210 for a call without one) whatever the precision (`%.1000f` of 1e300, `%.1100e` of 5e-324 and a precision of 100,000 work), about 60,000 instructions for an ordinary number.
* **`strtod`, `strtof`, `strtold`, `atof`, and `%f %F %e %E %g %G %a %A` in `sscanf`, `fscanf`, `scanf`.** The result is the nearest number to the exact value of the text, ties to the even one, for a decimal number of any length (the first 800 digits count, and one more for any non-zero digit after them: the halfway point between two `double`s has 768 digits at most), a hexadecimal one (`0x1.8p3`), `inf`, `infinity`, `nan` and `nan(chars)` (the characters in the parentheses are read as an integer, as `strtoull` with base 0 reads one, and become the payload of the NaN, as in glibc: `nan(12)` is `0x7ff800000000000c`). `strtof` and `%f` round once, to a `float`, not twice through a `double`. `ERANGE` is set for infinity and for a result that is zero or subnormal and not exact (glibc's rule: tiny after rounding to the precision of the type). `strtod` takes about 640 bytes of stack, and for a number of more than about 395 digits (or a large exponent) memory from `malloc` as well (780 digits: 670 bytes); if `malloc` fails the first 40 digits are used. `sscanf` with a floating point conversion takes about 1,070 bytes of stack (500 with integers and strings only), and memory from `malloc` for a number of more than 62 characters. `scanf` collects the characters the way glibc's does and converts them with the same routine, so as in glibc the text collected must be a number all through (`1e` and `0x1p+` are no number: nothing is stored), `0x` is used up, `infin` is no number but `inf` and `infinity` are, `nan(abc` is none either, and `%1f` or `%5lf` limit the width.
* **`<math.h>`: 98 functions**, in `double` and `float` (the `float` ones work in `double` and round once). *Exact*, the result and `errno` as glibc gives them: `sqrt`, `floor`, `ceil`, `trunc`, `round`, `rint`, `nearbyint`, `lround`, `llround`, `lrint`, `llrint`, `fmod`, `remainder`, `frexp`, `ldexp`, `scalbn`, `modf`, `copysign`, `fabs`, `fmin`, `fmax`, `fdim`, `nextafter`, `logb`, `ilogb`, `nan`. *Sun's fdlibm 5.3* (GNU Classpath's copy, `lib/fd_*.c`, with Sun's notice, which allows its use if the notice stays; `lib/fdlibm.h` says what was changed): `exp`, `log`, `log10`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `hypot`, `cbrt`, `expm1`, `log1p`; `exp2`, `log2`, `asinh`, `acosh` and `atanh` are worked out from those. Measured against the `long double` functions of glibc over 12,000 values of each, the error is within 1 unit in the last place for `exp`, `log`, `pow`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `hypot`, `cbrt`, `expm1` and `log1p`, within 1.6 for `log10`, `log2`, `atan2`, `cosh`, `asinh`, `acosh` and `atanh`, and within 2.2 for `sinh` and `tanh`; the last bit is therefore not always the one glibc gives. `errno` follows glibc 2.43 (probed): `EDOM` for a domain error (`sqrt (-1)`, `log (-1)`, `acos (2)`, `sin (inf)`, `fmod (1, 0)`, `ilogb (0)`), `ERANGE` for `log (0)`, `atanh (1)`, `log1p (-1)`, an overflow and an underflow to 0; `pow (0, -1)` is a pole (`ERANGE`); a subnormal result sets nothing (except `nextafter`, `atan2` when it underflows to 0, and `asinh` and `atanh` of a subnormal number, as in glibc; glibc sets `ERANGE` for some subnormal results of `expf`, `exp2f` and `powf` by a rule of its own that is not copied). `pow (1, y)` and `pow (-1, +-inf)` are 1 for every `y`, a NaN included, as C99 says. Every function that is not exact is compared with glibc on special values (zeros, infinities, NaN, subnormals, the edges of each domain) for the class of the result and `errno` (the section `fpmathsp`). `fmin` and `fmax` return the second argument for equal zeros, and a NaN for a signaling NaN, as glibc's do. The macros (`isnan`, `isinf`, `isfinite`, `isnormal`, `signbit`, `fpclassify`, `isgreater` ...) are the compiler's.
* **Stack.** `snprintf` with a floating point conversion uses about 1,000 bytes of stack, `sscanf` with one about 1,070 (500 without), `strtod` 640; of `math.h` every function but one stays under 170 bytes, and `sin`, `cos` and `tan` of an argument above about 8e5 radians need about 850 (the argument reduction). The SVC stack of RISC OS is 32 KB, the IRQ stack 8 KB.
* **Size.** A program that uses `printf` takes 5.1 KB more than before for the conversions of `double` (`fpfmt.o` 4.0 KB, `fpbig.o` 1.0 KB); `sscanf` takes 5.4 KB more (`strtod.o` 3.7 KB, `scanf.o` 1.6 KB, and `fpbig.o` if `printf` has not brought it); `sqrt` costs 0.7 KB, `exp` 1.8 KB, `log` 2.0 KB, `pow` 4.7 KB, `sin` 6.7 KB (its argument reduction is most of that). A module that wants none of it defines `__modlib_fmtdouble` and `__modlib_strtofp` itself (two functions that return 0): the linker then does not take the library's.
* **Not there:** a rounding mode other than to nearest, `fenv.h`, exception flags and traps (nothing raises `SIGFPE`: `1.0 / 0.0` is infinity), `erf`, `gamma`, `fma`, `remquo`, `scalbln`, `nexttoward`, `nanf`, the complex functions, `_Float16`, and the `long double` functions (`long double` is `double`). A NaN made by arithmetic is positive (libgcc's), where the PC's is negative.
* **How it was tested.** The sections `fparith`, `fpconv` and `gccrt` of `libtest` run the soft float of `libgcc` and the routines of `gccrt.c` against the hardware `double`s of the host (62,500, 40,000 and 32,500 results: the same), `fpprintf` (9,000 formatted numbers), `strtod` (9,800 texts, each as `double` and `float`; exact halfway points among them, written out in 760 digits) and `fpscanf` (10,500) against glibc, `fpmathx` (135,000 results: the exact functions of `<math.h>` with their `errno`) against glibc, and `fpmath` (the other functions: the host build of the library and the ARM code agree bit for bit, and the error against `long double` is measured); every section equal on the host (with AddressSanitizer and UBSanitizer) at 40 times the size and as ARM code on the interpreter. Deliberately broken versions (a tie rounded up, the digits after the 800th ignored) are caught. `modkit/tests/sim-fpsvc.py` runs the module `FpSvc` of the hardware pack on the interpreter and the kernel model: about 1,700 answers worked out by glibc and Python (printf, strtod, sscanf, the arithmetic, `math.h`), the largest conversions, and arithmetic in a generic veneer called in IRQ mode. **On the Raspberry Pi** (Compute Module 4, RISC OS 5.30, 2026-10-09, the pack `module40` with the kit of that day): `FpSvc` passed 892 checks (printf, strtod, sscanf, the arithmetic, the conversions), 791 for `math.h` and the 10 largest conversions in SVC mode; 100 calls of floating point arithmetic in a generic veneer that `OS_CallEvery` calls gave the bits that the host gives; and `LibTest` as a module gave the hashes of glibc's run in all the sections that are compared with it (`fparith`, `fpconv`, `gccrt`, `fpprintf`, `strtod`, `fpscanf`, `fpmathx`: 318,084 results with `fpmath`, which is compared with the host build of the library). The one line that failed (`getenv` of a variable that the run script had not set) was the script's fault. The corrections made since (below) are for the next run, `module41`.

### C++ in modules

*New since 16.2.0-16: in the repository, in no release yet. Run on the interpreter and in the kernel model, and on the Raspberry Pi (below).*

* **How.** Put `module-is-c-plus-plus:` in the CMHG file. `cmunge` then makes the initialisation veneer call `__modlib_cxx_init` (the static constructors, in the order of their priority, from `.init_array`) before the module's own initialisation code, and the finalisation veneer call the module's finalisation code first and `__modlib_cxx_fini` after it (the destructors that `__aeabi_atexit` registered, last in first out, then `.fini_array`); a module with no finalisation code gets a finalisation veneer anyway. A module without the directive is as it was (the constructors do not run: the test checks that). `module.mk` compiles `.cc`, `.cpp` and `.cxx` sources with `g++ -mmodule -std=gnu++17 -fno-exceptions -fno-rtti -fno-threadsafe-statics` (a module has one thread of control, and the guard of a local static is an ARMv6 barrier instruction), with the folder `include-cxx` first, then the headers of libstdc++, then the kit's, and links with the C driver (`gcc -mmodule`; `g++` would add the hard-float libstdc++ and libm). Without `module.mk`, use its `MODCXXFLAGS` (`tests/cxx/headers-survey.py` asks `make` for them): `g++ -mmodule` alone does not put the headers in this order. [`examples/cxxmod`](../modkit/examples/cxxmod) is a module of about 90 lines of C++: a static object, classes with virtual functions, `new` and `delete`, a template, a lambda, a local static (13.7 KB).
* **`new` and `delete`** are `malloc` and `free` (the RMA); a failed `new` is `abort ()` (a RISC OS error), `new (std::nothrow)` gives a null pointer. A program may replace the global `operator new (size_t)` and `operator delete (void *)`: `new[]`, the nothrow forms and the sized forms go through whatever is linked, as in C++.
* **The C++ library.** There is no libstdc++ in a module, but most of it is headers, and the kit links the few members of the toolchain's `libstdc++.a` that those headers need: [`bin/mklibgcc.sh`](../modkit/bin/mklibgcc.sh) keeps the members whose code is plain ARMv6 (the same filter as for `libgcc-mod.a`: 58 of 199, see below) in `libstdcxx-mod.a`, which `libmodkit.a` names, without the exception runtime. They are libstdc++'s own code, under the GPL version 3 with the GCC Runtime Library Exception, like the library in every program that GCC links. The filter also drops the members that were compiled position independent: this tool chain's `-fPIC` code (the shared libraries of UnixLib) reaches its data through a table at address `0x8000` of the *program*, which a module does not have (the first version of the filter let `string-inst.o` through, and the module read the memory at `0x8038`), so only 58 of the 199 members are left (the red-black tree behind `map` and `set`, the list nodes, and the like). `std::string` and the other templates that libstdc++ says it has instantiated (`extern template`) are instantiated by the module's own code instead: `include-cxx/bits/c++config.h` switches `_GLIBCXX_EXTERN_TEMPLATE` off. `modreloc` refuses code with a `.got` and says why. What the code of those members names of the exception runtime (`__cxa_begin_catch`, `__gxx_personality_v0`, `_Unwind_Resume` ...) is in `lib/cxxeh.c`, as functions that end the call: nothing in a module throws, so they are never reached.
* **Works** (`tests/cxx/headers-survey.py` compiles and links 51 small programs; `tests/cxx/test-cxx.py` runs two larger ones on the interpreter and compares their text with the host's): static objects with constructors and destructors in several translation units, virtual functions, multiple inheritance, abstract classes, templates, lambdas, structured bindings, `if constexpr`, local statics, `new[]` of objects with destructors, replacing `operator new`; `<new>`, `<array>`, `<algorithm>`, `<numeric>`, `<vector>`, `<deque>`, `<list>`, `<map>`, `<set>` (and `multimap`), `<unordered_map>`, `<unordered_set>` (their rehash policy and `std::_Hash_bytes` are the kit's own, `lib/cxxhash.c`: the bucket counts are other primes than the host's, so the order of the elements differs), `<string>` (`std::string`, `std::to_string`, `std::stoi`), `<string_view>`, `<memory>` (`unique_ptr`, `shared_ptr`, `make_shared`), `<functional>` (`std::function`, `std::bind`), `<tuple>`, `<optional>`, `<variant>`, `<utility>`, `<iterator>`, `<bitset>`, `<span>` (C++20), `<atomic>`, `<chrono>` (the types and arithmetic), `<initializer_list>`, `<type_traits>`, `<limits>`, `<complex>`, `<cmath>`, and the C headers `<cstdio>`, `<cstdlib>`, `<cstring>`, `<cstdint>`, `<ctime>`, `<cassert>` ... A module that uses `std::string`, `std::vector`, `std::map`, `std::set`, `std::list`, `std::unordered_map` and `std::function` (the test module `CxxStd`) is 78 KB.
* **Does not work.** Exceptions (`throw`, `try` and `catch` do not compile: `-fno-exceptions`), RTTI (`dynamic_cast` and `typeid` do not compile: `-fno-rtti`), `thread_local` (it does not link), the streams (`<iostream>`, `<sstream>`, `<fstream>`: they need locales and the library's `cout`), `<mutex>` and `<thread>` (there are no threads: `bits/gthr-default.h` of the kit is the single thread version of GCC, so `shared_ptr` counts without atomics and `<mutex>` does not compile), the exception classes of `<stdexcept>` (`std::runtime_error`: their members are not linked), `<random>` (it needs `std::lgamma`), the wide characters (`wchar.h` and `wctype.h` only have the types; libstdc++ is configured without `wchar_t` support on this target) and the aligned `new` of C++17.
* **`<cmath>` and `<math.h>`** are the kit's own for C++ (`include-cxx`): libstdc++'s asks the C library for functions that the kit lacks (`erf`, `lgamma`, `tgamma`, `fma`, `remquo`, `nexttoward` and the `long double` functions). The kit's has what `math.h` declares, with the overloads that C++ adds for `float`, `long double` (the `double` function is called) and integers, `std::abs`, and the classification macros as functions. Not there: the special functions of C++17, `std::lerp`, three-argument `std::hypot`.
* **On the hardware.** On the Raspberry Pi (Compute Module 4, RISC OS 5.30, 2026-10-10, the pack `module41`): `CxxMod` printed the constructor line before its initialisation line, answered `*CxxMod_Run 5` and `*CxxMod_Run 3` with the right areas and call counts, and printed its finalisation line before the destructor line when it was killed; `CxxStd` (`std::string`, `vector`, `map`, `set`, `list`, `deque`, `unordered_map`, `unique_ptr`, `shared_ptr`, `make_shared`, `std::function`, `optional`, `variant`, `<cmath>`, `<chrono>`, `<atomic>`) printed `33 lines, 0 differ: ok` twice in SVC mode; and `LibTest` as a module gave `TOTAL fail=0` with every compared section equal to glibc's, including the new `fpmathsp` (special values and `errno` of the maths functions) and `tmpfile`.
* **How it is tested.** `tests/sim-cxxmod.py` builds `CxxMod` and `CxxStd` with `module.mk`, loads them at two addresses in the model of the kernel, and checks the order of the constructors, the module's code and the destructors, the answers, that every block claimed from the RMA is freed when the module is killed, that a module built without the directive does not run its constructor, and that the linked image has no VFP, NEON or ARMv7-only instruction. `tests/cxx/test-cxx.py` runs `cxxtest.cc` (the language) and `cxxstd.cc` (the library: strings, containers, smart pointers ...) on the host and on the interpreter, and the text must be the same. The interpreter learned `ldrex` and `strex` for `std::atomic`.

## How it is tested

* **The library**: `modkit/tests/libtest` generates its inputs from a fixed generator and runs the same test program three ways: against glibc (the oracle), against the library's own sources built for the host with AddressSanitizer and UBSanitizer, and as ARM code on the A32 interpreter (`tools/a32.py`) with a model of the few SWIs. The results of every section are hashed and **the three hashes must be equal** (about 118,000 results in the sections that are compared: `ctype`, `string`, `numbers`, `sort`, `div`, `sscanf`, `printf`, `stdio`, `time`, `inttypes`, `signal`). The sections that have answers of their own (`limits`, `rand`, `swix`, `clock`, `heap`, `setjmp`, `getenv`, and for `stdio` the errors, access, the end of a program, the screen and keyboard streams: `stdio2`, `stdio3`) check them. `run-host.sh` and `run-arm.py` run it; `run-arm.py` takes a few minutes.
* **`cmunge`**: `modkit/tests/test-ctools.py` compares the C `cmunge` with the Python one on 400 generated CMHG files, on the real ones and on files that must be refused (2978 checks), and on the files it makes with the real CMunge, where the real one accepts them. `modkit/tests/os-cmhg-corpus.py` runs every CMHG file of the RISC OS Open sources through `cmunge` and the real CMunge and compares what the module headers say (`cmhgdiff.py`).
* **The machine code**: `sim-veneers.py` (generic veneers in SVC, IRQ and USER mode with every flag state, SWI decoding table with a prefix that is not the title, service numbers that are no ARM immediate), `sim-runnable.py` (a module run as a program: `argc`, `argv`, `atexit`, `exit`, `abort`, the module as a module afterwards), `sim-mk32.py` (international help, `add-syntax`, the module's own SWIs, the self test in SVC and in USER mode), `sim-tickmod.py`: the machine code on the ARM interpreter against a model of the kernel.

## What it is

A module is a flat image with a header, loaded into the RMA, called in SVC mode, with no UnixLib or Shared C Library (the C library is the kit's own). `modkit` supplies what is missing around the compiler:

| Part | What it does |
|---|---|
| `src/cmunge.c` | CMunge's command line (`-tgcc -32bit -p -D -I -d -o -s`) over the module header generator: reads a **CMHG** file (title, help and date strings, initialisation and finalisation code, `*` commands with international help, SWI chunks, vector, IRQ/callback and generic handlers, `module-is-runnable`) and writes the assembler header with the entry veneers, plus a C header (`bin/cmunge` and `bin/mkmodhdr.py` are the Python version) |
| `lib/`, `include/` | the C library of the kit (one source per group of functions, [above](#the-c-library-of-modkit)), integer division (`divmod.c`), the SWI veneer (`modswi.S`), the linker script `module.ld` |
| `src/mkoslib.c` | writes OSLib-style veneers for the OSLib functions your objects use (or the SWIs you name), from OSLib's headers |
| `src/modreloc.c` | the relocation step: the module is linked as position-dependent code and **relocates itself** when it starts, from a table of address words, so it can be loaded anywhere |
| `lib/riscos_consts.py` | reads SWI and service call numbers from the RISC OS sources instead of typing them from memory |
| `module.mk` | the make rules: `include` it from the Makefile of a module; it builds the kit's library from the kit's own sources into the module's build folder, so a change of the kit counts at once |
| `tests/` | host simulations: a model of the RISC OS kernel (`riscosmodel.py`, on top of `modpoc/kernelmodel.py`) and an ARM interpreter (`tools/a32.py`) run the module's machine code offline (`sim-tickmod.py`, `sim-veneers.py`, `sim-runnable.py`, `sim-mk32.py`); `libtest/`: the library against glibc; `test-ctools.py`, `os-cmhg-corpus.py`: the tools; `hwpack/`: the module of a hardware test |
| `modpoc/` | the two earlier proofs of concept, `HelloMod` and `HelloMod2` (hand-written header and veneers), with their kernel model and a mutation test |

`-mmodule` compiles with `-march=armv6 -mfloat-abi=soft -marm -ffreestanding -fno-stack-clash-protection` (so addresses live in literal pools and no `movw`/`movt` is used), `-fvisibility=hidden` and no unwind tables or exceptions; whatever `-march`, `-mcpu`, `-mfpu` or `-mfloat-abi` you give is replaced (a module image has no relocation for `movw`/`movt`), except `-march=armv6k` and the like.

## Building the example

`modkit/examples/tickmod` is a module that claims the **`TickerV`** vector (called every centisecond in interrupt context), asks for **transient callbacks**, and records the processor mode, IRQ mask and registers in both handlers.

```bash
export OSLIB=<a directory that contains oslib/*.h>               # OSLib's headers (from GCCSDK or the OSLib distribution), for the SWI veneers
export RISCOS_SOURCES=<a checkout of the RISC OS Open sources>   # optional: https://gitlab.riscosopen.org/RiscOS/Sources: makes the one SWI number of the header be READ from the sources
cd modkit/examples/tickmod
make BIN=<cross toolchain>/bin                                   # -> TickMod,ffa (the module) and TickWait,ff8 (a tiny helper that waits in user mode)
```

A module Makefile sets `MODULE`, `CMHG`, `SRCS` and `OSLIB_FUNCS` and includes `module.mk` (see `examples/tickmod/Makefile`): it runs the commands of the table above. It needs GNU make 4.3 or later. The tool chain installs a copy of `module.mk`, the scripts and the headers in `share/riscos-modkit/`.

## Porting the Makefile of a GCCSDK 4.7.4 module

A 4.7.4 module Makefile (compile with `-mmodule`, `cmunge`, link with `-lOSLibH32`) needs four changes. This is the Makefile of a real module (a network command server, 800 lines of C that use sockets, files and OS calls through OSLib) before and after; the module built from its **unmodified source** and passed 101 of the 102 checks of the host simulation (the 102nd is a name-length detail of the renamed test copy):

```make
# before (GCCSDK 4.7.4)
CC    = arm-unknown-riscos-gcc -c -Wall -mpoke-function-name -O2 -mlibscl -mthrowback -mmodule -mhard-float -march=armv7-a -std=gnu99 -I$(ENV)/include -Ih -I.
LINK  = arm-unknown-riscos-gcc -mpoke-function-name -O2 -mlibscl -mthrowback -mmodule -mhard-float -march=armv7-a -L$(ENV)/lib
OBJS  = mod.o header.o
mod,ffa: $(OBJS)
	$(LINK) -o $@ $(OBJS) -lOSLibH32

# after (this tool chain)
TC    = <tool chain>/bin/arm-riscos-gnueabihf
CC    = $(TC)-gcc -c -Wall -mpoke-function-name -O2 -mthrowback -mmodule -std=gnu99 -I$(ENV)/include -Ih -I.
LINK  = $(TC)-gcc -mthrowback -mmodule
OBJS  = mod.o header.o oslibv.o
mod,ffa: $(OBJS)
	$(LINK) -o $@ $(OBJS)
oslibv.c: mod.o
	$(TC)-mkoslib -I $(ENV)/include/oslib -o $@ --from-objects mod.o
oslibv.o: oslibv.c
	$(CC) -x c -o $@ oslibv.c
```

1. The compiler is `arm-riscos-gnueabihf-gcc`. `-mlibscl`, `-mhard-float` and `-march=armv7-a` can stay (they are accepted; `-mmodule` replaces the architecture and the float ABI), but there is no reason to keep them.
2. `cmunge` is the same command (`cmunge -32bit -tgcc -o header.o -d header.h file.cmhg`); the `cmunge` of the tool chain is the one in its `bin/`.
3. `-lOSLibH32` becomes the veneers that `mkoslib` writes from the objects.
4. The source must not need the C library beyond the list in [The C library of modkit](#the-c-library-of-modkit). A call that is not there is an error (the compiler stops at a function that no header declares; with `-fpermissive` it is an undefined symbol at the link): that is the whole list of what to port.

OSLib's headers are needed (for the register layout in their comments); the headers of GCCSDK's `env/include/oslib` are the ones used here.

## Trying it on RISC OS

Copy `TickMod,ffa` (type &FFA, module) and `TickWait,ff8` to RISC OS. **Save your work first**: the module is called from interrupts, and a mistake in a vector veneer shows up as a crash within a second of `*TickMod_Start`.

```
RMLoad TickMod
Help TickMod
TickMod_Start                 claims TickerV
TickWait 200                  wait two seconds in user mode: ticks and callbacks are counted
TickMod_Status
TickMod_Delay 200             two seconds inside a command (SVC mode): one callback waits until it returns
TickMod_Stop
RMKill TickMod
```

On the author's machine the module ran with: ticks at exactly 100 Hz, the tick handler always in SVC mode with IRQs off, the callback in SVC mode with IRQs on, `r12` right, a callback that waits for the end of a command, `OS_RemoveCallBack`,
`RMKill` with the vector claimed, and thirty quick load / start / kill rounds, without a crash.

## Limits

* No `UnixLib` or `SharedCLibrary`, no exceptions, files only with [the rules above](#stdio-files-and-streams) (nothing is closed when a module is killed), floating point only as [described below](#floating-point) and C++ only as [described below](#c-in-modules): modules run on a small stack, in SVC mode, so keep stack use low (`qsort` is an in-place heap sort, with no recursion and no memory) and do not call blocking functions.
* There is no automatic stack checking. `malloc`, `free`, `calloc` and `realloc` take their memory from the RMA (`OS_Module` 6 and 7).
* The header generator implements the subset of CMHG listed above; it reports anything else as an error rather than dropping it silently. **Where it differs from CMunge** (checked against the real CMunge 0.76 on the RISC OS Open sources and on generated files): a command without `max-args:` takes no arguments (CMunge's default; `cmunge` of 16.2.0-14 accepted 255); `min-args:`, `max-args:` and `gstrans-map:` above 255 are refused (they were cut to 255); a SWI chunk must be a non-zero multiple of 64 and must not have bit 17 set; a `swi-decoding-table:` without a prefix of its own takes the module title; `\n` in a string is a carriage return (13) as in CMHG, and the C escapes `\t \x41 \a` are accepted (CMunge keeps the letter); quoted names are accepted (CMunge keeps the quotes); `help:` is refused (CMunge refuses it too); the `help-string:` is read the way CMunge reads it (name, version, date) and refused when CMunge refuses it; `finalisation-code:` is optional; the handler of `generic-veneers:` returns a `_kernel_oserror *` (0: return to the caller with the registers the handler left in the block and the flags as they were, else V set and r0 = the error), where 16.2.0-14 treated it like a vector handler; `module-is-runnable:` was ignored with a warning in 16.2.0-14 and is a real start entry in 16.2.0-15.
* **Every section of the module must be one that the linker script places in the image**: `.text*`, `.rodata*`, `.data*`, `.bss*` and COMMON. `modreloc` refuses (since 16.2.0-16; it used to leave the section out) a link that has a loaded section of another name, for instance an assembler `AREA` of the OS sources, or `__attribute__ ((section ("x")))`; rename it (`objcopy --rename-section NAME=.text.NAME`, or a name that starts with `.data.`). The script also defines `Image$$RO$$Base`, `Image$$RO$$Limit`, `Image$$RW$$Base`, `Image$$RW$$Limit`, `Image$$ZI$$Base` and `Image$$ZI$$Limit` (addresses inside the image, as the Norcroft linker's are) and the library has `__errno`, the BSD name of `errno`.
* The relocation is the modkit's own (a self-relocating image made by `modreloc`), not `ld`'s module support (`--ro-module-reloc` of GCCSDK's linker is not in binutils 2.45.1): that is why the driver runs a program (`modreloc`) after the linker, and why the code is ARMv6.
* `cmunge` has the options of CMunge that a freestanding module can use (`-tgcc -32bit -p -px -D -U -I -d -o -s`) and refuses the others (`-zbase`, `-zoslib`, `-zerrors`, `-x<type>`, `-tnorcroft`, ...). **The tools are C programs** (`modkit/src`: `cmunge`, `modreloc`, `mkoslib`), the same source for Linux (in the cross tool chain) and for RISC OS (in the native package), so modules can be built **on RISC OS** too: the native `Gcc16` 16.2.0-16 has them, `libmodkit.a`, the linker script and the headers, and its `gcc -mmodule` is the same command as the cross one (16.2.0-14 was the first release with the tools, with the smaller kit). The `*.py` files in `modkit/bin` are the first versions of the three tools; `modkit/tests/test-ctools.py` checks the C ones against them (2978 comparisons: the same output byte for byte on every CMHG file and ELF file of the test, and on every one of the 2334 OSLib functions).
* One person has tested it on one machine. For modules that matter, use GCCSDK's tool chain.
