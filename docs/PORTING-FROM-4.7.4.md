# Moving a module from GCCSDK 4.7.4

This page is for someone who has a module that GCCSDK 4.7.4 builds (`gcc -mmodule`, CMunge, the Shared C Library or `-znoscl`) and is deciding whether to build it with this tool chain, and how. It says why you might, who should not, what works as it is, what to change, what behaves differently and what is still missing. The details of the kit are in [MODULES.md](MODULES.md).

## Why move, and who should not

**What you get** (each point was checked against a GCCSDK 4.7.4 Release 6 installation):

* **A current compiler.** 4.7.4 is GCC 4.7.4 of 2012: C up to C11 (default `gnu89`; it rejects `_Generic` even with `-std=c11`), C++ up to C++11 (default `gnu++98`), no `<stdatomic.h>` or `<uchar.h>`, and a C++ library without `<optional>`, `<variant>`, `<string_view>`, `<span>`, `<any>` or `<filesystem>`. It rejects `-std=c17`, `-std=c23`, `-std=c++14` and later, `-Og`, `-fanalyzer` and `-fsanitize=address`. This tool chain is GCC 16.2: C up to C23, C++ up to C++23, `-fanalyzer` (checked: it reports a double free), and in a module the C++17 parts listed in [MODULES.md](MODULES.md#c-in-modules) (structured bindings, `if constexpr`, `std::optional`, `std::variant`, `std::string_view`, `std::span`).
* **More C library than 4.7.4's module library has:** `stat`, `lstat`, `access`, `dup`, `dup2`, `fsync`, `fcntl`, the wide-character string functions (`wcslen`, `mbrtowc` ...), `strlcpy`, `strlcat`, `strndup`, `strnlen`, `inet_aton`, `inet_pton` and `inet_ntop`. Of the 439 public names (no leading underscore) that 4.7.4's module library defines, the kit has 423; the 16 it lacks are 13 names that belong to the Shared C Library itself (`TrapHandler`, `EventHandler`, `UncaughtTrapHandler`, `UnhandledEventHandler`, `disable_stack_extension` and the eight `x$` run-time entries of the Norcroft compiler) and three `signbit` functions (`signbit` is a macro of `<math.h>` here). [`tools/compare-4.7.4-names.sh`](../tools/compare-4.7.4-names.sh) reproduces the count. Sockets are file descriptors, as in UnixLib, so UNIX-style source such as Sunfish builds with no `-lTCPIPLibs`, no `-liconv` and no shim.
* **One EABI tool chain** for programs, modules and libraries (OSLib, DeskLib, FlexLib and SFLib are built for it from your copies), and the module tools run on RISC OS itself: a network module built on the Pi is byte for byte the module that the Linux cross compiler makes.
* **CMHG veneers that CMunge 0.76 cannot make with `-tgcc`:** `vector-handlers: v/h (error-capable:)` makes the real CMunge write an instruction the GNU assembler rejects; `cmunge` of this tool chain builds it, and it ran on the Pi.

**What has been run, on one Raspberry Pi Compute Module 4 (RISC OS 5.30), and what has only been built**

* *Run:* Sunfish, Alex Waugh's NFS client filing system (MIT, 224,264 bytes as the recipe builds it with the kit of 16.2.0-23 (298,516 before the link dropped unused functions), 40 C compilations of its own source plus four ObjAsm files; unmodified source, `-D_DEFAULT_SOURCE` added): it loads, mounts an NFS export (NFS3 over UDP), lists directories and reads 64 KB of a file whose CRC-32 equals that of an independent NFS client (13 Oct 2026; read only: the write path, TCP, NFS2 and NFS4, the `Encoding:` key, the Free module and the Wimp front end were not tried). An 800-line network module (sockets, files, OS calls): built on the Pi in 3 to 5 seconds, byte for byte the cross build, 39 network checks passed. Three modules of the RISC OS Open sources (Squash, MimeMap, DrawFile) loaded in place of the ROM's: 545 checks on each side and 9,820 lines of results, none different.
* *Built, not run:* GCCSDK's own SOManager, ARMEABISupport and SysLogD and its four example modules, from their own sources and Makefiles; 38 of the 66 C modules of the RISC OS Open sources, unchanged.

**When to stay with GCCSDK 4.7.4**

These are the reasons, and the only ones:

* **Your CPU is older than ARMv6.** A module here is ARMv6 code (a linked module contains `uxtb`, `uxth`, `rev`), and `-mmodule` replaces any `-march=` or `-mcpu=` of your Makefile **without a warning** (`-march=armv5te` gives ARMv6 code). 4.7.4's default module code is ARMv3. The kit has been run on a Cortex-A72 only, not on an ARMv6 CPU. (26-bit code is not a reason: neither tool chain makes it, and 4.7.4 rejects `-mapcs-26` too.)
* **You want hardware floating point in the module.** Here a module is always soft float: it has no VFP instruction and touches no VFP register, because RISC OS does not save the VFP state for code in SVC mode. 4.7.4's `-mmodule` makes FPA code by default and has VFP and NEON variants (`-mfpu=vfp -mfloat-abi=softfp`).
* **You need C++ exceptions, RTTI or iostreams inside a module.** 4.7.4 compiles and links them (a module with `try`/`catch`, `typeid` and `std::cout` links to 320 KB, 109 KB without the streams; whether it runs was not tested); this tool chain does not support them in a module ([MODULES.md](MODULES.md#c-in-modules)).
* **You want the smallest possible module.** The C library is inside each module here, not in a shared module, so a module that uses much of it is bigger than 4.7.4's. Same sources and flags (the kit with function-level garbage collection, 16.2.0-23):

  | Module | 4.7.4 | This tool chain |
  |---|---|---|
  | SysLogD | 11,108 | 38,780 |
  | ARMEABISupport | 32,096 | 36,100 |
  | SOManager | 29,748 | 40,516 |
  | `Simple` example (no library calls) | 4,032 | 640 |
  | `ResourceFS` example | 4,596 | 1,036 |
  | `NoSCL` example | 1,220 | 1,132 |

  A module that calls few library functions is smaller here, because the linker drops every function that nothing uses (`-mmodule` passes `--gc-sections`). The examples have no stdio, floating point or sockets; the three real modules do.
* **You build applications for the Shared C Library** (AIF files). `-mlibscl` without `-mmodule` is silently ignored here (you get a UnixLib ELF program), and there is no `elf2aif`. This tool chain does not support the Shared C Library at all.

If none of that applies, the rest of this page is a checklist. Your code may also depend on how the Shared C Library behaves: see [What behaves differently](#what-behaves-differently).

**The short version.** The commands are the same (`cmunge -tgcc -32bit -p ...`, `gcc -mmodule ...`). The code is ARMv6, soft float, and uses a C library of its own instead of the Shared C Library. The real modules of GCCSDK (the Shared Object Manager, ARMEABISupport and SysLogD) and its four example modules (the `FS` example needs OSLib: [OSLIB.md](OSLIB.md)) build from their own sources and Makefiles with this tool chain ([`modkit/tests/test-gccsdk-modules.py`](../modkit/tests/test-gccsdk-modules.py), [`test-gccsdk-examples.py`](../modkit/tests/test-gccsdk-examples.py)); that is how most of the differences below were found.

## What works as it is

| In your Makefile | Here |
|---|---|
| `cmunge -tgcc -32bit -p -d header.h -o header.o module.cmhg` | the same, with all the CMHG directives that GCCSDK's own modules use (SWI tables and decoding code, service calls, vectors, events, generic veneers with `private-word:` and `carry-capable:`, `error-chunk-base-number:` and `error-identifiers:` since 16.2.0-20, `vector-traps:` and `pdriver-handler:` since 16.2.0-22). A Makefile for the Linux cross compiler that says `arm-unknown-riscos-gcc` (and `-ld`, `-ar`, `-objcopy` ...) must say `arm-riscos-gnueabihf-gcc` and so on; `cmunge`, `mkresfs` and `asasm` keep their names |
| `cmunge -zbase`, `-zoslib`, `-zerrors`, `-xh FILE`, `-xhdr FILE`, `-depend FILE`, `-apcs 3/32/nonreent/fpe2/noswst/nofpr/nofp` | accepted (`-depend` with the same warning as CMunge's: no file is written; the `-apcs` flags in CMunge's abbreviated forms); `cmunge -h` says which are only accepted |
| `gcc -mmodule -O3 -std=gnu99 -c file.c` | the same; the code is made for ARMv6, soft float, ARM state, and `__TARGET_MODULE__` and `__TARGET_SCL__` are defined as before |
| `gcc -mlibscl -mmodule ...`, `-mpoke-function-name`, `-mthrowback`, `-mhard-float`, `-march=armv7-a` and the like | accepted, and `-mmodule` replaces the architecture and the float ABI (`-mlibscl` after `-mmodule` needs a compiler of 16.2.0-20 or later). `-mpoke-function-name` is on by default in 4.7.4 and off here: see [What behaves differently](#what-behaves-differently) |
| `gcc -mmodule -o Module,ffa main.o header.o` | the same: the driver links with the module linker script and runs `modreloc`, so the output is the flat module image. Since 16.2.0-23 the link drops the functions that nothing uses (`--gc-sections`); a program that has no module header (a test with only `main`) needs `-Wl,-u,main`, and `-Wl,--no-gc-sections` turns the dropping off |
| `-LOSLib: -lOSLib32` | works after `install-oslib.py --oslib-src <your svn checkout of OSLib> --toolchain <tool chain>` (new in 16.2.0-21; [OSLIB.md](OSLIB.md)): it builds **the real OSLib** with its own tools. OSLib is GPL with a linking exception and is not part of this project, so the library is built from your copy. X and non-X functions are all there, and the non-X ones are safe in modules (SVC mode). `-lOSLibH32` links too. The older `OSLIB=<folder with oslib/> modkit/bin/mkoslib-lib.sh <tool chain>` still makes a smaller library from the headers alone |
| `mkresfs` (GCCSDK's tool for ResourceFS modules) | it writes C, so it works with this tool chain as it is |
| `asasm` for assembler files | `asasm`'s objects do not link as they are: they carry EABI version 0 (`ld: error: source object callback.o has EABI version 0, but target ... has EABI version 5`) and name their sections after the `AREA` (`C$$Code`, `C$$Data`), which the module linker script does not place. Run **`arm-riscos-gnueabihf-asasm-fix`** on the objects (`arm-riscos-gnueabihf-asasm-fix callback.o ...`, in place): it sets the EABI version to 5 and renames each such section to `.text`, `.data`, `.bss` or `.rodata` by its kind. [`tests/sunfish/build-sunfish.sh`](../tests/sunfish/build-sunfish.sh) and `tools/build-os-modules.py` do this. `--no-warn-mismatch` is **not** a way round it: it would also hide a hard-float object linked into a soft-float module. Or rewrite the file for GNU `as` (GCCSDK's own modules' `.s` files are GNU syntax and build as they are) |

## What to change

* **Remove `-mfpu=fpa`, `-mfpu=fpe2`, `-mfpu=fpe3` and `-mapcs-26`.** GCC 16 does not know them (it has no FPA): they are errors. (4.7.4 does not know `-mapcs-26` or `-mapcs-32` either: GCCSDK 4 makes no 26-bit code.) Every other CPU or float option is **accepted and ignored**: `-mmodule` replaces `-march=`, `-mcpu=`, `-mfpu=`, `-mfloat-abi=` and `-mhard-float` by ARMv6, ARM state and soft float, with no warning.
* **Floating point.** 4.7.4's `-mmodule` makes FPA code by default (run by the Floating Point Emulator, or by the Shared C Library's own routines) and also has VFP and NEON variants (`-mfpu=vfp -mfloat-abi=softfp`). A module here is always soft float: `printf` and `scanf` of `%f %e %g %a` and `strtod` are exact (glibc's answers), `<math.h>` is within 1 to 2.2 units in the last place, and a module touches no VFP register of the program it interrupts. Correctness is not lost; floating point that ran on the VFP now runs in integer code, which is slower (there is no measurement).
* **Language level.** The default is `-std=gnu23` (4.7.4: `gnu89`), and GCC 16 is stricter.
  * `-std=gnu89` compiles old code as it is.
  * With `-std=gnu99`, `gnu11` or `gnu17` an implicit declaration of a function, an implicit `int`, an integer made into a pointer or the other way, an incompatible pointer type and a `return` with a missing or surplus value are **errors** (4.7.4: warnings). K&R function definitions and `int f ();` still compile.
  * `-std=gnu23` also makes `int f ();` mean `int f (void);` (a call `f (1)` is an error) and `bool`, `true` and `false` keywords (`typedef int bool;` is an error).
  * To build old code at a newer level, turn the errors back into warnings: `-Wno-error=implicit-function-declaration -Wno-error=implicit-int -Wno-error=int-conversion -Wno-error=incompatible-pointer-types -Wno-error=return-mismatch`.
  * Under strict `-std=c99` (and `c11`, `c23`) the POSIX and BSD names (`strdup`, `strcasecmp`, `getline` ...) are not declared: use `-std=gnu99`, or add `-D_DEFAULT_SOURCE` (Sunfish needs it).
* **The C library.** The Shared C Library is not used: there is no `-lscl`, no stubs, and `library-enter-code:` and `library-initialisation-code:` (which redirect its start-up) are refused. What the library has is in [MODULES.md](MODULES.md#the-c-library-of-modkit): C90 and C95 except the wide input and output functions (`fwprintf`, `swprintf`, `fgetwc` ...) and `wcsftime`, the C99 maths (`erf`, `lgamma`, `tgamma`, `fma`, `remquo`, `scalbln`, `nexttoward`, `nanf`, with `long double` as `double`) and a software `<fenv.h>`, the `_kernel_` functions that modules use, `<swis.h>` (`_swi`, `_swix`), `stdio` with files, floating point, sockets (`<sys/socket.h>`, `<netdb.h>`), the descriptor functions on files (`open`, `read`, `write`, `lseek`, `fstat`, `ftruncate` ...), the POSIX and BSD helpers that 4.7.4's module library had (`stpcpy`, `setenv`, `gmtime_r`, `gettimeofday`, `getline`, `fnmatch`, `warn` ..., since 16.2.0-21; the stubs `sethostname`, `setdomainname`, `settimeofday` and `clock_settime` and the `_l` functions `strcasecmp_l`, `strncasecmp_l` and `strerror_l` since 16.2.0-23), and the headers of GCCSDK's UnixLib that modules include for constants and types (`<sys/elf.h>` and `<sys/mman.h>` have the constants only; `<fcntl.h>` has `open`, `creat` and `fcntl` too; `<limits.h>`, `<net/if.h>`, `<sys/errno.h>`, `<sys/param.h>`).
* **Sockets.** A socket is a file descriptor (16.2.0-23): `close`, `read`, `write`, `ioctl` (`FIONBIO` ...), `fcntl` and `select` work on the number that `socket` or `accept` gives, as in UnixLib. The number is **not** the Internet module's handle. Code that gives the number to a `Socket_*` SWI, or compares it with a handle that the Internet module's events pass (GCCSDK's SysLogD compares `R2` of an `Event_Internet` with its socket), must use `__modlib_socket_handle (fd)` (declared in `<sys/socket.h>`); `__modlib_socket_fd (handle)` makes a descriptor of a handle that came from a SWI. For SysLogD that is one line: `r->r[2] != __modlib_socket_handle (sock)`. Sockets are closed when the module ends through its finalisation or `__modlib_closeall ()`; a kill that does not run the finalisation does not close them. `fdopen` on a socket fails with `ENOTSUP`.
* **SWI names.** `<swis.h>` has the names of the RISC OS Open sources and of GCCSDK's own list (`ARMEABISupport_MemoryOp`, `SysLog_LogMessage` ...), as plain macros. The `X` forms of the names that only GCCSDK has are not defined (its own modules use `[XName]` as the name of an assembler operand).
* **Build with `-lOSLib32` or `-lOSLibH32` (see [OSLIB.md](OSLIB.md)) or `mkoslib`.** Without a built OSLib library but with OSLib's headers, `mkoslib -I <OSLib>/oslib -o oslibv.c --from-objects main.o` writes the veneers of the functions that your objects use.
* **C++.** `g++ -mmodule` alone does not find the C++ headers (`fatal error: string: No such file or directory`): use the flags of `module.mk` (`MODCXXFLAGS`: the kit's `include-cxx` first, `-fno-exceptions -fno-rtti -fno-threadsafe-statics`) and link with `gcc -mmodule` ([MODULES.md](MODULES.md#c-in-modules)). Code with `throw`, `try`, `dynamic_cast`, `typeid`, `<iostream>` or threads does not compile or link here; 4.7.4 compiles and links it.

## What behaves differently

Found by comparing the preprocessor output of 4.7.4's `-mmodule` headers with the kit's. Code that compares error numbers or sizes, or depends on a Shared C Library detail, can change its behaviour without a compile error.

| | 4.7.4 (`-mmodule`, Shared C Library) | This tool chain |
|---|---|---|
| `EDOM`, `ERANGE`, `EILSEQ`, `EOVERFLOW`, `EFBIG`, `ENOENT` | 1, 2, 4, 5, 6, 84 | 33, 34, 90, 91, 27, 2 (UnixLib's): compare names, not numbers |
| nine error names of 4.7.4's `<errno.h>`: `ESIGNUM`, `EBADRPC`, `ERPCMISMATCH`, `EPROGUNAVAIL`, `EPROGMISMATCH`, `EPROCUNAVAIL`, `EFTYPE`, `EAUTH`, `ENEEDAUTH` | defined | not defined: a source that uses one does not compile |
| `BUFSIZ`, `FOPEN_MAX` | 4096, 16 | 512, 32 |
| `time_t`, `clock_t` | `long` | `long` too (32 bit; the Norcroft Shared C Library's own header has an `unsigned int`). `localtime` is `gmtime`: the Territory Manager's time zone is not read |
| a file made by `fopen (name, "w")` | type Text (&FFF), as the Shared C Library's source does | type Data (&FFD); `fopen` cannot set a type: call `OS_File` 18 yourself |
| the default language | `gnu89`, `gnu++98`; an implicit declaration is a warning | `gnu23`, `gnu++20`: see "Language level" above |
| `strdup`, `strcasecmp` under strict `-std=c99` | `strdup` undeclared (a warning), `strcasecmp` declared | both undeclared (an error): `-std=gnu99` or `-D_DEFAULT_SOURCE` |
| function names for the post-mortem backtrace | `-mpoke-function-name` is on by default: the name of each function is stored before its code | accepted, but off unless you give it (objdump shows the name before the code only with the option) |
| a socket number | the Internet module's handle | a file descriptor: `__modlib_socket_handle (fd)` gives the handle |
| `<fenv.h>` | the Shared C Library's | software only: `feraiseexcept` and the others keep flags that the arithmetic never sets, and the rounding mode is always to nearest (`fesetround` of another mode fails) |
| `#ifdef __TARGET_SCL__` code | the Shared C Library is there | the macro is defined, but there is no Shared C Library: code that calls `_kernel_init`, `x$divide` ... will not link |
| size of the module | see the table under "When to stay with GCCSDK 4.7.4" | the C library is linked in; unused functions are dropped (16.2.0-23) |

## What is the same as in 4.7.4

* **The stack.** The C code of a module runs on the kernel's SVC stack (32 KB for the whole OS) or the IRQ stack (8 KB), as it did: GCCSDK's own documentation says that module code in SVC and IRQ mode is compiled **without** stack checking (`-mmodule` implies `-mno-apcs-stack-check`), because those stacks are not chunked. There is no private stack and no overflow check; `long __modlib_stack_left (void)` (`<kernel.h>`) says how many bytes are left on the SVC stack.
* **Sockets.** The calls of Acorn's TCPIPLibs (`socketclose`, `socketread`, `socketwrite`, `socketioctl`) build as they did, and since 16.2.0-23 so does a source that treats a socket as a file, as UnixLib and the `unixlib` library of the TCPIPLibs do: `close`, `read`, `write`, `ioctl` (`FIONBIO` ...) and `fcntl` on the number that `socket` or `accept` returned, `select` with it, `dup`. A socket is a file descriptor of the same table as `open`'s ([MODULES.md](MODULES.md#sockets)). The example is Sunfish, an NFS client filing system (MIT; 40 C compilations and four ObjAsm files, 298 KB): from its unmodified source (add `-D_DEFAULT_SOURCE`; the four `.s` files need the `asasm` fix above), with no `-lTCPIPLibs` and no `-liconv`, it loads, mounts an NFS export and reads a file on the Pi (read only; the kit's `iconv` knows UTF-8, ASCII, ISO-8859-1, UTF-16 and UTF-32 only; [tests/sunfish](../tests/sunfish/README.md)). Before 16.2.0-23 a socket was the Internet module's own number and `ioctl` and `close` on it gave "Bad file descriptor" (a module had to be changed to use `socketioctl` and `socketclose`).
* **C++** in a module: 4.7.4 had constructors and destructors; here they are there too (`module-is-c-plus-plus:`), and `new`, virtual functions, templates and the containers of the C++ library work as well ([MODULES.md](MODULES.md#c-in-modules)); there are no exceptions, no RTTI and no streams. 4.7.4 has more: a C++ module with `try`/`catch`, `typeid`, `std::vector`, `std::string`, `std::map` and `std::cout` compiles and links with `arm-unknown-riscos-g++ -mmodule` (whether it runs in SVC mode was not tested).

## What is still missing

| Missing | What to do |
|---|---|
| `library-enter-code:`, `library-initialisation-code:`, `-tnorcroft`, `-26bit`, `-blank` | nothing: the first two belong to the Shared C Library, `-26bit` and `-tnorcroft` to Norcroft (4.7.4's compiler makes no 26-bit code either); `-blank` writes an empty CMHG file and is not here. `-apcs 3/reent` is refused here and by CMunge 0.76 |
| the `help` flag of a command, `swi-handler-code: f (flags-capable:)` | CMunge 0.76 refuses both too; write the handler by hand (a generic veneer does the job) |
| `module-is-runnable: simple-app:` | CMunge's own comment calls it "VERY experimental"; use `module-is-runnable:` |
| the wide input and output functions (`fwprintf`, `fgetwc`, `swprintf`, `swscanf` ...), `wcsftime` | the Shared C Library of 4.7.4 did not have them either. (`%ls` and `%lc` in `printf` are not wide here: they are read as `%s` and `%c`) |
| `mkdir`, `chdir`, `opendir`, `getcwd`, `fork`, `getpid`, `pipe`, `mmap` ... | 4.7.4's module library did not have them either (checked with `nm`). Here a module has descriptors for files (`open`, `read`, `write`, `lseek`, `fstat`, `ftruncate` ... since 16.2.0-21; `stat`, `lstat`, `access`, `dup`, `dup2`, `fsync` since 16.2.0-22: 4.7.4's module library has none of those) and `FILE *` streams |
| `-mlibscl` for an application (AIF), `elf2aif` | not supported: `-mlibscl` without `-mmodule` is ignored (you get a UnixLib ELF program), there is no `elf2aif`; keep 4.7.4 |
| DeskLib (`libDesk.a`, `libDesk-sclmodule.a`) | built from your copy of [DeskLib32](https://github.com/adyoull/desklib32) with `install-desklib.py` ([DESKLIB.md](DESKLIB.md)); not shipped, its licence allows only unaltered copies. OSLib and OSLibSupport are built from source by `install-oslib.py` ([OSLIB.md](OSLIB.md)), FlexLib and SFLib by `install-flexlib.py` and `install-sflib.py` ([FLEXLIB.md](FLEXLIB.md)), RUfl by `install-rufl.py` ([RUFL.md](RUFL.md)), and NetSurf with its whole stack by `build-netsurf.py` ([NETSURF.md](NETSURF.md)); the other libraries that GCCSDK ships for the old ABI cannot be linked: build them from source for this tool chain |
| a private stack, or stack checking (`-mapcs-stack-check`) | 4.7.4 did not have them for module code in SVC and IRQ mode; it documents `-mapcs-stack-check` for code that runs in USER mode (the start code of a runnable module). Here the option is accepted with a warning and does nothing |
| Norcroft inline assembler, `__value_in_regs`, `__swi` (as the RISC OS sources use them) | GCC cannot read them (4.7.4's GCC neither): rewrite those blocks ([OS-MODULES.md](OS-MODULES.md)) |

## Checking a Makefile

The quickest check is to build the module with the unchanged Makefile and look at the first error: it is one of the lines above in almost every case. If the error is something else, please report it with the line that failed ([the issues page](https://github.com/robheaton/riscos-gcc16/issues)): this page was written from exactly such lists, from the real modules of GCCSDK.
