Subject: UnixLib: scanf () has no long long conversions (%llx, %lld, %ju, %zu,
         %hhd ...): values are cut to 32 bits, %hhd writes two bytes, %Lf
         stores a float (found because the native lto1 cannot read its own
         objects)
Attach:  patches/unixlib-scanf-long-long.patch (204 lines, one file)
         repro/scanf/ (scantest.c, scanfcheck.c with its table scantab,
         build-model.sh: a host model of the old and of the patched function)

Summary
-------
vfscanf () in libunixlib/stdio/scanf.c is the 4.4BSD scanner. It knows three
length modifiers, l, L and h. Every integer conversion goes through strtol or
strtoul, and the result is stored as a long, short, int or pointer. So for
what the C standard added later it silently does the wrong thing:

  %llx %lld %llu %lli %llo   the second 'l' sets the same flag again, so the
        number is converted by strtoul / strtol: it is limited to 32 bits (a
        16 digit hex number gives ULONG_MAX), and only the LOW word of the
        long long is stored; the high word keeps what was there before.
  %hhd %hhx ...              the second 'h' sets the same flag again: a short
        is stored into the one byte target, one byte past it.
  %jd %zu %td %qd ...        j, z, t and q are not modifiers. They reach the
        "default: /* compat */" branch of the conversion switch, which takes
        them for a decimal strtol conversion; the real conversion letter is
        then matched as literal text. ("%zx" of "89abcdef" stores 89 and
        returns 1.)
  %Lf                        stores a float (4 bytes) into a long double (8
        bytes on this ABI): only l sets the flag that selects the double
        store; L sets another one, and the float store is the else branch.

The patch (13 hunks, 68 lines added, 19 removed) adds a long long conversion
(strtoll / strtoull) for ll, q and j, hh (a char), z and t, %n with them, and
a long double store (strtold) for %Lf. What no modifier, l and h did before
is unchanged: the old and the new function give identical results for them
(the table below, and a host model). L changes only for %Lf.

How I found it
--------------
The native GCC 16.2.0 that I run on RISC OS could not link anything with
-flto. lto1 stopped with

  lto1: fatal error: bytecode stream in file 'dm.o' generated with GCC
        compiler older than 10.0

for every object, although the objects were fine. lto1 finds the sections of
an LTO object by their names, .gnu.lto_.lto.<id>, where <id> is a 64 bit hash
written as 16 hex digits (for example f8f459e5fb71f146), and it reads the id
back from the name with (gcc/lto/lto-common.cc, lto_section_with_id)

  sscanf (s, "." HOST_WIDE_INT_PRINT_HEX_PURE, id)      i.e.  ".%llx"

UnixLib stored 0xffffffff in the low word of the variable (strtoul's overflow
value) and left the high word alone, so the name that lto1 rebuilt from the id
never matched a section, lto_get_summary_section_data () returned NULL, and
lto1 reported the "older than 10.0" error. The same GCC reads archive member
offsets with sscanf (p, "@%" PRIi64 "%n", ...) (lto-wrapper.cc three times,
lto/lto-object.cc once) and has a resolution file reader with the same kind of
format (used with the linker plugin only); they need the same repair.

(The failure was also silent for a while: the output of the processes that
collect2 starts with a redirected stdout ends up in the temporary file that
collect2 then reads as a list of file names. That is handled in collect2 and
lto-wrapper in my port and is not part of this report.)

The patch
---------
 * Two new flags, LONGLONG (ll, q, j) and CHARSZ (hh; SHORT stays set), and
   a second conversion pointer, ccfnll, set next to ccfn at every integer
   conversion: strtoll for d and i, strtoull for o u x p.
 * 'l' when LONG is already set sets LONGLONG; 'h' when SHORT is already set
   sets CHARSZ; 'j' and 'q' set LONGLONG. 'z' and 't' mean as big as size_t
   and ptrdiff_t: nothing to do while those are int sized, as they are on
   this target; the code tests sizeof and sets LONG or LONGLONG where they are
   bigger, so that it stays right on a 64 bit target.
 * The store: LONGLONG stores an unsigned long long; otherwise as before, with
   a char for CHARSZ. %n stores a long long for LONGLONG and a char for CHARSZ.
 * %Lf (LONGDBL) stores a long double converted by strtold.
 * #include <stddef.h> for size_t and ptrdiff_t.

Deliberately not changed: %D %O %X stay the BSD synonyms of %ld %lo %lx and
%E %F of %le %lf; %G, %a and %A are still not conversions (they go to the
default branch, a decimal integer conversion); no wide character functions; the
behaviour for numbers outside the range of the target. Two differences from
glibc that were there before and that the patch leaves alone (the comparison
with glibc leaves such inputs out): a hex prefix that a width cuts off ("%2x"
of "0x1F"), and a bare "0x" ("%x" of "0x"): UnixLib returns 1 and stores 0,
glibc returns 0.

%Lf uses UnixLib's strtold, which is a placeholder that calls strtod ("until
we have time to get a proper version"). That is right where long double is
the same as double, as it is on this ABI; I did not look further.

Suggested ChangeLog entry (date and name are yours):

	* stdio/scanf.c (vfscanf): Understand the length modifiers ll, q,
	j, hh, z and t, and %Lf.  Convert with strtoll / strtoull into a
	long long for ll, q and j, store a char for hh.  Before, ll was l,
	hh was h, j z t q were taken for a decimal conversion, and %Lf
	stored a float.  Include <stddef.h>.

What I did not do
-----------------
I did not look at the history of the file in svn, nor search the mailing list
or the bug tracker for it, so I do not know whether the problem is known or
since when it is there. I did not look at wide character functions, if there
are any, nor at other code that parses numbers (apart from the strtold remark
above). The comparison table is made by glibc on a 64 bit host, with the 32 bit
target emulated in the model and only the values inside the 32 bit range
compared: it says nothing about numbers outside that range. I did not try
a 64 bit target for the z and t paths: they are written to be right there
and tested only through the int sized case.

assistant (Claude); every run on the machine was mine.
