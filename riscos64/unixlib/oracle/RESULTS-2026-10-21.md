# UnixLib's own tests (the oracle) on UnixLib 64: first table (21 October 2026)

Phase 0 of `PLAN-unixlib64-next.md`. The 67 test programs of the 32-bit UnixLib (`unixlib/root/libunixlib/test/*/*.c`, without `scl`) were built for AArch64 with
`aarch64-riscos-gcc -munixlib` (tool chain 0.10) by `build-oracle.sh` and run on Pyromaniac (without the time limit of the build service) (`--direct`: the skeleton's `fork` is not available) with the shell of
GNU tools 11, one program per job, 120 seconds each. Nothing was fixed in this pass: it is the baseline.

## What it says
* 30 of the 41 programs that build pass; the 11 others are mostly known gaps (`.`/`..`, `iconv`, `fork`) and a few **new real bugs**: `strsep`, `longjmp` with `alloca`,
  and two `printf` corner cases of picolibc.
* The 26 that do not build are about **8 library gaps** (`kernel.h`, `syslog.h`, `ieee754.h`, `fpu_control.h`, `environ`, `PTHREAD_CANCELED`, `long double` constants, `tgmath.h`), about **10 old
  test assumptions** that need small edits, and 3 tests that are 32-bit only.
* Not in this suite: `stdio`'s `tfformat`/`tiformat` are the only ones that run thousands of cases; `string` and `stdlib` are small. It is a start, not a proof.

## Next (Phase 1, from this table)
`kernel.h` with the `_kernel_*` functions, `syslog.h` and the syslog functions, `ieee754.h`, `fpu_control.h`, `environ` under `_GNU_SOURCE`,
`PTHREAD_CANCELED`, `long double` constants in `math.h`, and look at `strsep`, `longjmp`+`alloca`, `%#.0o`, `%.100g`; then edit the tests that need `#include`s and re-run.

Files: `build-oracle.sh` (builds), results of the run in `/var/tmp/a64/oracle/res/` (one `oj_*.txt` per test), the build log in `/var/tmp/a64/oracle/log/`.

### Check with the rebuilt ports (08:03)
All the ports were built again with the SDK as it is now (`ports7`). The first attempt exposed a mistake of mine in the first `readdir` change: `d_ino` was computed with a system call per entry (about 60 ms each in the emulator), so one scan of the gawk test directory (1,661 entries) took **98 seconds** and every test job stopped. Fixed: the directory is canonicalised once per stream and the inode of an entry is a hash of "directory.leaf" (3 seconds for the same scan; `d_ino == st_ino` still holds).
With the rebuilt programs a sample of the suites gives: gawk 12 chunks, 48 items pass, 0 fail; sed 20 tests, 16 pass, 3 skipped, 0 fail; grep 28 jobs, 10 pass, 15 skipped, 1 not passing (`stack-overflow`, known), the rest still running when this was written.

# Evening of 21 October (17:00-18:00): Phase 1 continued, Phase 2 survey

**Full regression with the Phase 1 library** (all ports rebuilt with it, `ports7`): gawk 282 items, only `poundbang` and `printf-corners` fail; sed 46 pass, 16 skipped by the suite, 4 not passing (the four known); grep 50 pass, 71 skipped, 4 not passing (`symlink`, `stack-overflow`, the two Spencer tests); Lua `l1` and `l3` pass. Identical to the baseline before Phase 1: no regression.

**Fixed this evening** (uncommitted, in the SDK and picolibc patches):
* `pthread/cond` (never ended): threads here switch only at blocking calls, a thread that waits by polling the clock never let the others run, and the signals it sent meanwhile were lost. `clock ()`, `times ()`, `gettimeofday ()` and `clock_gettime ()` now give the other threads a turn, at most once for each centisecond (`__ul64_timeslice` in `pthread.c`, a weak reference from `riscos_syscalls.c`). The test passes (12 s).
* picolibc `%#.0o` of 0 (`tools/picolibc-printf-alt-octal.patch`): `stdio/tiformat` passes (0 errors in 5,010).
* picolibc `long double` printing (`tools/picolibc-ldtoa-rounding.patch`): the conversion truncated instead of rounding (`%.0Lf` of 0.84 gave 0, `%Lg` of 123456.789 gave 123456) because the rounding increment was a factor of 10 too small and a value that rounds to a unit beyond the first digit was never rounded up. Now rounds to nearest and exact ties to even, as glibc does (15 of 24 test rows differed from libquadmath, 5 remain: near-ties like 2.675 that need exact big integer arithmetic).
* **`MB_LEN_MAX` was 1**, while `MB_CUR_MAX` is 6 in the UTF-8 locales: a program with a buffer of `MB_LEN_MAX` bytes for `wcrtomb` made the fortified check say "overflow detected" and end. Now 16 (as glibc; `fix-picolibc-headers.py` and `refresh-sdk.sh` for GCC's own `limits.h`). `sed` with `\b`, `\<`, `\B` in a UTF-8 locale died with it.
* A program started by another (`env sed ...`) got its parent's name as `argv[0]` (`Sh$Argv0` stayed in `environ` and was exported again): now removed from `environ` at start-up, and `posix_spawn`/`exec*` pass the `argv[0]` they are given as the name (error messages say `sed:`, not `/work/sed:` or `env:`).
* `b64_ntop`, `b64_pton` (RFC 4648 test vectors pass).

**Known, not fixed:** `printf` of a double prints at most 17 significant digits and then zeros (`%.30f` of 0.1 gives `0.100000000000000000000000000000`, glibc gives the exact expansion `0.100000000000000005551115123126`): picolibc's float printing is built around a 17-digit buffer; an exact version needs a different conversion (big integer arithmetic). `random ()` is not glibc's generator (a different sequence for the same seed). `initstate`/`setstate` are missing for that reason.

**Phase 2 survey:**
* `setlocale` already accepts `C`, `POSIX`, and any `xx_YY.UTF-8` / `.utf8` name with UTF-8 multibyte handling (`MB_CUR_MAX` 6). `iswalpha`, `iswalnum`, `towupper`, `towlower`, `iswspace`, `iswpunct`, `mbrtowc`, `wcrtomb`, `wcwidth` match glibc on Latin, Greek, Cyrillic and CJK samples.
* The 24 grep jobs and 5 sed tests "skipped: en_US.UTF-8 locale not found" were skipped by the test harness, not by the library: it needs a small helper program, `get-mb-cur-max`, that was never built. With it (`/var/tmp/a64/helpers/get-mb-cur-max,ff8` into the `bin` of the test directories) the grep locale tests run: **14 pass, 1 fails** (`equiv-classes`: `[[=e=]]` must match `é`, which needs the locale's collation data), 8 skipped for other reasons (PCRE, `timeout`). Sed: 2 pass, 5 fail (two were the `env:` name; `\b` in a UTF-8 locale was the `MB_LEN_MAX` bug; `badenc` and `utf8-ru` to look at after the rebuild).
* What is really missing for Phase 2: **collation** (`strcoll`, `strxfrm`: `strcoll ("a", "B")` is 1 here in code point order, -1 in glibc's `en_US`; `[[=e=]]` equivalence classes), `iconv`, `nl_langinfo` and `strftime`/`strptime` names in the locales; the multibyte core works.
