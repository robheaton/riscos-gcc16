# kit: C modules for RISC OS 64 (first version, 16 October 2026)

`aarch64-riscos-gcc -mmodule -O2 hello64.c hello64_hdr.S -o Hello64` makes `Hello64,ffa`, a 64-bit module written in C, that loads and works on RISC OS Pyromaniac.

* **The C library** (16 October 2026): `build-kit.sh` also builds `libmodkit64.a`, the 129 sources of `modkit/lib` for AArch64 (floating point allowed, `MODLIB_HOST` with `platform64.c`/`modsys64.S` as the SWI layer, `heap.c`, `exit.c`, `setjmp64.S` with AArch64 branches), and the driver links it with `-mmodule` and `-mmodule-fp` and puts `modkit/include` on the include path: `<stdio.h> <stdlib.h> <string.h> <ctype.h> <math.h> <time.h>`... work in a module (`printf` writes to the screen with OS_WriteC, `malloc` takes RMA blocks, 16-byte aligned). `examples/libmod64` uses snprintf (with `%f`), qsort, bsearch, strtol, strtod, sscanf, malloc, string and ctype functions, `<math.h>` and `<time.h>`: 12 checks pass on Pyromaniac. Use `-mmodule-fp` for a module that calls the maths or `%f`. Files, `fopen` and the rest of stdio are in the library too (the program-mode and module-mode tests of `libtest/` run them); the sockets and C++ parts of the 32-bit library are not in it.
* **`_swi`, `_swix` and OSLib** (16 October 2026): `<swis.h>`'s `_swi`/`_swix`/`_vswi`/`_vswix` are in `libmodkit64.a` (`modkit/lib/swix.c`); on AArch64 the words of a `_BLOCK` are read from the argument list into an array (a `va_list` is not a pointer there), so `_BLOCK` takes up to 16 words. `examples/swi64` tests inputs, outputs, flags, `_RETURN`, errors and `_BLOCK` (12 checks pass on Pyromaniac). The OSLib veneers of `modkit/bin/mkoslib.py` work unchanged for the simple SWIs (`examples/oslib64/build.sh` builds the OSLib test module of the 32-bit kit: `MKOSLIB_NM=aarch64-none-elf-nm` for the object scan); **structures that hold pointers (OSLib's wimp icons, ...) do not have the layout the OS expects on a 64-bit machine** (a pointer is 8 bytes there), so the Wimp is not usable that way yet. All addresses given to a SWI are cut to 32 bits: they must be below 4 GB, as they are today.
* `include/modkit64.h`: the C interface. You define `module_init`, `module_final`, `module_swi`, `module_command`, `module_service` (all optional); the kit has `mk_error` (an error block in the RMA: every error
  that leaves the module is copied there, because a program cannot read an error block in the module's own code), `mk_swi`, `mk_rma_claim/free`, `mk_printf`, and `memcpy` and friends. 
* the header of the module (the header words, the tables of commands, SWI names and service numbers) is a small assembler file that includes `modcore64.S` (the relocator, the entry veneers, the service glue).
  `examples/hello64/hello64_hdr.S` is written by hand; it is what `cmunge` will generate from a CMHG file.
* `cmunge64.py` (16 October 2026): CMHG file -> the module header (AArch64 assembler) and the C header, with the parser and the C header of the 32-bit `modkit/bin/cmunge`. `cmunge64.py -d hello64h.h -o hello64_hdr.o hello64.cmhg`,
  then `aarch64-riscos-gcc -mmodule hello64c.c hello64_hdr.o -o Hello64` (`examples/hello64c`: the same module as `examples/hello64`, with a CMHG file; it passes the same 8 checks on Pyromaniac).
  The handlers use `modkit/include/kernel.h` (`_kernel_oserror`, `_kernel_swi_regs`). Supported: title/help/date strings, initialisation and finalisation code, the service call handler (with or without service numbers), the command table (handlers per
  command, `no-handler:`), the SWI chunk, decoding table (`NAME/FN`) and handler, the messages file, `swi-decoding-code` (one function, or NAME/NUMBER) and `error-identifiers` (the error blocks are in the
  module; the kit copies them to the RMA when a handler returns one). Refused with a message, for now: the veneers (irq, vector, generic, event, vector traps: the kernel's conventions are not known),
  `module-is-runnable`, `module-is-c-plus-plus`, `pdriver-handler`. Of the 26 CMHG files in `modkit/tests` and `modkit/examples`, 12 are accepted and assemble; the other 14 use one of those.
  `examples/dec64` tests the two new features. **Pyromaniac ignores the SWI decoding code** (it decodes names with the table only), so the module's own entry is tested by calling it from the module (`Dec64_SelfTest`): both
  forms pass; a kernel may call it differently.
* `module64.ld` (the layout: linked at 4, loaded at a page plus 4, a read-write region on a page boundary, the zero-initialised area after the image, written into the file as zeros by `modreloc64.py`: a kernel is not required to allocate it), `modflags.sh` (the compiler options: position independent
  without a GOT, hidden symbols, no floating point or vector registers, x18 reserved), `../tools/modreloc64.py` (lists the 64-bit words that hold an address in a table that the module relocates itself with,
  refuses what cannot be relocated, checks the header, writes the image).
* `-mmodule-fp` (instead of `-mmodule`) allows hardware floating point and vector registers in the module: Pyromaniac keeps the caller's v0-v31 and FPCR across a SWI of a module. `examples/fpmod64` computes in double precision in a module and passes on Pyromaniac; interrupt handlers and the other entries were not tested for this. The default stays `-mgeneral-regs-only`.
* `build-kit.sh` builds the runtime objects (`out/kit-lib/modrt64.o`, `modswi64.o`); `examples/hello64/hello64test.c` is a program that tests the module (`tools/run_on_service.py`, job `hello64`: 8 checks pass on Pyromaniac).

**Service calls and the register block.** The service entry of a module is a plain one, called for every service; the kit filters the numbers of the module's list itself and handles both conventions that are known:
the number in `x1` with the other registers as the caller gave them (RISC OS Pyromaniac), or the number in `x0` with `x1` = the address of a block of 64-bit slots, a claim being a 0 written into r1 of the block. The
handler (`module_service`, or the CMHG `service-call-handler`) is the same for both: it gets `r[0]`-`r[9]`, sets `r[1] = 0` to claim. The slots of the register block of a SWI are 32 bits on Pyromaniac and 64 bits on a kernel
with 64-bit slots; the kit finds out when the module starts and converts, so a handler always sees `mk_reg` (32 bits, like `_kernel_swi_regs`). `examples/svc64` tests the service entry in both conventions.

What is not decided: floating point at EL1 on kernels other than Pyromaniac (the example `fpmod64` works there), vectors/IRQ/events.
